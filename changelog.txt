== Typography Stylist — Full Changelog ==

The complete version history of Typography Stylist. Recent releases are also
summarized in readme.txt; release notes with downloads live on GitHub:
https://github.com/mattcowan/typography-stylist-for-wordpress/releases


== Changelog ==

= Unreleased =
* **NEW: optional Glyphs and Paragraph Styles buttons in the block toolbar.** Both features were previously only reachable *through* another panel — the glyph browser sat behind the Typography Stylist popover's features section, and paragraph styles were a dropdown inside that same popover and the sidebar. Two new Options settings put them one click away instead. "Glyphs Toolbar Button" adds a Glyphs button beside the Typography Stylist button, in the Typography Stylist block and on regular headings and paragraphs; the panel opens on the font of whatever you have selected, replaces the selection with the glyph you pick, and keeps inserting after it as you click more. "Paragraph Styles Toolbar Button" adds a button to the Typography Stylist block that opens a browser showing every saved style **rendered in its own typeface** — real font, weight, letter spacing, and OpenType features, with sizes scaled into a readable range so a 64px display style still reads as larger than a 16px body style. Click a style to apply it. Both settings are **off by default**, so nothing changes in your editor unless you turn them on, and the buttons inside the existing panels stay exactly where they are.
* Fixed: the Paragraph Styles dropdown labelled every style's font "Default". It looked styles up by the wrong identifier and only searched uploaded font kits, so Adobe Fonts, custom font definitions, and adopted Font Library faces could never match. Style labels now name the actual font.
* **Fixed: the Glyphs Panel opened on the wrong font for text styled only by your theme.** A heading your theme sets in one of your fonts carries no plugin font of its own, so the panel had nothing to go on and silently loaded whichever font happened to be first in your list — you went looking for a swash and were browsing a different typeface entirely. The panel now resolves the font the text is actually rendering in, for both the toolbar button and the button inside the Typography Stylist panel, in the inline editor and the Typography Stylist block.
* **Fixed: text styled by your theme no longer loses its weight.** Themes make headings bold with CSS rather than a stored setting, and the plugin treated "no stored weight" as normal — so a bold heading quietly turned normal when converted to a Typography Stylist block, and a glyph inserted from the Glyphs Panel came out lighter than the headline around it. Both now use the weight the text is actually rendering at. This covers both conversion routes (the "Convert to Typography Stylist Block" button and the block menu's Transform to); a weight you set yourself still wins, and paragraphs keep whatever weight their theme gives them too.
* **Improved: the accessibility notice now appears at the top of the inline editor panel**, instead of below every feature control where you had to scroll past everything to discover that your selection had a problem. Its "Convert to Typography Stylist Block" action — the fix the notice is recommending — is now a button rather than a line of link text, in the notice and in the panel's standalone convert section.
* **NEW: the Glyphs Panel raises the same accessibility notice.** Opening the panel straight from the block toolbar skips the Typography Stylist panel, and with it the word-boundary check — so you could split a word by swapping in a glyph and never be told. The panel now shows the same warning at the top when your selection breaks a word, with the same one-click conversion to a Typography Stylist block (which closes the panel, since the conversion replaces the block it was pointed at).
* **Fixed: three settings did nothing when switched off.** "Disable Word Boundary Warning", "Inline Format: Add aria-label Attributes", and "Clear Button Confirmation" were passed to the editor as the text "0" rather than as false, and every non-empty string counts as true in JavaScript — so turning any of them off had no effect. All three now behave as their labels say. (The word-boundary warning had never been switchable at all: nothing in the editor read that setting.)
* **Fixed: applying a paragraph style to selected text no longer restyles the words around it.** Paragraph styles describe a whole paragraph, so the style browser applied them block-level — which meant styling one highlighted word also restyled every neighbouring word that carried no styling of its own. With text selected, the style now wraps just that text; with only a cursor it still applies to the whole block, and the browser says which it will do. Detaching follows the same scope.
* Fixed: the size labels in the paragraph style browser ("Fluid 20–48", "Fit ≤ 120px") were hardcoded English and could not be translated. They now go through the module's text domain, which also required giving its shared utility script its own script translations — those are registered per handle, not inherited from the editor script that depends on it.
* Developer: the toolbar-button click context now carries an `accessibility` object (word-boundary warning, whether conversion is available, and why not when it isn't), a `typost-convert-to-block` event lets an extension trigger the conversion its own UI offers, and `typost-apply-block-properties` accepts `applyTo: 'selection'` to scope a paragraph style to the selected text. See HOOKS.md.
* Developer: new `typost_editor_toolbar_buttons` JavaScript filter for adding block toolbar buttons (core renders them as real toolbar buttons so keyboard navigation is unaffected), plus `typost_admin_options_rows` / `typost_admin_options_checkboxes` PHP hooks for adding a single setting to the Options tab. See HOOKS.md.
* Changed: bumped the Glyphs Panel (1.3.0) and Paragraph Styles (1.2.0) module version constants so browsers pick up the updated module scripts.
* **NEW: choose what the Enter key does in a Typography Stylist block.** Pressing Enter in a Typography Stylist block has always added a line break and kept you in the same block — deliberate, because a multi-line headline should share one set of typography settings, but surprising if you expect the rest of the editor's behaviour. A new Options setting, "Enter Key in Typography Stylist Blocks", makes it a choice. It defaults to the existing line-break behaviour, so nothing changes unless you change it; turn it off and Enter splits the block like a core heading does, carrying the block's font, features, and spacing into the first half and starting a paragraph after it. Shift+Enter adds a line break either way, and existing content is untouched whichever setting you use. The Help tab now explains the difference between a Typography Stylist block and a regular heading, including how to add a line break inside a core heading (Shift+Enter) and how to merge a heading that has already split.
* **Fixed: "Convert to Typography Stylist Block" no longer disappears without explanation.** The inline editor hides the conversion when it genuinely cannot be performed — the block is locked, or its parent block restricts which blocks are allowed inside it — but since v2.0 it hid the action silently, which read as a missing feature rather than a constraint. The modal now says which of the two applies and names the parent block, so the fix (move the block out, or have the container allow `typost/block`) is obvious. The conversion is also offered for any eligible heading or paragraph now, not only when the accessibility notice about word boundaries appears.
* Developer: new `typost_can_convert_to_block` JavaScript filter for overriding that capability decision, and the Typography Stylist block's `splitting` support is registered server-side from the new option (see HOOKS.md).
* **Improved: the settings page no longer reloads.** Every action on Settings → Typography Stylist that used to end in a full page reload — uploading a font kit, adding an Adobe Fonts project or custom font definition, saving font edits, deleting a font, registering/removing fonts in the WP Font Library (single and bulk), bulk weight detection, and the Options/Accessibility/Clear Cache forms — now updates the page in place over the REST API. After a font change the font list, the Font Features preview-font selector (your selection is preserved), the deletion modal's replacement list, the Replacement Fonts tab, and the @font-face/--font-N CSS all refresh together, so nothing on any tab goes stale; newly uploaded fonts are previewable immediately. Changing the admin color scheme restyles the page live. Extension hooks are unaffected: the refreshed fragments are server-rendered through the same template functions (badges, per-font axis rows), and the typost:font-saved / typost:fonts-added waitUntil contract is preserved — extensions' saves still complete before the refresh. Every update is announced to screen readers through polite aria-live regions, keyboard focus is kept anchored when the list under it is replaced, and the forms keep working without JavaScript via their original POST handlers. Also fixed: the Options and Accessibility checkboxes read stale option names, so their displayed state never reflected previous saves.
* **NEW: Fit-to-width blocks can be saved as Paragraph Styles.** Saving a style from a block in Fit to width mode now captures the full fit look as a first-class style property: the fit mode itself, the maximum-size cap, and the fallback sizes. Applying the style to another Typography Stylist block switches it into fit mode and re-measures its own lines (per-line sizes are content-specific and never copied). The style's CSS now also emits the fluid fallback size for fit styles, so browsers without container-query support get fluid sizing instead of the inherited theme size — this also restores the fallback for styled fit blocks, which previously lost it. The Paragraph Styles admin tab shows these styles as "Fit to width (fallback X–Ypx)" instead of the garbled "fitpx". In the inline editor (headings/paragraphs), where fitting to a block width has no meaning, applying a fit style renders the style's fluid fallback size; the Font Size dropdown states this plainly with a "Fit to Width (blocks only)" entry instead of showing a wrong value.
* **Fixed: the editor now renders a Typography Stylist block's font when only the numeric font ID is stored.** The block records its font twice — a numeric ID and a family-name string — and the editor preview required the string while the frontend required the ID. Blocks created through the editor UI always carry both, but content authored programmatically (builders, migrations, scripted imports) typically stores just the ID: the frontend rendered it correctly while the editor silently fell back to the theme's own heading font, and — worse — a Fit-to-width block edited in that state would have measured its line ratios against the wrong font. Both editor paths (the visual preview and the fit measurement) now resolve the font exactly like the frontend does: numeric ID first, family-name string as the fallback. Spans created before v1.1.6 (and Glyphs Panel cross-font insertions) carry the family name alongside the numeric font ID; only the ID was updated on font changes, so previews could render the old font and frontend font detection could load it unnecessarily. The stale name is now removed on any actual font change, while same-font re-applies and non-font edits (weight, spacing, line height) leave it untouched.

= 2.2.3 =
* **NEW: Per-selection relative size and vertical shift inside Fit-to-width blocks.** Two new sliders in the Quick Feature Toggles, shown only while the block uses Fit to width sizing: Relative size scales the selected text against its fitted line (10–100%), and Vertical shift nudges it up or down in em — so the wedding-invitation ampersand can sit small and optically centered between the names. Unlike absolute inline font sizes (which fit mode ignores because they would break the measured width ratio), these em-relative adjustments scale linearly with the line: the fitted line still fills the block width exactly at every viewport size, the scaled selection is included in measurement, and every change re-measures automatically. Vertical shift moves the glyph without changing its width, so it needs no re-measurement at all. Stored as data-fitscale / data-fitshift attributes with plain inline CSS on the styled span — zero frontend JavaScript, and the screen-reader heading is untouched. A scaled or shifted glyph swapped for an alternate in the Glyphs panel keeps its adjustments.

= 2.2.2 =
* **NEW: Fit-to-width sizing.** The Typography Stylist block gains a third font-sizing mode alongside Inherit and Responsive: each line of the block (split on line breaks) is sized so its text spans the full block width — the classic wedding-invitation/poster look where a short line renders huge and a long line renders smaller, all flush to the same width. The editor measures each line with its real fonts, weights, letter spacing, and OpenType features (swashes and ligatures change widths) and stores per-line ratios; the frontend renders with CSS container-query units and stays zero-JavaScript. Lines never wrap in this mode, inline font sizes on selections are ignored (the block controls sizing), an optional maximum-size cap stops short lines growing enormous on wide screens, and browsers without container-query support fall back to the responsive clamp() sizes. Automatic optical sizing is disabled on fit lines — fonts with an opsz axis (like Fraunces) change glyph widths with the rendered size, which would break the measured fit; setting the optical-size axis to a fixed value with the variable-font sliders still works. Editing is fully WYSIWYG in a single view: each line renders at its own fitted size while you type — the poster layout stays live as you edit — and Quick Feature Toggle changes (line height, fonts, features) preview and land on selections at their true rendered sizes. Under the hood the editor feeds RichText a per-line-wrapped copy of the content while the stored markup stays flat, so selections, the native formatting toolbar, undo, and paste all keep working unchanged. Existing blocks are untouched: non-fit save output is byte-identical, with a save deprecation as a safety net.
* Fixed: variable-font axis sliders in the Quick Feature Toggles now change only the selected text instead of restyling the whole block. The axis panels read their starting values from the selection but wrote changes to the block-level attribute — selecting one line and moving a slider restyled every line. QFT axis changes now land on the selection as a styled span (like the other QFT controls: with the caret in styled text they update that span in place; with no styled text they still fall back to the block attribute), while the sidebar Inspector sliders intentionally remain block-level. "Reset to defaults" removes the axis settings from the selection the same way.
* Fixed: an axis change (or any extension-applied block property) no longer applies to every Typography Stylist block on the page. The property-application event had no targeting, so every mounted block handled it; it is now handled only by the block whose Quick Feature Toggles modal is open (or, for sidebar events, the selected block).
* Fixed: the variable-font axis panels now initialize from the selection inside the iframed editor canvas (WordPress 6.3+). They walked the top document's selection, which cannot see block content in the iframe; the host editor now hands them the selection's axis values directly.
* Fixed: fonts registered in the WP Font Library (WordPress 6.5+) no longer lose their webfont on the frontend. The plugin skipped its own @font-face for every registered font on the assumption that WordPress prints those faces — but WordPress only prints faces for fonts activated in global styles, so registered-but-unactivated fonts (including every auto-registered upload) silently rendered with a local or system fallback while the editor looked correct. The plugin now checks what WordPress will actually print (merged theme.json families) and keeps emitting its own @font-face whenever the family isn't there; activating the font in the Site Editor still hands printing over to WordPress with no double output.
* Improved: the "Detect Axes from Font File" server fallback now reports the actual failure reason instead of a generic error.
* Developer: font-variation-settings values arriving through the typost-apply-block-properties extension event are validated on every apply path (invalid values are treated as empty, never partially applied into a style string).
* Changed: bumped the Variable Fonts module version constant (1.3.1) so browsers pick up the updated module scripts.
* Improved: the Glyphs panel can now be repositioned by dragging its title bar, matching the Quick Feature Toggles modal — useful when the panel covers the text you're inserting into.
* Fixed: choosing an alternate glyph is now reversible — clicking the base glyph in the Glyphs panel's alternates view restores the plain character. Previously the base glyph was inserted as plain text that inherited the very alternate being removed (an ampersand swapped for its "and" alternate could never be swapped back), and because the caret collapsed after each insertion, every retry appended another copy instead of replacing. Alternates-view clicks now keep the inserted glyph selected so consecutive picks swap in place, and base-glyph clicks explicitly clear the alternate while keeping the surrounding font, weight, and spacing. Extensions get the same powers via a new `swap` flag on the `typost-insert-content` event (see HOOKS.md).
* Changed: bumped the Glyphs Panel module version constant (1.2.2) so browsers pick up the updated module scripts.
* Fixed: fonts uploaded together in one ZIP no longer share each other's variable-font axes. Every font family extracted from a kit points at the same kit directory, and axis detection scanned that whole directory — so each family was assigned the axes of whichever font file happened to parse first. A ZIP containing EB Garamond (weight axis only) and Fraunces (optical size, SOFT, WONK, weight) gave Fraunces a lone weight slider and hid its custom axes, and gave non-variable fonts in the same ZIP a phantom weight slider in place of their real weight dropdown. Detection is now scoped to the font files each family's own @font-face rules reference, with the file path confined to the kit directory (kit CSS arrives inside an uploaded ZIP, so it is untrusted input). Fonts uploaded on their own were never affected.
* Improved: "Detect Axes from Font File" is now the way to repair fonts whose axes were mis-detected before this fix. It gained a server-side fallback that re-reads uploaded fonts with the corrected detection, so it still works when the in-browser font parser is unavailable. The browser is tried first because it can read real axis names out of the font ("Softness" rather than "SOFT") and can decompress WOFF2, which PHP cannot. Re-detection returns the axes for review; nothing is stored until Save Changes.
* Added: the detect button now says up front that it replaces every axis row and discards hand-set axis names, ranges, and defaults, and asks for confirmation before overwriting axes that are already defined. Detecting axes for the first time is still a single click.
* Changed: variable-font axis sliders now sit directly beneath the weight control in the inline editor and the Quick Feature Toggles, matching the block sidebar. Font Style previously came between them, separating the axis sliders from the weight they extend.

= 2.2.0 =
* Fixed: converting a styled heading or paragraph to a Typography Stylist block no longer destroys inline styling. The inline editor's convert button rebuilt the block from plain text whenever the selection crossed styled-span boundaries — exactly the selections that surface the convert option — wiping per-letter glyph alternates, swashes, fonts, and weights; it now applies the popover's settings over the existing markup with every surrounding span preserved (and on any failure converts with the content untouched rather than ever rebuilding from text). The block-menu transform's feature-extraction path is now guarded the same way: features are only lifted to block level when the spans carry nothing else that stripping them would silently delete. Converted spans also use the modern font-ID format so frontend font loading works.
* **NEW: Font Style (visual italic) controls.** All three editing surfaces gain a Font Style setting — block-level in the Typography Stylist block sidebar, per-selection in its Quick Feature Toggles, and per-selection in the inline editor for regular heading and paragraph blocks — selecting the font's italic (or upright) face. This is deliberately style-only: it never adds emphasis semantics, and the control says so — for semantic emphasis that screen readers announce, use the editor's own Italic button, which continues to work as before. Ideal for display typography where italic is a design choice, not emphasis.
* Fixed: feature previews now render with the italic face when the selection is italic — whether via the editor's Italic button (em), the new Font Style setting, or an italic styled span. Previously previews always showed the roman face, hiding italic-only glyphs like EB Garamond's swash italic capitals.
* Improved: the Glyphs Panel now browses the face variant actually rendering at your selection. Select italic text (via the Italic button or the Font Style setting) and open the panel: it loads the font’s italic file — with its own glyph set and features, like swash italic capitals — and renders every cell in that face. No toggle needed; the selection decides.
* Fixed: moving one variable-font axis slider no longer changes other axes. The axis panels emitted every axis on any change — including untouched axes pinned to the font file's built-in defaults, which differ from normal rendering (Fraunces' built-in weight default is 900, so nudging its WONK slider turned text bold). Only axes the author has actually adjusted (or that were already applied to the text) are written into font-variation-settings; "Reset to defaults" now returns axes to natural rendering instead of pinning them.
* Fixed: the variable-font Weight slider in the Quick Feature Toggles now works — it identified its context with a selector that matched nothing, dispatched to the wrong editor, and was silently dropped. The weight slider and the custom-axes panel also now share one axis session, so weight and custom-axis adjustments combine instead of overwriting each other.
* Changed: bumped the Variable Fonts module version constant (1.3.0) so browsers pick up the updated module scripts.
* Fixed: Quick Feature Toggle changes always land on the selected text. The per-setting apply paths read the live editor selection, which the popover itself can collapse by taking focus — toggles then silently applied block-wide (or not at all) despite an active selection. All appliers, clear/reset actions, and the settings-detection now share one selection resolver that falls back to the selection captured when the popover opened.
* Fixed: applying a font or feature over a whole span no longer wipes glyph alternates chosen from the Glyphs Panel — the rebuilt font-feature-settings honors raw indexed alternate values (e.g. a 2nd stylistic alternate) instead of flattening them, in both the apply and the feature-removal paths.
* Fixed: changing the font of styled text now clears variable-font axis values carried over from the previous font (axis settings are font-specific) — in whole-span merges and partial-selection splits alike.
* Fixed: splitting a styled span (partial-selection changes) corrupted spans whose attributes or styles contain double quotes — variable-font axis values and glyph alternates — because attribute values were not escaped when rebuilding the markup.
* Changed: the 3-level limit on nested styled spans is now enforced on every application path — previously one fallback path could exceed it. Applying to a fully-selected span merges in place regardless of depth, so existing deeply-nested content remains editable.
* Developer: span styling internals consolidated — one canonical style-string parser/builder (parseStyleString/buildStyleString), one shared whole-span merge (mergeTypostSpanStyling), and one QFT selection resolver, replacing seven copy-paste variants (see todo/refactor-style-string-helpers.md).
* Fixed: font (and other single-value) changes over multi-span selections in the Typography Stylist block's quick toggles now actually take effect. Applying a font to a selection containing styled spans wrapped them in a new span whose font-family every inner span overrode — the change looked like it did nothing, and repeated attempts deepened the nesting. The wrapped property is now removed from descendant spans so the new value renders throughout (their other settings are untouched), applied feature tags merge into descendants that declare their own feature settings, and descendant spans left with nothing are unwrapped.
* Fixed: changing one setting over a mixed selection in the inline editor no longer wipes the others. Selecting text that contained differently-styled spans (different features, sizes, or fonts on parts of the selection) and then changing any single setting — font family, weight, size, spacing, line height, or a feature toggle — replaced the entire selection with one uniform span built from the popover's controls, destroying every per-part setting. The editor now detects mixed selections and applies only the changed property to each styled run: a font change re-fonts everything while each part keeps its own features and sizes, and a feature toggle adds to (or removes from) each part's own feature set. Uniform selections and presets behave as before.
* Fixed: feature previews in the inline editor now render in the selection's actual font. Spans written since v1.1.6 carry only a numeric font ID (no legacy data-font family name), which the preview resolution didn't consult — previews silently fell back to the block's theme font. Affected any span created by the Typography Stylist block's quick toggles or built programmatically, including the wp.org Live Preview demo headline.
* Fixed: inserting a glyph from the Glyphs Panel no longer loses the surrounding span's styling. Swapping a selected letter for a feature glyph replaced its typost span outright, dropping font size (fixed and responsive), letter spacing, and line height — the inserted letter landed at the default size. Insertion now merges the replaced span's styling into the new glyph's span (the glyph's own feature, font, and weight still win), and glyphs swapped at the very start of a span no longer inherit formatting from the text before the span.
* Improved: the Glyphs Panel now opens straight to the selected text's alternates. A selected letter pre-fills the "Alternates for character" box; a short combination (up to 4 characters, e.g. "Th") shows its exact ligature alternates, falling back to the first letter's alternates when the font has no such ligature. Longer selections still open the full glyph grid, and the "All glyphs" button returns to it at any time.
* Changed: bumped the Glyphs Panel module version constant (1.2.1) so browsers pick up the updated module scripts.

= 2.1.2 =
* **NEW: automatic font-weight detection.** Newly uploaded font kits and newly added Adobe Fonts get their "Available Font Weights" checkboxes pre-set to only the weights the font actually ships, instead of all nine weights being enabled by default. Uploaded kits read the weights from their parsed (or generated) @font-face rules; Adobe Fonts read them from the kit stylesheet, fetched server-side when the project is added. WordPress Font Library fonts adopted from the editor picker carry their real weights too. Variable fonts covering the full 100–900 range keep all weights enabled (the weight slider replaces the dropdown anyway). Detection only ever narrows when it is confident — if the stylesheet can't be fetched or a kit can't be read, all weights stay enabled — and the checkboxes remain fully editable.
* New: one-click "Auto-detect weights for existing fonts" button on the Custom Fonts tab. Shown only for fonts added before weight detection existed that were never manually configured; it processes uploaded and Adobe fonts in one pass and disappears once every font is covered. Manual font definitions are skipped — there is no font file to read.
* Fixed: the Glyphs Panel reported "No readable font file is available" for variable fonts uploaded as font-only ZIPs — the generated @font-face CSS declares `format('truetype-variations')`, which the panel's file picker didn't recognize. Variable-font format hints now normalize to their base format, so variable fonts glyph-browse like any other uploaded font.

= 2.1.1 =
* Packaging: re-release of the 2.1.0 feature set under a fresh version number. The 2.1.0 tag's downloadable ZIP was cached against stale contents and never delivered the new files (Variable Fonts core integration, font metadata/sources modules, WordPress Font Library integration); 2.1.1 ships them correctly. See the 2.1.0 entry below for the full list of changes included in this release.

= 2.1.0 =
* Fixed: deleting an uploaded font now also removes its WordPress Font Library registration — previously the wp_font_family post survived the delete, kept printing @font-face rules for font files that no longer existed, and made the font appear to still be installed. Removal is ownership-guarded: only families the plugin itself registered are ever touched.
* Fixed: fonts registered in the WordPress Font Library no longer appear twice on the Custom Fonts tab (once as an uploaded font card and again in the read-only WP Library rows). The uploaded card with its "In WP Library" badge is now the single listing; genuine Library fonts — including orphaned registrations from older versions — remain visible.
* Removed: the required "Font Kit Name" field from the Upload Font Kit form. The name was stored but never displayed anywhere — font cards show the family names read from the kit. The REST endpoint still accepts an optional `name` and defaults to the ZIP filename, so API callers keep working.
* **NEW: font-only ZIPs (no CSS) are now accepted by Upload Font Kit.** Uploading a ZIP that contains just font files — e.g. a Google Fonts download — no longer fails with "No CSS file found in the font kit". The plugin reads each font's built-in metadata (name, OS/2, and fvar tables for TTF, OTF, and WOFF files) and generates the @font-face stylesheet automatically: correct family names, weights, italics, and for variable fonts a font-weight range with the matching format('…-variations'). Generated kits flow through the existing pipeline unchanged, including variable-font axis detection, the Variable card badge, and the editor weight slider. WOFF2 metadata cannot be read server-side, so WOFF2-only ZIPs fall back to filename-based detection and the upload shows a "review the generated font styles" warning. Kits whose CSS files contain no @font-face rules get the same fallback.
* **NEW: WordPress Font Library integration (WP 6.5+).** Uploaded webfont kits can now be registered in the WordPress Font Library (Appearance → Editor): newly uploaded fonts register automatically (toggle in Options), and existing fonts can be registered per font or in bulk from the Custom Fonts tab — registration is opt-in and fully reversible. Registered fonts keep their numeric IDs: the plugin's `--font-N` CSS variables alias to WordPress's `--wp--preset--font-family--{slug}` presets with a literal fallback, so all existing content, inline spans, and extension integrations keep rendering forever, even if a font is later removed from the Library. WordPress serves the font files for registered fonts (no double-loading). Adobe Fonts and custom font definitions remain plugin-managed by design (Adobe fonts load from Adobe's servers and may not be self-hosted).
* **NEW: WordPress Font Library fonts in the editor font pickers.** Both the inline editor and the Typography Stylist block now offer Library fonts (theme fonts and fonts installed via Appearance → Editor) in a dedicated picker group. Picking one adopts it seamlessly — it gets a numeric font ID like every other source, so the save format and all extensions work unchanged.
* **NEW: Variable font support.** Automatic axis detection on upload, per-axis admin configuration, and axis sliders in the editor — weight, width, slant, optical size, and any custom axes a font defines.
* **NEW: `typost_force_enqueue_font_ids` filter** — themes and extensions can force specific fonts to load on every page (for fonts referenced only from theme CSS, invisible to the content scan).
* Improved: extension data saves on the font edit form no longer race the page reload (`typost:font-saved` now provides a `waitUntil()` collector).
* Fixed: the per-page font CSS cache key now includes the used font IDs, so pages using different fonts can no longer share stale cached CSS.
* Fixed: font CSS variables now load inside the iframed block editor canvas (WP 6.3+) even when no uploaded webfont kits exist — Adobe Fonts, custom font definitions, and Font Library fonts previously fell back to the system font in the editor while rendering correctly on the frontend.
* Improved: the Glyphs Panel now distinguishes missing or failed parsing-library loads from genuinely unreadable fonts, shows honest error messages with technical detail, and offers a "Try again" button that retries without reloading the page.
* **NEW: "Detect Axes from Font File" button** — each font's Variable Font settings can now read the axis definitions (tag, name, min/max/default) straight from the font binary in your browser, instead of typing them by hand. Works for uploaded kits, Adobe Fonts, and custom font definitions, including WOFF2 files that upload-time detection can't parse. Detected axes fill the form for review; nothing is stored until you save.
* Improved: variable fonts without a weight (`wght`) axis no longer show the standard Font Weight dropdown in the editors — the variable axis sliders take its place (matching the per-font "Hide weight selection" admin setting, which previously only affected the admin form).
* Fixed: the "Variable Font Axes" section in the inline editor pop-up now has the same left/right padding as the other sections.
* Developer: the `typost_weight_control` JS filter recognizes a new `'hidden'` return value (suppress the weight control entirely), and the `typost_qft_after_font_controls` hook state now includes `inlineFontFamilyAtSelection` — see HOOKS.md.
* Fixed: extension panels rendered into font-dependent hook points (e.g. the Variable Font axis sliders) no longer go stale when the font is changed — the hook containers now remount with fresh state on font switch instead of keeping the previous font's controls.
* Improved: Variable Font quick-select buttons for custom axes now snap to round values (200, 400, 600 instead of 201, 401, 601) and are capped at 7 buttons so they fit on a single row; near-duplicate values next to the axis default are no longer generated.
* Added: variable font axes are now detected automatically when fonts are added — both webfont kit ZIP uploads and Adobe Fonts kits. Each family in a kit is checked individually, so kits mixing variable and static fonts work correctly; static families are simply left untouched.

* **NEW: Glyphs Panel (built into core) — the flagship feature of 2.0.** An Illustrator-style full-font glyph browser. Explore every character and OpenType feature in a font; search by character, U+ codepoint, or glyph name; filter by Unicode block, stylistic set, or OpenType feature; and view all alternates for a single character. Click or press Enter to insert any glyph (including indexed feature alternates) directly into your content via a "Glyphs…" button in the inline rich-text toolbar (any heading or paragraph), in the Typography Stylist block's Quick Feature Toggles, or from a dedicated "Glyphs" admin tab (browse + copy to clipboard); closing the panel returns you to the editor popover you launched it from. Accessible by design: the glyph grid is a fully keyboard-navigable ARIA grid (arrow keys, Home/End, Page Up/Down, Enter to insert) with row/column semantics, and insertions and result counts are announced to screen readers — inserted glyphs use the real Unicode character plus CSS font-feature-settings, so assistive technology always reads the underlying text.
