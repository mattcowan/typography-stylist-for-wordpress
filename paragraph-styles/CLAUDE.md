# CLAUDE.md — Paragraph Styles module

Self-contained module bundled into core in v2.3 (formerly the standalone `typography-stylist-paragraph-styles` extension plugin). Saves and loads named paragraph style presets — font, weight, size (fixed or responsive), letter spacing, line height, OpenType features, and variable font axes — applied from a dropdown panel in both editors and rendered by CSS class on the frontend. It consumes core's *public* extension API only, never core internals.

## Loading

`typography-stylist.php` (`typost_init()`) does `require_once TYPOST_PLUGIN_DIR . 'paragraph-styles/paragraph-styles.php'` then `Typost_Paragraph_Styles::get_instance()`, guarded by `! class_exists('Typost_Paragraph_Styles')` so the `final class` can never fatally redeclare — a still-active standalone copy of the former extension wins gracefully. Constants are guarded by `! defined('TYPOST_PS_VERSION')` for the same reason. This file has **no plugin header** and no `plugins_loaded` bootstrap.

## Data model

- `typost_paragraph_styles` — array of `{id, name, created, modified, properties, basedOn?, grepRules?, nestedRules?}` in wp_options (`basedOn` = parent style id, absent = none; see "Based On (#200)" below — with a parent, `properties` holds only the overrides; `grepRules` = ordered GREP rules, absent = none, see "GREP styles (#196)" below; `nestedRules` = ordered nested rules, absent = none, see "Nested styles (#195)" below). `properties` mirrors editor state keys: `fontId` (numeric), `fontWeight`, `fontStyle` (`'normal'`/`'italic'`/`'oblique'`; absent = inherit — style-owned since the italic fix, see below), `fontSize` (`'responsive'`, `'fit'`, or px value), `fontSizeUnit` (#233: `'rem'` on every sized style saved since; absent = a style saved before, which writes px exactly as before — `generate_style_css()`/`buildStyleCssBlock()` divide by 16 via `px_to_rem()`/`pxToRem()` (six decimals, keeps decimals on fixed sizes where the px path `intval()`s) only for `'rem'`, and a `'rem'` responsive/fit clamp also takes its vw term from `responsive_zoom_vw()`/`responsiveZoomVw()`, the zoom-safe slope of #234 (twin of core's `getResponsiveZoomLimit()`; px styles keep the author's slope); `buildPropertiesFromState(state, newUnit)` stores the site's new-content unit (`typostData.newFontSizeUnit`: `'rem'`, or `'px'` under the #248 Options setting) whenever it stores a size; `buildPropertiesForStyleSave(state, base, isUpdate, newUnit)` keeps the unit of a style that already had a size on Update Style (`'rem'` stays rem, anything else is px — whatever the setting is now), while Save as New and a size added to a sizeless style take the new-content unit; never compared by `isStyleModified` and never read by the editors' apply handlers — a block keeps its own unit; the sanitizer keeps only `'px'`/`'rem'`), `fontSizeMin/Preferred/Max`, `fitMaxSize` (fit styles only — always stored, 0 = uncapped), `letterSpacing` (thousandths of em), `lineHeight`, `features[]`, `fontVariationSettings`, `initialHang` (First Letter Hang in em, 0–1, three decimals; absent = 0, never stored as 0; emitted as `--typost-hang: N` — core's block `style.css` owns the `::first-letter` rule that consumes it, so the generators stay one rule block; block-level only, so `isStyleModified` compares it only when the editor state reports the key, which the inline editor never does — #242), `textCase` (#214: `'none'`/`'uppercase'`/`'lowercase'`/`'capitalize'`/`'small-caps'`/`'all-small-caps'`; absent = Default, never stored as `''`; whitelisted by `TEXT_CASE_VALUES`) with `fakeSmallCaps` (stored only as `false`, only with a small caps value; absent = allowed), and (#207) `alignment` (`'start'`/`'center'`/`'end'`/`'justify'`; absent = Default, never stored as `''`) with `alignLast` (`'center'`/`'end'`/`'justify'`, only with justify; absent = start), `wordSpacing` (thousandths of em like `letterSpacing`, can be negative) and `textWrap` (`'balance'`/`'pretty'`; absent = normal) — see "Alignment, word spacing and line breaking (#207)" below — (#208) `hyphens` (`'auto'` only; absent = off) with the group `hyphenateLimitWord`/`hyphenateLimitBefore`/`hyphenateLimitAfter` (integers 1–20, stored only when set and only with hyphenation on; absent = auto) and `hyphenateCharacter` (1–4 code points; absent = the language's hyphen) — see "Hyphenation (#208)" below — and (#215) `textColor` (`#rrggbb[aa]`, `var:preset|color|{slug}[|#rrggbb[aa]]`, or `transparent`; absent = the theme's color, never stored as `''`) with the outline group `textStrokeWidth` (px, 0–20, two decimals; absent = none), `textStrokeColor` (same color forms minus `transparent`; absent = the text color) and `textStrokePosition` (`'behind'` only; absent = on top) — see "Text color and outline (#215)" below. (#199) `indentStart`, `indentEnd`, `spaceBefore`, `spaceAfter` (lengths `'1.5em'`/`'24px'`, zero or more; absent = none, never stored as `''`), `firstLineIndent` (a length, negative = hanging indent) with `indentAfterSame` (stored only as `true`, only with a positive indent) — see "Indents and paragraph spacing (#199)" below. Case is style-owned with the same diff-only-when-reported rule and `buildPropertiesForStyleSave` carry as `initialHang`, but unlike the hang both core editors report it: the inline editor stores a span's case in `data-textcase`/`data-fakesmallcaps` (also under a style, so Detach writes it inline); `case_declarations()` / `caseDeclarations()` emit it after the hang and must stay identical (see root CLAUDE.md for the mapping). Because the REST PATCH **replaces** `properties` wholesale, Update Style and Save as New build their payload with `buildPropertiesForStyleSave(state, activeStyle.properties)`, which carries a block-only key the editor does not report from the active style; plain `buildPropertiesFromState` there let an inline-editor Update Style delete a shared style's hang from every block using it (PR review). When core gains a new text property, walk `docs/typography-property-checklist.md` — `fontStyle` shipped in core without these style-side integrations and silently dropped italic from every saved style.
- `typost_paragraph_styles_next_id` — sequential integer ID counter. Legacy timestamp IDs (`ps_1709312345_123`) are migrated on load; `legacyId` is kept so old CSS selectors keep matching.
- `typost_paragraph_styles_cache` / `typost_paragraph_styles_css_v2` (`CSS_CACHE_KEY`; the pre-#315 `typost_paragraph_styles_css` is only deleted by uninstall) — 12h transients (data / generated CSS), cleared on CRUD and `typost_cache_clear`. All cleaned up in core's `uninstall.php`.

## CSS rendering

`generate_style_css()` emits three selectors per style: a plain `.typost-ps-{id}` (0,1,0) for previews such as the style browser rows, and the block-level (`.typost-styled` + five `.typost-ps-{id}`) and inline-span (`.typost-styled[data-style-id="{id}"]` + four bare `[data-style-id]`) forms boosted to **(0,6,0)** by repeating the class/attribute, plus legacy-ID variants. The boost is deliberate (v2.3, QA finding PS-6): on the frontend save.js emits no inline styles under a `styleClass`, and theme heading rules — `.entry-content h2` at (0,1,1), a color-scheme rule with `:not()` at (0,3,4) on a real site and (0,5,2) in the editor, where WordPress prefixes theme editor styles with `.editor-styles-wrapper` — were silently overriding the style's font-family and font-weight. Inline `style=""` attributes still win, by design. `selectorSet()` in ps-utils.js is the JS twin. Font family is `var(--font-{fontId})` so core's font detection/@font-face loading applies unchanged. Responsive sizes use `clamp()` with core's 320/1920 viewport constants. Fit-to-width styles (`fontSize: 'fit'`) emit the **same fallback clamp** — on fit blocks the per-line `calc(...cqi)` sizes in content override it (the clamp restores the no-container-query fallback that save.js skips under `styleClass`); on inline spans fit degrades to the clamp by design. Applying a fit style block-level switches the target block into fit mode (it re-measures its own `fitLineSizes`; the stored `fitMaxSize` cap rides along). Output paths:

- **Frontend (per page since 2.3.1, #227):** `wp_head` priority 6 (right after core's font variables at 5) prints `<style id="typost-paragraph-styles-css">` holding **only the styles the page references**, generated per request with `generate_style_css()` in stored order (so the text is a subsequence of `get_all_css()`; no extra cache — the generator is a few string ops per style). References come from `style_refs_from_content()` (`data-style-id` + `typost-ps-N`, the same scan `font_ids_from_content()` now uses) over: the queried post on singular pages (content + excerpt), plus the synced patterns those reference (`get_synced_pattern_content()`, a regex twin of core's private helper — block comment attrs escape `<`/`>`, so `[^>]*?"ref":(\d+)` is safe), plus on classic themes (`! wp_is_block_theme()`) the `widget_block` option's stored content, so header block widgets print in the head rather than after the text (the option includes inactive widgets — over-printing a rule is the accepted cost); the refs a `render_block` collector (`collect_rendered_style_refs()`, strpos-gated) has seen so far — a **block theme renders its whole template before `wp_head`**, so template parts, query loops and block widgets are covered there; and `typost_force_enqueue_paragraph_style_ids` (`get_forced_style_refs()`, memoized; its styles' fonts are added to core's `typost_force_enqueue_font_ids`). `wp_footer` at `PHP_INT_MAX` (`output_late_style_css()`, last so popup/modal plugins that render blocks in `wp_footer` are counted) prints `<style id="typost-paragraph-styles-late-css">` for styles that blocks rendered **after** the head (classic-theme widgets/footers, custom query loops); `$printed_style_ids` keeps each rule to one print per request. Legacy `ps_…` refs match `legacyId` (`styles_for_refs()`). When `enqueue_editor_assets()` runs outside wp-admin (an editor mounted on a frontend page by a shortcode), every style prints — the editor must have them all, as in wp-admin. The scan's quote handling matters: saved block comment JSON stores `"` as backslash-u0022 (`serialize_block_attributes()` and the JS serializer), not as backslash-quote, so the `data-style-id` regex accepts that prefix — pattern-override text exists only in that form. (The Write/Edit tools decode a lone backslash-u sequence; the tests build it with `chr(92)`.) Not covered: non-block markup that carries a style class (classic text widgets, PHP templates) and HTML that a singular page loads by AJAX (related posts and the like) → the filter. **Pages that list posts print every style** (`page_lists_posts()`: `! is_singular()` with a non-empty main loop — archives, the blog page, search; a 404 or empty result prints only what it references): "load more" / infinite-scroll endpoints return post HTML without running `wp_head`/`wp_footer`, so the added posts can only use rules the first page printed. Scoping archives to their loop's styles (the issue's original criterion) regressed exactly that, flagged in review on 2026-10-02; Matt chose fail-safe archives over docs-plus-filter. An AJAX-aware alternative (inline `<style>` in AJAX/REST block output) is not built: it would put `<style>` into `content.rendered` for every REST consumer and still cannot see every loader shape. Core's Query Loop pagination was fine either way: its interactivity router copies the fetched page's `<style>` elements. Fonts for styles found only by the footer pass are an existing core gap (core's font scan never read template parts either).
- **Editor:** `enqueue_block_assets` + `wp_add_inline_style()` on a dummy handle (`typost-paragraph-styles-inline`) — this reaches **iframed** editors (WP 6.3+) as well as non-iframed ones; guarded by `is_admin()` to avoid double output on the frontend. Verified against the checklist in `todo/archive/editor-iframe-testing.md`.
- **In-session saves:** the server paths above print only at page load, and applying a style strips inline styles from the span/block (the class provides rendering) — so a style created or updated mid-session used to render as theme defaults until reload ("saved my style and the text went default-bold"). `editor.js` listens for `typost-paragraph-styles-updated` and rebuilds `<style id="typost-ps-dynamic-css">` in the top document **and** every `iframe[name="editor-canvas"]` from `buildStyleCssBlock()` in ps-utils — the JS twin of `generate_style_css()`. The panel dispatches that event *before* it dispatches the apply, so the rules exist by the time the span relies on them. **The two generators must stay byte-identical for the same properties — change both or neither.**

## Editor integration

`assets/js/editor.js` renders `ParagraphStylesPanel` (ES5 `wp.element`, no build step) into three hook points: `typost_inline_modal_top`, `typost_qft_modal_top`, `typost_inspector_top` (re-rendered on `typost_inline_modal_opened`). It reads state via the `typost_current_editor_state` filter (inspector maps to the `qft` state provider) and applies styles by dispatching the **`typost-apply-block-properties`** CustomEvent with `{properties, paragraphStyleId, styleClass, source}` — core's generic write bridge. (The standalone extension still dispatched the pre-2.0 `typost-apply-paragraph-style` name, which nothing listens to; fixed when bundling.) Active-style detection uses `state.paragraphStyleId`; the panel offers Update / Save as New / Detach when a style is active, with a `(modified)` badge computed by diffing state against stored properties. **QFT panel with text selected (#303):** every other control in the Quick Feature Toggles styles the selected text, but the panel used to capture the block's attributes and apply block-level, so Save from one letter restyled the whole block. `resolvePanelScope(editorSource, state)` (ps-utils) now gives `{applyTo, state, activeStyleId}`: for `'qft'` with `state.hasSelection` it is `applyTo: 'selection'`, `state.selection` (core's `resolveSelectionStyleState()`: the values set on the selected text — its spans, or the style of a `data-style-id` span — never the block's; no `initialHang`/`textCase` keys, so the diff skips them and Update Style keeps the style's own) and `selectionParagraphStyleId`; otherwise the block state as before. The Inspector panel is always block-level and the inline panel unchanged. Block-level in the block (`'inspector'`, `'qft'` with a caret) merges `state.block` (the block attributes' own explicit font/weight/style) over the shared explicit keys, which report the selected text's first (#278) — the Inspector badge used to show "(modified)" for a selected word with its own weight, and its Save stored that weight for the whole block; the browser's block-level Detach reads the same. Every action reads the scope at click time (select, Save, Save as New, Update, Detach), so core's existing selection route (`applyInlineParagraphStyle()`, with its split, strip and conflict confirm) does the apply. Save and Save as New send `savedFromSelection` (the inline panel always, the QFT panel in selection scope; `buildApplyEventDetail`'s 5th argument): the hosts skip the "replaces that styling" confirm when the selection has one set of values — block `selectionHasOneStyleSet()` (every touched span covers the whole selection, none carries its own case, which the capture leaves out), inline `!isMixedFormatSelection()` (its state captures case) — and still strip. A selection Detach (panel and browser, `paragraphStyleId: 0` + `applyTo: 'selection'`) runs core's `detachParagraphStyleFromSelection()`: each touched `data-style-id` span gets the style's values as data-* + declarations in the QFT's form (sizes in the style's unit, fit → its fallback clamp, case via `buildInlineCaseAttributes`/`caseDeclarations`), keeping any property it declares itself; it used to strip the attribute only and lose the look. On `typost-paragraph-style-apply-cancelled` the `'qft'`/`'inspector'` panels re-read the active style from the state instead of `lastActiveRef`: nothing was applied, and the Inspector panel (same `'qft'` state) hears the QFT's cancel too, which used to blank its badge. **Focus:** most panel actions remove the control that was used (badge ⇄ select switch, Update Style only while modified, the save forms close), which dropped focus to `body` where Escape no longer closed the modal; each such handler calls `keepFocusInPanel()`, and an effect after every render moves focus to the save form's input, else the badge (`tabIndex: -1`), else the first control — only once the used control is gone and only when focus is on `body`. The move waits a 0 ms timer (this legacy root renders each `setState` of a promise callback on its own, so an in-between view is not the last one) and keeps the flag while a save request runs (`savingRef`): Firefox drops focus from the Save button when it is disabled, the timer then lands on the name field, and the field goes when the form closes (2 of 5 Firefox runs ended on `body`, #303 review). The `firefox-focus` Playwright project runs the `@firefox`-tagged tests of `tests/e2e/paragraph-style-selection-scope.spec.js`. **Update Style in selection scope** re-applies the updated style to the selection (`applyTo: 'selection'`, `savedFromSelection`): the QFT wrote the change onto the styled span as its own declaration, which beats the class, so without the re-apply a later change to the style (another use, the admin Edit form) never reached that text. Core clears the declaration through the normal strip (asking only for a mixed selection) and returns early when the selection already carries the style with nothing to strip, so a plain re-apply never splits the style's span. A selection Detach with no style span is a no-op (it fell through to a block-level detach once `detachParagraphStyleFromSelection()` reported `success: false`).

Pure logic lives in `assets/js/lib/ps-utils.js` (UMD-lite: `window.typostPSUtils` + CommonJS export) — `findFontName`, `isStyleModified`, `buildPropertiesFromState`, `buildApplyEventDetail`, `buildStylePreviewStyle`, `buildStyleCssBlock`, plus the browser's list helpers (`filterParagraphStyles`, `buildBrowserSampleText`, `groupParagraphStyles`, `paginateGroups`, `flattenGroups`, `resolveBrowserCursorIndex`, `resolveBrowserCursorKey`, `findTypeAheadMatch`) — enqueued as a dependency of `editor.js` and covered by Jest in `__tests__/` (auto-collected by core `npm test`). `editor.js` itself is an IIFE over `wp.element`/`wp.components` and cannot be required under Jest, so every decision its DOM layer makes is a helper call.

`fontStyle` is captured, diffed and normalized like any other style-owned property: `buildPropertiesFromState` stores it when set (`''` = inherit is never stored), `isStyleModified` compares it, and `normalizeApplyProperties` defaults it to `''` so applying a non-italic style resets a lingering italic. It was originally excluded on the theory that "styles cannot express italic" — that carve-out plus the missing capture/sanitize/CSS steps meant saving a style from italic text silently dropped the italic everywhere; do not reintroduce it.

Capture and diff read `state.explicitFontStyle` (falling back to `state.fontStyle` only for providers that predate the key — see `persistableFontStyle`). `state.fontStyle` is the **rendered** style and includes italic derived from semantic `<em>`/`<i>`, which must never reach a saved style: em renders italic on its own, so the style's CSS could neither reproduce it elsewhere nor reset it (em's element rule outranks inherited `font-style`), and capturing it would pin the "(modified)" badge on whenever the caret sits in emphasis — one Update Style click away from propagating phantom italic to every use of the style.

The font and weight follow the same rule (#278): capture, diff and Detach read `state.explicitFontId` / `state.explicitFontWeight` (`persistableFontId` / `persistableFontWeight`, falling back to `fontId` / `fontWeight` for providers without the keys). `state.fontId` is the **rendered** font — for text with no font of its own both core editors report the plugin font the theme gives it (`getInheritedFontId()` inline, `inheritedFontId` in the block), so the Glyphs panel browses what the author sees — and `state.fontWeight` is the rendered weight (a theme-bold heading inline via `getBlockInheritedWeight()`, `<strong>` in the QFT). Reading those made every style without a font show "(modified)" on a theme-font heading, and Detach wrote the theme's `data-font-id` + `font-family` onto the span (seen on the test site, a style with only `textCase` + `letterSpacing`). An unset explicit weight compares as 400, like a style without a weight. Found with it: inline Detach (`paragraphStyleId: 0`) takes the apply handler's reset branch, which used to skip marking the payload's weight as picked, so `resolveWeightToWrite()` wrote none and a detached span lost the style's weight; `resolveApplyWeightChoice()` (`assets/js/inline-apply-rules.js`) now counts Detach's weight like an extension's.

`findFontName` matches the **`font_id`** field, not `id`: styles store the canonical numeric font id while the localized font entries key `id` to the string kit/project slug. `getFontName` searches `fonts` + `adobeFonts` + `manualFonts` + `adoptedWpFonts` for the same reason. Both were wrong until v1.2 (matching `id` only, uploaded kits only), so every style's label read "Default" — the editor-side twin of the wrong-case admin bug noted below; do not reintroduce either.

### Style browser (toolbar button, v1.2+)

Optional direct-access button, registered on core's `typost_editor_toolbar_buttons` filter with `editors: ['qft', 'inline']` (the Typography Stylist block toolbar and, since #219, the inline editor's toolbar on core blocks — see "Styles on core blocks" below for how it scopes there) when `typost_ps_toolbar_button` is on (default on since 2.3.5, #322; setting rendered into core's Options tab via `typost_admin_options_rows`, flag exposed as `typostData.paragraphStylesOptions.toolbarButton`). Its `PSIcon` is a swash "P" on a **square 256×256 grid**, drawn as one of a set with core's swash "T" and the Glyphs Panel swash "G" so the toolbar group shares a cap height and baseline; the source lives in core at `assets/images/icons/toolbar-p.svg`. (It replaced a "Ps" ligature that needed a viewBox wider than tall to hold its cap height — that mark is gone.)

`ParagraphStylesBrowser` renders each style in a `wp.components.Modal` **in the editor's parent document** (block toolbars live outside the canvas iframe) — the `.typost-ps-{id}` rules reach it through `enqueue_block_assets`, and `--font-N` + editor `@font-face` through core's `admin_head`/editor font enqueues. Each row carries the style's real CSS class so family, weight, letter-spacing and OpenType features come from the actual style; only `font-size`/`line-height` are overridden, via `buildStylePreviewStyle`, which maps the true size into a 12–40px band so relative order still reads without a 64px style dominating the list.

**Sample text, grouping, listbox (2026-09 polish).** The aria-hidden sample in each row renders the *selected text* in the style (`buildBrowserSampleText`: whitespace collapsed, 40-char cap cut on a word boundary with one ellipsis, style name when there is no text); `openBrowser()` fills the `sampleText` prop from the launch context's `selectedText` — the block toolbar's click context carries it (`capturedSelection.text`, `''` with a caret), and the inline panel passes its host state's `selectedText` (the sliced selection, or the whole text with a caret only), read at click time before the WordPress-forced close of the host modal resets it. The meta line still shows the name, so the option's accessible name is unchanged. A "Group by" select (None / Font family / Size mode / Recently used, component state only) groups the *search-filtered* list before paging (`groupParagraphStyles` → `paginateGroups`, which counts rows across groups and drops groups left empty); each group is `<li role="group" aria-labelledby>` (a listbox may only own option and group children) holding a visible `<div>` heading (not an h-tag — the modal owns the heading) and a presentational `<ul>` of options, so NVDA names the group when arrowing into it; ungrouped renders the flat list. The list is a single-select listbox: the `<ul role="listbox" tabindex="0">` is the one Tab stop and points at the keyboard cursor through `aria-activedescendant`; rows are `<li role="option" tabindex="-1">` with `aria-selected` **only** on the applied style's row (`is-active`), while the cursor is a separate `is-cursor` class shown as the focus ring. ArrowDown/ArrowUp/Home/End move the cursor (`resolveBrowserCursorKey`), Enter/Space apply it (Space `preventDefault`ed so the modal does not scroll), Escape stays with the Modal, printable characters do first-letter type-ahead (`findTypeAheadMatch` over lowercased names, 500 ms buffer; a repeated letter cycles, a longer buffer matches a prefix). The cursor is keyed by style id (`resolveBrowserCursorIndex` falls back to the applied style, then the first row), scrolls into view (`block: 'nearest'`), and after "Show more" lands on the first newly revealed row with focus kept on the listbox. The open-focus effect (SR-6) now focuses the listbox rather than a row. Font names for grouping come from `findFontName` directly (unresolved → the "No font set" group), not `getFontName` with its "Default" placeholder. "Recently used" lists the styles this author applied last (`readRecentStyleIds` / `recordRecentStyleId` over `localStorage` key `typost_ps_recent_styles`, eight ids, most recent first, every read and write wrapped so a blocked store reads as nothing remembered) and the rest under "Other styles"; `onApply` records the pick, and with nothing remembered the mode renders the flat list.

It applies with `dispatchApply(style, 'inspector')` — **not `'qft'`**: core drops a `'qft'` apply unless the Quick Feature Toggle modal is open, whereas an `'inspector'` apply targets the selected block, which is exactly the block whose toolbar was clicked.

**Scope.** With text selected the browser adds `applyTo: 'selection'`, and core wraps just that text in a `<span class="typost-styled" data-style-id="N">` (rendered by the module's existing `.typost-styled[data-style-id]` rule — no inline style string, which is what keeps "Update Style" able to restyle every use). Block-level would restyle neighbouring words that merely carry no styling of their own. `hasSelection` comes from the toolbar context's `capturedSelection`; with a caret only, the flag is omitted and the apply stays block-level. Detach follows the same scope (a selection Detach keeps the look since #303: see the QFT panel note above). Note that `removePropertyFromSpan` in core counts `data-style-id` as a reason to keep a span alive — without that, removing any other property would unwrap the span and silently drop the style. Apply and Detach both close the browser: they are terminal actions, closing returns focus to the toolbar button, and it avoids the focus bug where detaching unmounts the very button that was clicked and drops focus to the document root.

## Styles on core blocks (#219)

A whole core Paragraph or Heading block (`CORE_STYLE_BLOCKS` in ps-utils) takes a style through its **className**, as `typost-styled typost-ps-N` — option (a) in the issue. Core serializes className into the block comment and the root element's `class`, so the block stays valid (checked with `@wordpress/block-library` 11.2: serialize → parse → valid for Paragraph and Heading, next to `is-style-outline`, a drop cap, preset and custom sizes; detach drops the attribute). The generator's existing block-level selector (`.typost-styled.typost-ps-N`×5, (0,6,0)) matches the element with no change, and so do the frontend scans (`style_refs_from_content()`, `font_ids_from_content()`, core's `typost-styled` gate) and the editor's kit loader (it reads every attribute string). Option (b), a registered block style variation per style, was rejected: a block holds one variation, so a paragraph style would have replaced the theme's "Outline".

- **Overrides:** the block's own sidebar settings are inline styles or core preset classes with `!important`, so they beat the class — acceptance criterion 6 needs no code. Core blocks keep no copy of the style's values, so there is **no "(modified)" badge and no Update Style** from a core block; Update Style elsewhere restyles them through the class.
- **ClassName helpers** (ps-utils, tested): `applyStyleToClassName` strips any `typost-styled`/`typost-ps-*` token and appends the new pair (a block carries one style; other classes keep their order), `removeStyleFromClassName` returns `undefined` when nothing is left so the attribute drops instead of saving `""`, `getCoreBlockStyleRef` reads the ref (a legacy `ps_…` ref included — `findStyleByRef` matches `legacyId`). A hyphenated class such as `typost-ps-5-custom` reads as a (legacy) ref, as in the PHP scan.
- **Where it applies from:** `editor.js` adds a "Paragraph Style" `InspectorControls` panel to a selected core Paragraph/Heading through the `editor.BlockEdit` filter (always on — the toolbar button is opt-in): badge (style name, or "Missing style" for a deleted one, so Detach can clean it up), "Browse styles…" (opens the browser with `editorSource: 'core-block'` and the block's text as the sample), Detach (focus moves to Browse, because Detach unmounts itself). The panel's `initialOpen` is frozen on mount (`initialOpenRef`): core `PanelBody` reads `initialOpen` on every render until the author toggles it, so a live `!!ref` closed the panel on Detach, unmounted Browse right after it took focus, and dropped keyboard focus to `body` (#219 QA, both engines). The toolbar button's click context from the inline editor (`source: 'inline'`) goes through `resolveBrowserLaunch()`: a selection keeps the inline route (a `data-style-id` span, unchanged behaviour); a caret in a core Paragraph/Heading is `'core-block'`; a caret in any other block is `needsSelection` — the browser explains instead of listing, because a collapsed range would style nothing. The Typography Stylist block's toolbar keeps the `'inspector'` route.
- **Apply:** a `'core-block'` browser never dispatches `typost-apply-block-properties`; `setCoreBlockStyle()` calls `updateBlockAttributes(clientId, { className })` (one undo step) and asks `typostFontKits.ensureFontIds()` for the style's kit.
- **First Letter Hang:** core's `style.css` rule only reaches `.wp-block-typost` content, and a core-block-only page does not even load that file, so `generate_style_css()` / `buildStyleCssBlock()` append per-style core-block rules **only for a style with a hang** (a style without one adds nothing, keeping a theme's `::first-letter` margin and `p + p` indent untouched): `::first-letter` margin on the frontend; `text-indent` on `.block-editor-rich-text__editable` in the editor (the Chromium Home-key bug); `--typost-hang-on: 0` for `has-text-align-center`, `has-text-align-right:dir(ltr)` and `has-text-align-left:dir(rtl)` (current core still writes these classes through the `textAlign` support); excluded inside `.wp-block-typost`, on `.has-drop-cap`, and on a block with an inline `text-indent` (core's Text indent support, WP 7.0+: in the editor that inline value beat the hang's `text-indent` while the frontend added the `::first-letter` margin to it — 80px vs 60px, #219 QA). **Block direction in the editor:** core writes a block's own text direction as an inline `direction` declaration with no `dir` attribute, and `:dir()` follows the attribute, so on its own the guard hung an end-aligned block whose direction differs from the page and dropped the hang from a start-aligned one (measured, #219 QA). Four more rules key on `[style*="direction: rtl"]` / `[style*="direction:rtl"]` (and `ltr`), after the `:dir()` rules at equal (0,4,0) specificity, turning the hang off or back on. Saved markup carries `dir`, so on the frontend only the `:dir()` rules match. Numeric ids only (new applies never write a legacy id). Measured in Chromium: −0.5em on a left-aligned Paragraph and Heading, none for centered, end-aligned (LTR and RTL), drop-cap and Typography Stylist content. **Plain typography switch (#315):** the frontend `::first-letter` margin also multiplies by `(1 - var(--typost-plain, 0))`, so a theme's `.typost-plain` / `--typost-plain: 1` (core CLAUDE.md, HOOKS.md) turns it off; the editor `text-indent` rule keeps the plain amount (frontend-only switch). That changed the generated CSS, so `CSS_CACHE_KEY` is now `typost_paragraph_styles_css_v2` — rename it again whenever the generated text changes.
- **Not covered:** a theme or plugin that renders a core block without its className, and other core blocks (List item, Quote, Pullquote — out of scope in the issue; their inner Paragraphs are core Paragraphs and work).

## Alignment, word spacing and line breaking (#207)

Four style-only properties: no editor has a control or an attribute for them, so they are set only in the admin Edit form, render only through the style's class. Detach keeps the alignment as the block's own alignment when the block has none (see "Detach keeps the alignment" below; Justify not on core blocks) and drops `alignLast`, `wordSpacing` and `textWrap`, which no block has a setting for (documented). Keys are deliberately **not** `textAlign`, which is the Typography Stylist block's own attribute (left/center/right) and must stay an override.

- **Editors:** never in an editor state, so `isStyleModified` compares them only when the state reports the key (only the Edit form's `stateFromEditValues()` does) and `buildPropertiesForStyleSave` carries them from the base style, so Update Style and Save as New keep them. `normalizeApplyProperties` adds no defaults (nothing to reset); the keys ride in the apply payload and both hosts ignore them.
- **CSS** (`generate_style_css()` / `buildStyleCssBlock()`, shared fixture `__tests__/fixtures/alignment-css.json` read by `alignment.test.js` and `tests/Unit/ParagraphStylesAlignmentTest.php`): `word-spacing: Nem` and `text-wrap: balance|pretty` go in the main rule after the case. `text-wrap` is followed by `text-wrap-mode: inherit`: the shorthand also sets the mode to `wrap`, which broke text inside a `nowrap` context (fit lines, a theme's nowrap nav); browsers with only the single `text-wrap` property ignore the longhand (PR #329 review). The alignment goes in a **second rule** on the same selectors, each with `ALIGNMENT_GUARD` = `:not([style^="text-align:"], [style*=";text-align:"], [style*="; text-align:"], [class*="has-text-align-"], .typost-fit)` appended: only a real inline `text-align` declaration (saved `text-align:center`, editor `text-align: center`) turns it off, not `text-align-last` or a `--x-text-align` property, and a fit block (`.typost-fit`, editor and frontend) never takes it, because measurement decides line 1's hang from the block's own `textAlign` (`resolveHangTextAlign()` in the block's utils.js mirrors this for the Inspector's hang notice). The rule holds: `text-align`, `text-align-last` (justify only) and, for a centered or end-aligned style with a hang, `--typost-hang-on: 0`. The guard is what keeps a block's own alignment winning: the Typography Stylist block's inline `text-align` beats the class anyway, but core's `has-text-align-*` classes are (0,1,0), and the last line alignment and the hang switch would still apply under either override. With the guard, an overriding block gets the existing hang rules (style.css, `core_block_hang_css()`) back. A style with only an alignment writes only the guarded rule. **Fit styles write none of the four** (fit sets line widths itself; word spacing would change what it measured), and their card does not list them; the form hides the fields in fit mode, and `fitOwnValues()` (admin.js) keeps the hidden fields out of a fit save: dropped for a style with no parent, the parent's values for a style based on another, so no override is stored. Server `sanitize_properties()` holds `wordSpacing` to the form's -500…1000. PHP reads the values through `normalize_alignment()` / `normalize_align_last()` / `normalize_text_wrap()`, the twins of the ps-utils.js helpers. **Detach keeps the alignment** (PR #329 review, as Detach keeps case and size unit): the block gets the style's alignment as its own when it has none. Typography Stylist block: `styleAlignmentToTextAlign()` (block utils.js) → `textAlign`, Start/End → left/right by `isRTL()`, Justify kept (the block renders it inline), skipped for a fit block. Core blocks: `alignmentToBlockAlign()` (twin, parity test) and `buildCoreBlockAlignUpdate()`, written in the same `updateBlockAttributes()` call as the class (one undo step) to `style.typography.textAlign` when the type has the typography support (WP 7.x), else a `textAlign` attribute, else `align` only on a type without `supports.align` — the 7.1 Heading's `align` is the wide/full block alignment, and an earlier version wrote `align: 'center'` there (measured). Core has no `has-text-align-justify` rule, so Justify is not kept on core blocks. No `!important`, so a block's or span's own inline `word-spacing` beats the style, and a text-spacing tool or user style sheet that sets word spacing with `!important` overrides it (WCAG 1.4.12; a normal user-origin rule loses to any author rule in the cascade, so the old "a user style sheet still wins" wording was wrong, PR #329 review). Unknown `text-wrap` values are dropped by the browser, which keeps normal wrapping. Verified in Chromium 153 on a test page: end style turns the hang off, inline `text-align:left` and `has-text-align-left` override it and get the hang back, inline `word-spacing` wins.
- **Based On:** `alignment` + `alignLast` are a group (`BASED_ON_GROUPS`, `''` unsets it, `compact` drops the group for an unknown value, `group_signature()` = `'none'` or `value|last`); `wordSpacing` (0) and `textWrap` (`''`) are in `EMPTY_PROPERTY_VALUES`, `wordSpacing` compares as an int. Fixture cases in `based-on.json`.
- **Edit form:** "Alignment and line breaking" fieldset. The justify note (WCAG 1.4.8, suggests hyphenation, #208) and the Last line select show only for Justify (`data-show-for-align`, hidden for fit too); `updateConditionalFields()` adds the note's id to the alignment select's `aria-describedby` only while it shows, because a hidden element named there is still read.
- **Out of scope** (issue): InDesign's min/desired/max spacing and glyph scaling, align towards spine, single-word justification, `text-justify` (no Safari).

## Hyphenation (#208)

Style-only like #207: no editor control or attribute; set in the admin Edit form's "Hyphenation" fieldset, rendered only through the style's class (editor iframe and frontend alike, so the editor shows it too). `isStyleModified` compares the group only when the state reports `hyphens` (only `stateFromEditValues()` does), `buildPropertiesForStyleSave` carries it from the base style, `normalizeApplyProperties` adds no defaults.

- **Values** (`normalizeHyphens()` / `normalizeHyphenateLimit()` / `normalizeHyphenateCharacter()` / `hyphenationProperties()` in ps-utils, PHP twins `normalize_hyphens()` / `normalize_hyphenate_limit()` / `normalize_hyphenate_character()` (public) / `hyphenation_properties()`): `hyphens` is on only for the exact string `'auto'`. A limit is a number or numeric string (PHP `is_numeric()` after `trim_js_whitespace()`, because PHP 7.4 rejects trailing whitespace; JS rejects booleans and `'0x1A'`), floored, below 1 → 0 (= auto, not stored), capped at `HYPHENATE_LIMIT_MAX` 20. The character is trimmed with JavaScript's `trim()` set (the PHP twin lists the same code points, not `\s`, which differs under UCP), must be valid UTF-8, at most `HYPHENATE_CHARACTER_MAX` 4 code points, and may not contain `"` `'` `\` `<` `>` `{` `}` `;`, C0/C1 controls or U+2028/2029 — so it can never end the CSS string or the `<style>` element; anything else normalizes to `''`. The limits and the character are stored only with hyphenation on, so an off style stores nothing (the sanitizer runs `hyphenation_properties()`; `$keep_empty` keeps `hyphens: ''` for a child).
- **CSS** (`hyphenation_declarations()` / `hyphenationDeclarations()`, shared fixture `__tests__/fixtures/hyphenation-css.json` read by `hyphenation.test.js` and `tests/Unit/ParagraphStylesHyphenationTest.php`): in the main rule right after `text-wrap`, inside the #207 not-fit branch: `-webkit-hyphens: auto`, `hyphens: auto`, then `hyphenate-limit-chars: W B A` (0 → `auto`) only when a limit is set, then `-webkit-hyphenate-character: "X"` and `hyphenate-character: "X"` when a character is set. Off writes nothing (not `hyphens: manual`): the browser default already breaks at `&shy;`, and a style without the keys stays byte-identical, so `CSS_CACHE_KEY` was not renamed. **Fit styles write none** (lines are nowrap; the #235 zoom floor turns wrapping on, where hyphens would break a measured line) and the card does not list it; the form hides the fieldset in fit mode and `fitOwnValues()` keeps it out of a fit save (parent's values for a child). The declarations sit on the inline-span selector too, so a selected word or GREP match under such a style hyphenates when it reaches a line end while the words around it do not (the author asked for that style; accepted). **A fit block can still carry a hyphenating style's class** (the author set Fit in the Inspector under a non-fit style, and `save.js` keeps `styleClass`), so `style.css` sets `hyphens: manual` on `.typost-fit .typost-line` and, with `!important` because a style's span selector is (0,6,0), on the spans inside it, and `measureFitLines()` does the same on the probe and its spans; otherwise the min-content word measurement and the #235 zoom floor would break words at hyphenation points.
- **Support** (MDN browser-compat-data, from the issue): `hyphens: auto` Chrome 88 desktop / Android 55, Firefox 43, Safari 17 unprefixed (`-webkit-` since 5.1); `hyphenate-limit-chars` Chrome 109, Firefox 137, no Safari; `hyphenate-character` Chrome 106, Firefox 98, Safari 17. Hyphenation needs a known language (`<html lang>`, which themes print) and a dictionary in that browser; Chrome never hyphenates capitalized English words. Language selection is #209.
- **Based On:** one group led by `hyphens` (`BASED_ON_GROUPS`; empty value `''`; `compact` drops the group unless `hyphens` is `'auto'`; signature `'none'` or `auto|W|B|A|char` with 0 for an unset limit). So a child that sets its own hyphenation does not keep the parent's character. Fixture cases in `based-on.json`.
- **Edit form:** a "Hyphenation" fieldset (hidden in fit mode): the Hyphenate checkbox (`data-field="hyphens"`, read as `'auto'`/`''`, `undefined` when the form has no such field so the stored value is carried), and, in `data-show-for-hyphens="auto"` containers that `updateConditionalFields()` shows only while it is checked, three number fields (empty = auto, `placeholder="Auto"`) and the character text field. The checkbox's help text says it depends on the page language and the browser, that Chrome skips capitalized English words, that the hyphens are not in the text (screen readers, copy), the readability cost, and that soft hyphens work with it off; the limits' help says Safari ignores them. `readEditForm()` reads a limit with `optionalNumberOf()` (`''` when empty, so a typed 0 is an error and not Auto); `validateEditValues()` checks the limits (whole numbers 1–20) and the character only while hyphenation is on and not fit, so a stale hidden value cannot block Save.
- **Card:** "Hyphenation: On" or "On (words of 6+ letters, 2+ before the hyphen, 3+ after the hyphen, hyphen “=”)" (`hyphenation_label()`), "None" for a child's unset, chip keys = the whole group.
- **Detach:** `buildDetachBlockSettings()` reports `hyphens` (not on a fit style) and the notice calls it "hyphenation"; no block setting holds it.
- **Export:** plain values, round-trip with no transfer code (`ExportRegistryTest` sets and unsets the group; `sanitizedPropertyKeys()` also reads the `hyphens` group from `BASED_ON_GROUPS`, because the sanitizer stores it through `hyphenation_properties()`).
- **Screen readers / copy:** automatic hyphens are a rendering effect and never in the DOM text, so nothing in the plugin changes the text. No WCAG criterion covers hyphenation.
- **Out of scope** (issue): hyphenation zone, consecutive-hyphen limit, "hyphenate across column" (no browser support); setting the language (#209).

## Indents and paragraph spacing (#199)

Six style-only properties, like #207's: no editor has a control or an attribute for them, so they are set only in the admin Edit form ("Indents and spacing" fieldset) and render only through the style's class. Values are lengths with a `px` or `em` unit, normalized by `normalize_length()` / `normalizeLength()` (regex `^-?(\d+(\.\d*)?|\.\d+)(px|em)$`, case-insensitive, trimmed; capped at `LENGTH_MAX` 1000px / 50em; three decimals with normalizeHang()'s textual rounding; below 0.0005 → `''`; negative only for the first line indent). Keys: `indentStart`/`indentEnd` (labeled Left/Right indent, logical so they follow the text direction), `firstLineIndent`, `indentAfterSame`, `spaceBefore`, `spaceAfter`. `SPACING_PROPERTIES` (both languages) lists the four plain lengths; the sanitizer stores them in a loop, so `ExportRegistryTest::sanitizedPropertyKeys()` also reads that constant.

- **CSS** (`paragraph_layout_css()` / `paragraphLayoutCss()`, shared fixture `__tests__/fixtures/paragraph-layout-css.json` read by `paragraph-layout.test.js` and `tests/Unit/ParagraphStylesLayoutTest.php`; emitted after the alignment rule, before the core-block hang rules). The mapping follows the pre-implementation review on the issue (measured on WP 7.1.3 / Twenty Twenty-Five):
  - **Never on the inline-span selector.** The rules go on the plain `.typost-ps-N` (the settings card preview) and the boosted block-level selector only: inline start/end padding or margin moved a selected word, and text-indent and block margins do nothing on a span. So "no effect on a text selection" holds by construction; the form's help text says it.
  - **Indents are padding + `box-sizing: border-box`** (border-box only when the style sets an indent). Core's constrained layout gives every non-aligned child `margin-left/right: auto !important`, so a margin indent did nothing on core blocks, and padding on TT25's content-box paragraphs widened the box past the column. A hanging indent (negative first line) is `padding-inline-start: H` (or `calc(L + H)` with a left indent) plus `text-indent: -H` — not the `hanging` keyword (Chrome 146+).
  - **First Letter Hang:** where a first line indent applies, the same rule sets `--typost-hang-on: 0` (only for a style with a hang). The class rule's `text-indent` is (0,6,0)+, so it also beats the editors' hang `text-indent` rules (block editor.css `.typost-hang` (0,4,0), `core_block_hang_css()` (0,4,1)), and the frontend `::first-letter` margin is 0 — editor and frontend agree (checked in a Chromium harness).
  - **Only after the same style:** the indent and the hang switch move into a sibling rule, `:is(W, S) + S` and `:is(W, S) + .wp-block-typost > S` (W = `.wp-block-typost:has(> S)`, S = the boosted class), covering all four pairs of Typography Stylist / core blocks — the same result as core's Text indent `.wp-block-paragraph + .wp-block-paragraph` with `theme.json` `textIndent: "subsequent"`. One `:is()` lists W and S for the numeric class and the legacy class (`findParagraphStyleByClass` treats them as one style), so adjacent paragraphs with either form pair (#199 review); with no legacy id the list is just W, S. A first paragraph keeps its hang. The style does not reset `text-indent` on other paragraphs (that would beat the editor hang rule), so a theme's own paragraph indent still applies there. Ignored for a negative indent (`indent_after_same_applies()` / `indentAfterSameApplies()`). The settings card preview is one paragraph, so it shows no indent for such a style.
  - **Space before/after:** `margin-block-start/end` on S (core blocks: the class is on the block, whose own inline spacing wins). In a Typography Stylist block S is the inner visual element, so the margins also go on the wrapper `.wp-block-typost:has(> S)` and the inner element gets `margin-block-*: 0` (`.wp-block-typost > S`, (0,7,0)). The inner and wrapper margins would otherwise collapse to the larger one (the review measured 24px block margin + 40px style = 40px), and with block padding they would add. **Known limit (documented; a design change is pending):** an em value on the wrapper resolves against the wrapper's inherited font size, not the style's size on S, so the same style gives different spacing on a Typography Stylist block and on a core block; px is exact on both. The boosted rule also beats the layout's `> :first-child { margin-block-start: 0 }`, so space before applies to a first block (documented).
  - **A block's own spacing, by block type (#199 review):** on core Paragraph and Heading blocks (`useBlockProps.save()`, `supports.spacing` and `typography.textIndent` in core trunk) the block's inline margin, padding and text-indent are on the same element as the class, so they override the style. A Typography Stylist block differs. Its `style.spacing` is inline on the wrapper (`useBlockProps()` in the editor, `Typost::add_block_support_attributes()` on the frontend, see the root CLAUDE.md): the margin overrides the style's wrapper margin, and the padding adds to the indents, which are padding on S, so it does not override them.
  - **Fit to width:** indents are not written (each line fills the width; a first line indent would overflow), spacing is. The card hides the indents and `fitOwnValues()` (admin.js) keeps the hidden fields out of a fit save, as for #207; `validateEditValues()` checks only the spacing fields in fit mode, so a bad value left in a hidden indent cannot block Save or send focus to a hidden input (#199 review). **A fit block under a style that is not fit** skips the indents through `INDENT_GUARD` = `:not(.typost-fit)`, on the indent rule and the "only after the same style" rule (#199 review): text-indent inherits into each frontend `.typost-line` (`display: block; nowrap`), so a line sized to the width overflows; padding shrinks every line; and `--typost-hang-on: 0` leaves line 1 short, because measurement sized it as hung. Such a block exists when a style changes from fit to another size in the Edit form while blocks use it, or when the Inspector sets fit under a style. So the indents and the margins are separate rules, and only the margins reach a fit block.
  - A style without the keys writes byte-identical CSS, so `CSS_CACHE_KEY` was not renamed.
- **Editors:** never in an editor state, so `isStyleModified` compares them only when the state reports the key, and `buildPropertiesForStyleSave` carries the unreported ones from the base style (`copyLayoutProperties()`, the first line indent with its option) — without it an editor Update Style deleted them from every block using the style (#199 review). `normalizeApplyProperties` adds no defaults. `buildStylePreviewStyle()` resets padding, text-indent and block margins on a style browser row of a style that sets any of them.
- **Based On:** `firstLineIndent` + `indentAfterSame` are a group (`''` unsets it, `group_signature()` = `'none'` or `length|0/1`); the four plain lengths are in `EMPTY_PROPERTY_VALUES` (`''`) and compare normalized. Fixture cases in `based-on.json`.
- **Edit form:** each value is a number input (`data-field="indentStart"`, `step="any"`, `min="0"` except the first line) and a unit select (`data-field="indentStartUnit"`, em/px, its own `aria-label`); `readEditForm()` joins them (`lengthOf()`: `''` for empty or 0), `fillEditForm()` splits the stored value (`splitLength()`, em for none). `validateEditValues()` rejects a negative value other than the first line indent and a value past the caps. `LENGTH_MAX` comes from ps-utils through `getUtils()`. The fieldset's help says the values do nothing on selected text, follow the text direction, and lose to a core block's own settings; the first line field's help says a negative value hangs and that it turns the hang off.
- **Detach keeps what a block setting can hold (#346):** `buildDetachBlockSettings()` (ps-utils.js) maps a whole block's Detach to the block's own settings: space before/after → `style.spacing.margin.top/bottom`, left/right indent → `style.spacing.padding.left/right` (the text direction picks the side, because the style's indents are logical and block padding is physical), text color (#215 section). A side or color the block already sets wins. Fit blocks skip the indents, which the style never wrote on them. An em value that would resolve against another size becomes px at the size the text renders at when Detach runs (`measureBlockFontSize()`, canvas iframe first) — **only as the fallback since #363.** Each route passes `emBasis`, the size the style's em values resolved against: core blocks `coreDetachEmBasis(properties, attrs)` (`'keep'` when the style sets no size or the block has its own size, so em stays em; else `styleFontSizeCss(properties)`, the exact value `buildStyleCssBlock()` writes — the generator now calls it, held byte for byte by the shared CSS fixtures), the Typography Stylist block `buildBlockFontSizeCss()` (block utils.js, same tests as `save()`, with the size and unit the block has after Detach; `''` for inherit and fit). A plain length multiplies in its unit (rem to four decimals, px to three), an expression gives `calc(N * expr)` and sets `followsTextSize`, and the notice then says core's sidebar shows the value empty (verified on WP 7.1.3: Line indent and Padding inputs read `''` for a calc() value, which renders and serializes fine; kses keeps nested functions, `kses.php` ~L3018). Why: the editor canvas is narrower than the page, so px at the measured size was wrong for responsive sizes (#348 live QA: 1.5em → 60.3px at the editor's 40.2px; the page drew 72px at 1400px). The px fallback remains for an inherited size (the theme's, not known): a core block loses the style's size, and a Typography Stylist block's indent moves from S to the wrapper. That block's margins stay in em (`keepMarginEm`), because the style wrote them on the wrapper too, so em reads the same size before and after on every theme; a px value would be measured in the editor, whose canvas can have another size than the published page (PR review: a 48px style with `spaceBefore: 1.5em` was 24px on the wrapper and came out 72px when converted from the heading's size). `emConverted` reports only real conversions. When the block is not rendered (`measureBlockFontSize()` returns null, for example a List View selection while the canvas is virtualized), em values stay in em and the notice claims no conversion, so a core block's values then resolve against its own size. **Routes:** core blocks through `setCoreBlockStyle(id, null)`, which feeds the alignment update's `style` in first so `style.typography.textAlign` survives; the Typography Stylist block in `edit.js`'s apply handler under `styleClass === ''`. Both add to the same attribute change, so Detach stays one undo step. Saved markup needs no deprecation: these are standard block supports, and the block's reach the frontend through `Typost::add_block_support_attributes()`. Selection Detach is unchanged (a span has no block settings), and the orphan effect for a deleted style has no values to keep. **Notice:** `showDetachNotice()` (editor.js) lists what could not stay, as a dismissible `core/notices` notice with a fixed id, not in the panel, because Detach can come from the style browser, which closes. The Typography Stylist route reaches it through the `typost-paragraph-style-detached` event, since the handler has no module strings. Listed: outline, first line indent and the same-style option (only where #348 below cannot keep them), word spacing, line breaking, hyphenation (#208), last line alignment, GREP rules (`hasGrepRules`, because they are on the style record, and not on a fit block, where they never matched); a core block also lists justified alignment and the type settings it never copied (font, weight, style, size, letter spacing, line height, features, axes, hang, case). **Known limits:** a hanging indent loses its padding too (`padStart` is only the start indent now), so hanging lines move back. On a Typography Stylist block a kept own padding replaces the sum it rendered under the style (the style's indent on S plus the block's padding on the wrapper). A core block's padding is content-box where the theme has no border-box reset (the #199 review measured half the indent and a box past the column under TT25), and no attribute can change that; the Typography Stylist wrapper has `box-sizing: border-box` in `style.css` for this reason (by the CSS box model; not measured on such a theme). The side comes from `wp.i18n.isRTL()`, as for the kept alignment, so it follows the admin language, not a block's own `dir`. **Editor-only shift, not a bug:** a theme that gives `.wp-block` a side gutter in the editor (the test site: 24px) loses it when a block has its own padding, because the inline padding replaces the gutter. So a detached Typography Stylist block moves by the gutter in the editor (120 → 96 with a 72px indent) and lines up with a core block with the same padding; the published page does not move. Measured on the test site, whose theme has a reset: `private/demo/qa-detach.js`, `qa-detach-box.js`.
- **Detach keeps a first line indent in core's Text indent (#348):** `buildDetachBlockSettings()` writes a positive `firstLineIndent` to `style.typography.textIndent` (the sidebar's "Line indent") when `options.textIndent` is true, converted em → px with the same `emToPx()` as the indents (no `keepMarginEm` exception: on a Typography Stylist block the value moves from S to the wrapper). A block's own `textIndent` (any value but `undefined`/`null`/`''`, 0 included — core's `hasValue()`) wins and nothing is reported, because it already showed over the style (inline on the element for core blocks; the block's `style.css` rule below for Typography Stylist blocks). Other `style.typography` keys are kept, so the alignment update `setCoreBlockStyle()` feeds in first (`style.typography.textAlign`) survives. A negative indent is still reported (Text indent has no matching padding), as are a fit block (the style never indented it, nothing reported) and a block that cannot hold it. **Gate** `canKeepTextIndent(blockType, styleProperty, features, blockName)`, read from the editor by `readTextIndentSupport(blockName)`: (1) `supports.typography.textIndent` on the registered type — core Paragraph from WP 7.0 (`wp-includes/blocks/paragraph/block.json:61` at 7.1.3), never core Heading; (2) `wp.blocks.__EXPERIMENTAL_STYLE_PROPERTY.textIndent` exists — core's style map gained it in 7.0 together with the PHP output in `block-supports/typography.php:231` (checked: 6.9.4 `blocks.js` and `typography.php` have no `textIndent`, 7.0 and 7.1.3 have both). The Typography Stylist block declares the support on every version, so (1) alone would write a value that WP < 7.0 never renders; (3) the theme setting `typography.textIndent` is not `false` (block-level `__experimentalFeatures.blocks[name]` first, then global): `false` hides the sidebar control (`useHasTextIndentControl()` reads it) while a stored value still renders, so the author could neither see nor remove it. Not modeled: per-section settings that core's private `getBlockSettings()` resolves from parent blocks with `__experimentalSettings`, and the `blockEditor.useSetting.before` filter. **"Only after a paragraph with the same style"** (`indentAfterSame`, the user's decision on the issue's open question: match what was shown): the indent is written only when `options.followsSameStyle`, i.e. the block was indented; otherwise nothing is written and nothing reported, since nothing visible is lost. `followsSameStyle` = `blockCarriesStyle(readPreviousBlock(clientId), style)`, the mirror of the sibling rule `:is(W, S) + S` / `:is(W, S) + .wp-block-typost > S` in `paragraphLayoutCss()`: the previous block in the same parent (`getPreviousBlockClientId()`) counts when it is a `typost/block` whose `styleClass` is the style (fit included — W has no fit guard; its visual copy always carries `typost-styled`), or any other block whose `className` tokens hold `typost-styled` and `typost-ps-{id|legacyId}`. The editor's block order stands for the published page; a block that renders nothing between the two (a hidden or empty dynamic block) would make the frontend differ, which is not handled. Side effect, inherent to Detach: a following same-style paragraph loses its indent, because its predecessor no longer carries the style (documented in DOCUMENTATION.md). **Routes:** both pass `textIndent` and `followsSameStyle` (`editor.js` `setCoreBlockStyle()`, `edit.js` apply handler with `readTextIndentSupport('typost/block')`); a source scan in `detach-block-settings.test.js` holds both calls. The values still go out in the same single `updateBlockAttributes()` / `setAttributes()` call, so Detach stays one undo step. No deprecation: `style` is a block support attribute both blocks already had. The Typography Stylist block's side (block.json support, CSS, hang, fit) is in the root CLAUDE.md, "Line indent on the block (#348)". Verified with a standalone harness that runs core's real `wp_apply_typography_support()` + `WP_Block_Supports::apply_block_supports()` + style engine against the block's block.json: 7.0 and 7.1.3 return `text-indent:24px;`, 6.9.4 returns nothing and no error.
- **Export:** plain values, so they round-trip with no transfer code (`ExportRegistryTest` sets and unsets all six).
## Text color and outline (#215)

Style-only like #207: no editor control or attribute, set in the admin Edit form's "Color and outline" fieldset, rendered only through the style's class. `isStyleModified` compares them only when the state reports the keys (only `stateFromEditValues()` does), `buildPropertiesForStyleSave` carries them from the base style (Update Style / Save as New keep them), `normalizeApplyProperties` adds no defaults. **Detach (#346)** keeps the text color in the block's own setting: a palette color as the `textColor` attribute with the slug the palette has (a style stores it kebab-cased, so `accent-1` finds `accent1`), the saved `|#hex` in `style.color.text` when the palette no longer has that color, a custom color in `style.color.text`. `readEditorPalette()` merges every origin from `__experimentalFeatures.color.palette`, because core sets `settings.colors` to only one (`custom ?? theme ?? default`), and skips the default origin under `defaultPalette: false`, when core prints no CSS for it. A color that is fully transparent, in whatever form, is never kept, because the outline that shows the text has no block setting and the text would vanish; it and the outline are named in the notice. **Reaching the text:** a kept color is on the wrapper, and with no style class `block_color_selector()` no longer applies, so a theme's `h2 { color }` would beat the inherited value on the element. `style.css` has `.wp-block-typost.has-text-color > :is(.typost-styled, .typost-block-content) { color: inherit; }` at (0,3,0), which needs `has-text-color`, so a style's color still wins on a block with no color of its own. It also serves any Typography Stylist heading with its own Text color and no style. See "Detach keeps what a block setting can hold" above.

- **Color values** (`normalize_color()` / `normalizeColor()`, twins; `normalize_hex_color()` / `normalizeHexColor()`): a custom color is `#rrggbb` or `#rrggbbaa` (lowercase, `#rgb`/`#rgba` expanded; the alpha channel is the "tint" of the issue). A palette color is core's own reference `var:preset|color|{slug}` (as theme.json writes it) plus, when the palette color was hex at save time, `|#hex`: the CSS fallback. `PALETTE_COLOR_PATTERN` in both languages. The slug is stored **kebab-cased** (the variable's name segment: `get_color_palette()` runs `_wp_to_kebab_case()`, so `accent1` → `accent-1`), so neither generator needs a kebab twin. `transparent` only for `textColor`. Anything else (keywords, `var()`, `url()`) normalizes to `''` and is dropped by the sanitizer.
- **CSS** (`generate_style_css()` / `buildStyleCssBlock()`, shared fixture `__tests__/fixtures/text-color-css.json`, read by `text-color.test.js` and `tests/Unit/ParagraphStylesTextColorTest.php`, generated from the JS twin and checked byte for byte by the PHP test): in the main rule after the #207 declarations (also for fit styles), `color: …`, then `-webkit-text-stroke-width: calc(Npx * (1 - var(--typost-plain-outline, 0)))`, `-webkit-text-stroke-color: …` (only when set; otherwise the stroke is `currentColor`) and `paint-order: stroke fill` for `'behind'` (`stroke_declarations()` / `strokeDeclarations()`). **Position default (2.4.0):** the Edit form opens on "Behind the fill" for a style whose resolved outline width normalizes to 0 (`fillEditForm()`), so a new outline saves `'behind'` unless the author picks On top; a style with an outline, own or inherited, keeps its saved position (`''` = On top). Only the form changed: the stored default is still On top (`''`, no key), `strokeProperties()` / `sanitize_properties()` keep the position only with a width, so the default alone writes nothing, and the editors' Save as New / Update Style carry the position from the style or state as before. Why: on top of the fill, a variable font's overlapping contours show as lines inside the letters; behind the fill hides them, except with a transparent fill (the help text says so). A palette color is `var(--wp--preset--color--{slug}[, #fallback])` (`color_css_value()` / `colorCssValue()`), so a palette change restyles every style using it with no save, and a theme that removes the color still shows the saved one. A transparent fill is written **only** with an outline that shows (`has_outline_partner()` / `hasOutlinePartner()`, also the Edit form's check: a normalized width above 0 and a color of its own that is not `#rrggbb00`; `text_color_css_value()` / `textColorCssValue()`): without one the stroke would be `currentColor` = transparent, or the color itself would draw nothing, and the text would vanish. For the same reason a palette outline on a transparent fill with no fallback (a palette color that is not hex, an import `{slug}`) or a zero-alpha one writes `var(--wp--preset--color--{slug}, CanvasText)` (`stroke_color_css_value()` / `strokeColorCssValue()`): a missing variable is invalid at computed time and the stroke falls back to `currentColor`. On filled text that fallback is the fill, so nothing is added. **Plain typography switch (#315):** `.typost-plain` (`assets/css/frontend.css`) sets `--typost-plain-outline: 1` (outline width 0) and `--typost-plain-fill: currentColor`; the transparent fill is written `color: var(--typost-plain-fill, transparent)`, and `currentColor` on `color` computes as `inherit` (CSS Color 4; measured in Chromium 156, Firefox 157 and WebKit 27.2: the parent's color). A style's other colors stay. The width deliberately does not read `--typost-plain`: HOOKS.md documents a theme setting that property alone (hangs only), and that would leave outline-only text with width 0 and a transparent fill, so no text at all. `.editor-styles-wrapper, .block-editor-block-list__block` reset all three in the same file (`--typost-plain-fill: initial`, so the `var()` fallback applies), because the editor uses the same rule and a page can mount the editor on the frontend. There is no unprefixed `text-stroke`; `-webkit-text-stroke` works in Chrome, Firefox 49+, Safari 3+; `paint-order` on HTML text from Chrome 123, Firefox 60, Safari 11 (older browsers draw the stroke on top). No forced-colors rule: in forced colors the browser forces `color` and the stroke color to the system text color (the issue measured Chromium 145 and Firefox 146: outline-only text renders solid and readable). Existing styles' CSS is byte-identical (no `CSS_CACHE_KEY` rename: the #315 rename was needed because stored styles with a hang changed their text, while no released style has these keys, and the first save of one deletes the transient).
- **Block override** (acceptance criterion): the Typography Stylist block's `color.text` support puts `has-text-color` (+ a preset class or an inline color) on the `.wp-block-typost` wrapper, while the style class sits on the visual element inside it, where a class color beats the inherited one. A style with a text color adds `.wp-block-typost.has-text-color > .typost-styled.typost-ps-N×5 { color: inherit; }` (`block_color_selector()` / `blockColorSelector()`, (0,8,0) vs the style's (0,6,0); legacy ids too), after the alignment rule and before the core-block hang rules. Same structure in the editor (`useBlockProps` wrapper, RichText as a direct child). A data-style-id span inside such a block keeps the style's color (only the direct child matches). Core Paragraph/Heading need nothing: their own color is an inline style or a preset class with `!important` on the element itself. On the frontend `has-text-color` comes from `Typost::add_block_support_attributes()` at render time (see the root CLAUDE.md), not from saved markup.
- **Based On:** `textColor` inherits on its own (`EMPTY_PROPERTY_VALUES` `''`, compared normalized); the outline is a group led by `textStrokeWidth` (`BASED_ON_GROUPS`; empty value `0` via `group_empty_value()` / `groupEmptyValue()`, which `compute_overrides()` / `computeStyleOverrides()` now use instead of the inline `'fontSize' ? 'inherit' : ''`; `compact` drops the group for width ≤ 0; signature `width|color|position`). Palette colors compare by slug only (`comparable_color()` / `comparableColor()`, also in `isStyleModified`): the fallback records the palette at save time and the Edit form rebuilds it, so after a theme change a child's unchanged color must not read as an override. `sanitize_properties($raw, $keep_empty)` keeps `textColor: ''` and `textStrokeWidth: 0` only for a child. Fixture cases in `based-on.json`.
- **Palette** (`get_color_palette()`, memoized per request in `self::$color_palette`): `wp_get_global_settings(['color','palette'])` by origin — theme, then custom (Global Styles), then default unless `color.defaultPalette` is false; `get_theme_support('editor-color-palette')` without global settings (WP 5.8). A slug in two origins is listed once with the value that wins in core's CSS (custom > theme > default). Colors must match a plain-CSS allow-list (`safe_css_color()`: `[#a-zA-Z0-9(),.%\s/+-]`, ≤ 200 chars), because they are printed in the admin surface CSS. `get_theme_colors()` reads `wp_get_global_styles(['color'])` background/text and resolves `var:preset|color|x` / `var(--wp--preset--color--x)` through the palette. **Tests:** Brain Monkey keeps a mocked function defined for the rest of the run, so tests seed the memo through reflection (`ExportTestCase::setPalette()`, the TextColor test's `resetPalette()`) and leave it `array()`, never `null`, so later tests do not call the WordPress function.
- **Edit form:** "Color and outline" fieldset. The color selects (`data-field="textColor"` / `"textStrokeColor"`) list Default / the palette in optgroups (`preset:{slug}` values, label "Name (value)", rendered by `admin-tab.php` from `get_color_palette()`) / Custom / Transparent (text only); a custom hex field (`textColorCustom` / `textStrokeColorCustom`, shown only for Custom, `data-show-for-color`) with a native `<input type="color" data-color-picker-for>` that has no alpha, so `applyColorPicker()` keeps the field's alpha digits. `fillColorField()` keeps the stored value on the select (`data-stored`) and adds a missing slug as "slug (not in the theme palette)", so an untouched form saves it with its own fallback; `readColorField()` rebuilds a palette pick with the palette's **current** color as the fallback (`buildPaletteColor()`), so a baseline read right after filling compares equal and a rename sends no properties. A form without the fields reports `undefined`, so the stored values are carried. `validateEditValues()`: a custom field that is not hex, a width outside 0–20, transparent text without an outline that shows (`hasOutlinePartner()`, the generators' rule on the normalized values). Swatches (`data-swatch-for`, decorative, `aria-hidden`) and the contrast notice update on `change`/`input` of the color, width, size and weight fields (`updateColorFields()`, also called from `updateConditionalFields()`).
- **Contrast (WCAG 1.4.3):** pure helpers in ps-utils — `parseCssColor()` (hex, `rgb()/rgba()`, `transparent`; anything else, e.g. `oklch()`, is not checked), `contrastRatio()` (alpha composited over the background, so a tint is checked as shown), `isLargeText()` (24px, or 18.66px and bold; responsive/fit by `fontSizeMin`; no size = not large), `findContrastProblem(props, {palette, background, text})`. Pairs: fill vs background; outline-only → outline vs background (Understanding 1.4.3: a narrow border counts as the letter); fill + outline → flagged only when the fill passes against neither the background (thin outline) nor the outline (wide halo acts as background), since the check cannot know the rendered stroke-to-glyph ratio. A fill that passes with an outline on top at least `OUTLINE_COVERS_LETTER_RATIO` (0.1) of the font size (the smallest size of a fluid style; no size counts as 16px) also checks the outline against the background, pair `'outline-covers'`: a centered stroke as wide as a stem (about 0.1em in text weights) covers the stem. No fill color = the theme's text color; no outline color = the fill. The background is the theme's (`typostPSAdmin.themeColors`), white when unknown; the ratio is floored to two decimals. The notice (`.typost-ps-edit-contrast`, `role="status"`, empty while passing) joins both color selects' `aria-describedby` only while it has text. Core's `ContrastChecker` (`@wordpress/block-editor`, suggested in the issue) was not used: the admin form is jQuery with no React or block-editor packages.
- **Card and preview:** `render_card_details()` rows "Color:" (`color_label()`: palette name, "slug (not in the theme palette)", the hex, or "Transparent (outline only)") and "Outline:" ("2px, Accent, behind the fill"; "text color" when no own color), with the source chips and "None" for unsets. The preview surface (#217's open question) is `admin_preview_surface_css()` on its **own** handle `typost-paragraph-styles-admin-surface`, because `replaceStyleCss()` replaces the main handle's inline CSS after every save: the palette's `--wp--preset--color--*` variables on `.typost-ps-preview` (a settings page does not print them), the theme background on the sample, and the theme text color at `:where()` (0,0,0) so a style's own color always wins. The two colors are written only as a pair (a theme with one of them could otherwise make the sample unreadable). The style browser's sample gets the same surface through `buildStyleSampleSurface()` (inline, `typostData.paragraphStylesOptions.themeColors`), only for a style with a color or an outline; the theme text color there only when the class writes no color, as an inline color would beat the class. Its default color moved to `:where(.typost-ps-browser-sample)`: at (0,1,0) the rule came after the style's plain `.typost-ps-N` and hid every text color and transparent fill until a mid-session save re-appended the style CSS. A theme with neither color (a classic theme) gets no surface, so a white style's sample can be invisible in the browser; the row's name stays readable.
- **Export/import** (`Typost_PS_Transfer`, the follow-up comment on the issue): export writes a palette color as `{slug, value}` (`export_colors()`: the palette's current color when hex, else the stored fallback; `{slug}` alone when neither), custom colors as they are. Import maps them before sanitizing (`map_colors()`): a slug this site's palette has keeps the reference with this site's color as the fallback (the file's when this site's is not hex), and `palette_warnings()` says when its color differs from the file; a slug it lacks is a row in the preview's `colorRows` (core's generic row form, rendered by `admin-export.js` under the styles table with `colorHeading`) with `slug` (default: keep the reference, the file's color as fallback) or `value` (store the file's color as a custom color), sent as `color:{slug}` keys in the section's choices (a colon never appears in a file key); a slug with no color in the file is a warning only. Invalid file colors are dropped by the sanitizer.
- **Forced colors:** a style with a transparent fill also writes `@media (forced-colors: active)` with `color` and `-webkit-text-stroke-color` set to `CanvasText`. Without it Firefox keeps the transparent fill, the stroke follows it, and the text vanishes (pixels measured with Playwright emulation, literal and `var()` forms alike; Chromium paints solid text either way, and the note in #215 that Firefox painted it was not what this measured).
- **Not done:** an editor-side contrast warning (the editors have no color control, and the canvas background is per block/template); gradient text and InDesign tint/overprint (out of scope in the issue). Real Windows High Contrast was not tested here (no Windows); the issue's emulated forced-colors measurements are what the docs rely on.

### Edit form (#221)

Edit opens a form with every stored property except `fontSizeUnit` (the #207 alignment settings are only set here). One `<template id="typost-ps-edit-form-template">` in the tab holds the form (one copy of the 51 feature checkboxes, not one per card); `admin.js` clones it into the card's empty `.typost-ps-edit-form`, appends `-{id}` to every id and to `for`/`aria-describedby`/`aria-labelledby` (`suffixIds()`), and fills it from the style as stored now. **Edit fetches it first** (`GET …/admin-card`, which also refreshes the card's details, preview and CSS): the form sends every property, so filling from `typostPSAdmin.styles` — the page-load copy — put back the old values of an Update Style made in the editor while the tab was open (PR #292 review, reproduced: a font changed elsewhere reverted on the next form save). If that request fails the form opens from the page copy. `openEditForm()` calls `stop(true, true)` on the container first: the close animation's callback empties it, so Escape then Enter within 200 ms used to empty the new form and leave the card with no Edit button. Add a field to the template with a `data-field` name, to `fillEditForm()` / `readEditForm()` / `stateFromEditValues()`, and to `FORM_FIELDS` in `tests/Unit/ParagraphStylesAdminEditFormTest.php` (the Jest fixture in `admin-edit-form.test.js` mirrors the template).

- **Payload = Update Style's.** The form values become an editor state (`explicitFontId`/`explicitFontWeight`/`explicitFontStyle`, `fontSize` as `'inherit'`/a px string/`'responsive'`/`'fit'`, and `initialHang` + `textCase` always reported, so the form's 0 / Default wins), and `buildPropertiesForStyleSave(state, style.properties, true, typostPSAdmin.newFontSizeUnit)` builds the properties — so the unit rule is the editor's: a style with a size keeps its unit (px for a pre-#233 style), a size added to a sizeless style takes the new-content unit (#248).
- **Untouched values survive.** PATCH replaces `properties` wholesale, so the form always sends the full set — and sends **no** `properties` when the set equals what the untouched form builds (the baseline read right after filling), so a rename never rewrites properties the form cannot represent. Values the lists lack are added as options when filling: a deleted font (labeled from the card's `data-font-label`, i.e. `font_display_name()`), an off-list weight such as 350, and stored features the core list does not offer (an extension's, in `[data-extra-features]`, checked). Features keep their stored order (it is the CSS order); new picks follow. A fixed rem size keeps decimals (`step="any"`); a fixed **px** size is stored whole (`fixedSizeFor()`, `step="1"`), because both generators write px with `intval()`/`phpInt()` — a stored 24.5 showed "24.5px" on the card and rendered 24px. Floor, not round, so a stored decimal keeps its rendered size when another value is saved. The unit comes from `resolveEditFontSizeUnit()`, the same rule `buildPropertiesForStyleSave()` applies. The trio and `fitMaxSize` are integers like the sanitizer's `absint()`.
- **Validation** (`validateEditValues(values, { baseline, unit })`): a name, a fixed size above 0 (above 0 once made whole, for px), all three sizes for responsive/fit (the trio is only checked for those modes, like the sanitizer drops it for others), and axis settings that match the generators' `"tag" number` regex — an invalid pair was silently dropped from the CSS. The axis check runs only when the field differs from the baseline: the editor can store values the regex rejects (single quotes, exponents), and those blocked even a rename.
- **After a save** `GET /typost/v1/paragraph-styles/{id}/admin-card` (`edit_posts`, requested with `_locale=user` through `withUserLocale()` and `dataType: 'json'` so the labels come back in the admin's language, not the site's — `determine_locale()` reads `_locale=user` only on a JSON request, so until #296 the parameter alone did nothing) returns the stored `style`, the card's `details` and `preview` HTML from the same PHP renderers as the page, plus `css` = `get_all_css()` (regenerated, `save_styles()` deleted the transient). `replaceStyleCss()` **replaces** the text of `<style id="typost-paragraph-styles-admin-inline-css">` (appending a rule would keep a property the save removed), `replaceCardParts()` swaps details + preview, and `window.typostAdminFonts.scan(card)` loads an Adobe kit for a new font. If the card request fails after a successful PATCH, the page reloads rather than show a stale card. A rename alone skips the card request.
- **Frontend and caches:** nothing new — `save_styles()` already drops the CSS transient and core's per-post font detection cache, and the frontend generates the per-page style CSS on each request. Open editor sessions pick the change up on their next load (out of scope in the issue).
- **Focus and errors:** Edit focuses the name; Save, Cancel and Escape return focus to the card's Edit button. An error goes to the form's `role="alert"` box (`showFormError()`): a field error also sets `aria-invalid` on the field, adds the box id to its `aria-describedby` (after any help text) and focuses it; a server error with no field (404, 429, network) focuses Save — only a 400 (a name empty after sanitizing) goes to the name. `clearFormError()` removes the marks on the next submit. Enter in any field saves (the form's submit).

### Style preview (issues #220, #226)

Each card always shows a `<div class="typost-ps-preview">` holding a `<p class="typost-ps-preview-sample typost-ps-{id}" data-typost-font-id="N">`. #220 hid it behind a Preview disclosure button to save font downloads; #226 removed the button (Matt wanted previews on by default) once core's settings-page font loader made that cheap. Design constraints, several of them chosen so the #217 InDesign-controls work gets its preview for free:

- **Renders through the style's real class, never a per-property mapping.** `enqueue_admin_assets()` adds `get_all_css()` (the cached transient — same generator as the frontend and editor, so nothing new to keep byte-identical) to the `typost-paragraph-styles-admin` handle, so the plain `.typost-ps-{id}` (0,1,0) selector styles the sample. Any property a future issue adds to `generate_style_css()` shows in the preview without touching preview code. `typost_admin_assets` fires once per page load since #226 (core hooks `admin_enqueue_scripts`; before, it fired from both `admin_print_styles-{hook}` and `admin_print_scripts-{hook}` and every localized object printed twice). The `$admin_style_css_added` flag is only a precaution.
- **Defaults must never outrank the style.** Preview defaults (20px / 1.4) sit on the `.typost-ps-preview` container (inherited) or in `:where(.typost-ps-preview) p` (0,0,1 — beats the admin's bare `p { font-size: 13px; margin: 1em 0 }` by source order, loses to the style class). A (0,1,1)+ rule on the sample would silently beat #199's spacing or #207's alignment.
- **Page speed.** Kit and adopted fonts are declared by core's `@font-face` rules and download only while the tab is open (inactive tabs are `display: none`). Adobe Fonts kits are not on the settings page up front: the sample's `data-typost-font-id` (the *resolved* font — the end of the replacement chain) tells core's `window.typostAdminFonts` loader to add the kit stylesheet when the sample scrolls into view. Verified on a test site: opening the tab loaded the one kit on screen; the Caslon sample 1,100px below the fold loaded its kit (and only its 400-normal face) when scrolled to.
- **Fixed, server-rendered sample text** (translatable; carries fi/ffl/ffi/Th/st, a fraction and figures so features show). Server rendering is deliberate: the #195/#196 render-time rule engine can style the sample exactly as it styles content, which a client-typed sample could not without a REST round-trip. The sample's multi-line paragraph shape is what lets indents, justification, hyphenation and drop caps show. `lang` is the admin locale only when the string is actually translated (else `en`), because `hyphens: auto` follows `lang`.
- **Font label** comes from `Typost_Paragraph_Styles::resolve_font_label()` (pure, PHPUnit-tested): `found`, `replaced` (follows the `typost_font_replacements` chain with a cycle guard — the card names the font the style actually renders in, since `--font-{deleted}` aliases the replacement), `missing` (no mapping: the variable is undefined, `font-family` falls back to the inherited admin font, and the card says so instead of naming a font that no longer exists), or `default`. Mappings come from `$instance->font_sources()->get_font_replacements()`.
- **Manual font definitions** are loaded by the theme on the site, and nothing loads them on the settings page, so their preview carries a note that it can show a fallback font.
- Open questions deferred to #217: styles with text color (#215) or shading (#198) need a neutral or theme-colored preview surface. #215 gave the sample the theme's background and text color (see "Text color and outline (#215)"). #200 Based On merges parent properties into the child's rule, so the preview still needs only the style's own class.

## Based On (#200)

A style can inherit from another: `basedOn` on the record, sparse `properties` = what the style sets itself (no migration — a style without `basedOn` is exactly what it was). Resolution happens **when CSS is generated, never in markup**: content carries only the child's `typost-ps-N`, and `generate_style_css()` / `buildStyleCssBlock()` emit one self-contained rule from the resolved properties, so Update Style on a parent restyles every child on the next load with no content change, and the frontend prints only the child's rule.

- **Resolution** — `resolve_properties($style, $styles)` (PHP, static) / `resolveStyleProperties(style, styles)` (ps-utils): no `basedOn` → stored `properties` untouched (byte-identical CSS for every older style); otherwise walk up at most `MAX_BASED_ON_LEVELS` (10, the style included), stopping at a missing parent or a style already seen, merge root → leaf with `merge_properties()` / `mergeStyleProperties()`, then `compact_properties()` / `compactStyleProperties()`. **Groups** (`BASED_ON_GROUPS`): `fontSize` (+ unit, trio, fit cap) and `textCase` (+ `fakeSmallCaps`) inherit as a whole — a child with its own fixed size must not keep the parent's trio, a child's Small Caps must not inherit "no fake small caps"; group keys without the lead key are ignored. Every other key inherits on its own.
- **Unsetting an inherited value**: a child stores the key's empty value (`fontId: 0`, `fontWeight: ''`, `fontStyle: ''`, `features: []`, `letterSpacing: 0`, `lineHeight: 0`, `fontVariationSettings: ''`, `initialHang: 0`, `fontSize: 'inherit'`, `textCase: ''`, and since #207/#199/#208 `alignment: ''`, `wordSpacing: 0`, `textWrap: ''`, `hyphens: ''`, `firstLineIndent: ''` and `''` for `indentStart`/`indentEnd`/`spaceBefore`/`spaceAfter` — `EMPTY_PROPERTY_VALUES` in ps-utils). It wins the merge and `compact` then drops it, so resolved properties look like any style that sets nothing there (and the generators already skip empties). `sanitize_properties($raw, $keep_empty)` keeps the four empties it would otherwise drop (`fontStyle`, `textCase`, `fontVariationSettings`, `initialHang`) only for a style with a parent, so the "never stored as 0/''" rules above still hold for standalone styles. This is how "Body – First" removes Body's hang and #199's first line indent.
- **Open question in the issue, decided: an override equal to the parent becomes inherited.** The editors save their whole state, not per-property "set" flags, so "stay an override" would have turned every captured value into an override on the first Update Style and cut the child off from its parent. Update Style uses `buildStyleUpdateProperties(state, style, styles, unit)`: `buildPropertiesForStyleSave()` over the resolved properties, then `computeStyleOverrides(full, parentResolved)` keeps only what differs (groups compared whole via `groupSignature()`, values via `propertyValuesEqual()` — features in any order, line height within 0.0005, absent = empty, unset weight ≠ `'400'` because it renders differently) and stores an empty value for what the parent sets and the look does not. Save as New still makes a standalone style with the full look.
- **Client shape — every reader gets resolved properties for free.** `add_editor_data()`, REST GET, and the POST/PATCH responses go through `prepare_style_for_client()`: a child's `properties` is **resolved** and `ownProperties` holds what it stores; a standalone style is returned unchanged. So the apply payload, `isStyleModified` (the badge compares against parent + overrides), the block re-sync on `typost-paragraph-styles-updated`, `resolveDetachFontSizeUnit`, the inline weight helpers and the editor font kits needed no change. After every editor save `editor.js` runs `resolveStyleList()` (idempotent; reads `ownProperties` when present) over its list before writing `typostData.paragraphStyles`, so a parent's Update Style re-resolves its children in-session. **A write sends own properties** (`properties` in POST/PATCH = overrides), never the resolved ones — but the server no longer relies on it (PR #293 review): every child write runs `drop_inherited_properties()` against the parent, so a client that PATCHes back GET's resolved `properties` keeps inherited values inherited (it loses only explicit unsets, which resolved properties cannot carry).
- **PHP readers**: `generate_style_css($style, $styles = null)` (callers with the list pass it, to avoid re-reading per style), `font_ids_from_content()` and `font_ids_from_forced_styles()` via `resolved_font_id()` — a font a child inherits loads on the frontend. The admin card resolves too.
- **REST**: POST and PATCH accept `basedOn`, read by `parse_based_on()`: an int ≥ 0 or a string of digits, `''`/null = none (PATCH tests the key with `has_param()`, so a JSON `null` removes the parent and only an absent key leaves it — a `get_param()` null check made `null` a no-op, review of #293); anything else (negative, fraction, word, boolean, array) is a 400 with `field: 'basedOn'` — it used to go through `absint()`, so `-3` linked style 3 and `'abc'` silently removed the parent (PR #293 review). Then `based_on_error()`: exists, not the style itself or a descendant (`descendant_ids()`), and the resulting chain (levels above + 1 + the style's own subtree height) ≤ 10 → else 400, nothing saved. POST stores `properties` minus values equal to the parent's resolved ones. PATCH `properties` are the style's own **relative to its current parent** (sanitized, empties kept when it has one); without a Based On change they are stored minus values equal to the parent's — "Reset to Base" is `{properties: {}}`. A Based On change, **with or without `properties`**, then goes through `rebase_properties()` (one rule for both saves; the review found the form's save with edits kept the whole look while a parent-only save let unset keys inherit — QA: an upright style turned italic only when nothing else changed): to none → the resolved values become the style's own (`compact`), so it looks the same; a **first parent** (none before, or the old parent is gone) → `compute_overrides(look, parent)` (PHP twin of `computeStyleOverrides()`, held to the fixture's `overrides` cases; `EMPTY_PROPERTY_VALUES` now exists in both languages), so the style keeps its look and None afterwards gives it back exactly; **parent → another parent** → `drop_inherited_properties()` keeps the style's own overrides minus values equal to the new parent's, and everything it does not set inherits from the new parent (decided 2026-10-20). DELETE copies each direct child's resolved values into it and removes its link (grandchildren keep theirs: their parent looks the same), returning `detached` ids.
- **Admin (on the #221 edit form)**: `typostPSAdmin.styles` is the client shape, so the form fills with a child's resolved values and the card details resolve too (`render_admin_card_parts($style, $styles, $context)`, shared by the tab and the admin-card route; `data-font-label` names the resolved font). The template has a `data-field="basedOn"` select that `fillEditForm(form, style, fontLabel, unit, styles)` fills with None + every style except the style and its descendants (`getStyleDescendantIds()` in ps-utils, twin of `descendant_ids()`), a missing parent added as "A deleted style". `buildEditPayload(values, baseline, style, newUnit, styles)`: `basedOn` only when the select changed; properties only when the whole look differs from the untouched form's (compared before overrides), then `computeStyleOverrides(look, resolvedCurrentParent)` when the style has a parent now, the whole look when it has none — relative to the **current** parent even when the select changed, because the server applies the Based On change itself. A Based On change alone sends just `basedOn`. A rejected Based On is a 400 with `field: 'basedOn'`, so the form marks the select, not the name. "Reset to Base" is a form button (`.typost-ps-reset-base-btn`), PATCH `{properties: {}}`; `updateResetToBase(form, style)` shows it only when the style has a saved parent, `ownProperties`, and the select still names that parent — it runs on fill and on every change of the select (it used to stay visible after choosing None, and a click then kept the old parent and dropped the None choice). The reset saves no overrides and closes the form, so its confirm asks a longer question when `hasUnsavedEditChanges()` finds a change (#300): `buildEditPayload()` against the form's `data('baseline')` gives `properties` or `basedOn`, or the typed name differs. A change typed and then undone builds the same properties, so it counts as none. Cancel leaves the form open with its changes. `render_card_details()` splits the Font row's chip (family / weight) when only one of `fontId`/`fontWeight` is own. `render_card_details($props, $font, $inheritance)` adds "Based on: X", an Inherited/Override chip per row (`typost-ps-detail-source`, each row lists the keys it shows) and "None" for an empty override. `GET {id}/admin-card` also returns `related` (details + preview of every descendant) and `styles` (all, client shape); `admin.js`'s `applyCardResponse(styleId, card)` (used on Edit and after every save) swaps those cards (`replaceRelatedCards()`), replaces its style list, and requests the card after a rename too when the style has descendants (their details name it). A delete that detached children refreshes each child's card.
- **Parity**: `paragraph-styles/__tests__/fixtures/based-on.json` (resolution, compare, child CSS, overrides) is read by `based-on.test.js` and `tests/Unit/ParagraphStylesBasedOnTest.php`.
- **Not done / limits**: Based On is set only on the settings tab (the editor panel has no select; Save as New does not link to the active style). Nested/GREP rules (#195/#196) do not inherit (out of scope); GREP rules live on the style record, not in `properties`, so resolution never sees them. A child cannot unset a property that has no empty value of its own beyond the list above — every current property has one; new properties need an entry (see the checklist).

## GREP styles (#196, v2.4.0+)

A style can carry an ordered list of rules on its **record** (`grepRules`, beside `basedOn`; not in `properties`, so the editors' Update Style — which PATCHes `properties` only — never touches them, and no property plumbing changed): `{pattern: 'acronyms'|'fractions'|'ordinals'|'numbers'|'ampersand'|'custom', regex (custom only), styleId}`. Text in a block with the style that matches a rule's pattern renders in the rule's style. No editor preview yet (see "Not done").

- **Engine** — `includes/class-typost-ps-text-ranges.php` (`Typost_PS_Text_Ranges`), shared with the nested styles of #195: walks the rendered block with `WP_HTML_Processor::next_token()`; an opening tag the root callback accepts starts a root; each `#text` token's `get_modifiable_text()` (decoded) is appended to the root's plain text with its byte range; `<br>` adds `\n`, skipped elements (`SKIP_ELEMENTS`: code/kbd/samp/pre, raw text elements, SVG/MathML, form controls) and other void elements add U+FFFC so a pattern cannot join the text around them (`<wbr>` adds nothing); the ranges callback returns byte offsets; `map_ranges_to_segments()` writes each covered text node as escaped pieces, one wrapper per piece, so `N<em>AS</em>A` becomes three spans, each inside its own parent; every other text token is written with the same `escape()`, and tags and comments with `serialize_token()`. **Quotes (review of #342):** `serialize_token()` writes text with `ENT_QUOTES`, so a wrapped block held `&apos;`/`&quot;`, and `render_block` runs inside `do_blocks` (the_content 9), before `wptexturize` (10), which does not read them: the block kept straight quotes beside curly neighbors. `escape()` is `ENT_NOQUOTES|ENT_SUBSTITUTE|ENT_HTML5` plus `serialize_token()`'s `\r` → `&#xD;` and NUL → U+FFFD (WordPress 7.1). Literal quotes bring a second problem: `wptexturize` reads each text between tags alone, so a quote right after `</span>` reads as an opening quote (`<span>NASA</span>'s` → `NASA‘s`, `"<span>NASA</span>".` → `“NASA“.`, measured on 7.1.3; core does the same to `<em>NASA</em>'s`). `escape_gap()` curls only that quote, by calling `wptexturize()` on `x's` / `1' ` (previous character as `x` or a digit, next as `s` or a space), so the locale, `run_wptexturize` and primes still decide; it does nothing when the match ends in a space or opening bracket, or `wptexturize` is not on `the_content`. Real `wptexturize` on wrapped text gives the same quotes as on the unwrapped text (`6′`, `7″`, `1990’s`, `“NASA”.`). Root/skip tracking uses `get_current_depth()` (an opener's depth includes it, a closer is back at the parent's depth). **Fails open:** no `WP_HTML_Processor` with a *public* `serialize_token()` (WordPress < 6.9, `is_supported()` via reflection), `create_fragment()` null, `get_last_error()` set (unsupported markup), `paused_at_incomplete_token()` (an unterminated token at the end: it sets no error, and the tokens would drop it), a root over `MAX_PLAIN_BYTES` (64 KB), or no match → the original HTML byte for byte. Anything wrapped comes back in the HTML API's normalized form (double-quoted attributes, lower-case tags).
- **Where it runs** — `apply_grep_styles()` on `render_block` (priority 9, before `collect_rendered_style_refs()` at 10 so the rules' styles are collected) for `GREP_BLOCKS` (`core/paragraph`, `core/heading`, `typost/block` — filtering by block name also stops a parent block from re-wrapping its children), strpos-gated on `typost-ps-`, then `references_grep_rules()` (a regex over the block's `typost-ps-{ref}` references against the map, legacy `ps_…` refs included), so on a site with rules only a block whose style has rules is parsed. `wrap_grep($html, $rules_by_ref, $valid_ids, $require_styled = true, $font_ids = array())` (static, tested) first returns a fragment with a registered shortcode unchanged (`has_registered_shortcode()`: GREP runs before `do_shortcode` at 11, so a pattern would match inside `[foo id="42"]`; it tests the entity-decoded text too, because wrapped text is written back decoded and `&#91;foo&#93;` would become a real shortcode; `$shortcode_tags` must be non-empty, because the core regex with no tags matches any `[ `). A root has `typost-styled` + a `typost-ps-{ref}` class whose style has rules (legacy `ps_…` refs included), and not `typost-fit` (fit lines were measured in the editor; out of scope as in #195). The Typography Stylist block's screen reader copy has neither class, so only the `aria-hidden` visual copy changes. Spans are `<span class="typost-styled typost-grep" data-style-id="B">`: they render through B's existing inline-span rule, are never roots themselves (no `typost-ps-` class), so one level of rules only. `get_grep_style_map()` (memoized per request, reset by `save_styles()`).
- **Patterns** — `includes/class-typost-ps-grep.php` (`Typost_PS_Grep`). Built-ins (`built_in_patterns()`, stored by name): acronyms `\p{Lu}{2,}` as a word, a plural `s` may follow; fractions `\d{1,4}[/⁄]\d{1,4}` not touching another `/`, digit or decimal (so `9/22/2026`, `2026/9/22`, `1.5/2` are left alone — a bare `9/22` cannot be told from a fraction and does match, documented); ordinals `st|nd|rd|th|er|re|ème|ère|e` after a digit; numbers (digit runs with `.`/`,` inside); `&`. All compiled with `uD` (`D`: `$` only at the end, as in JS) and delimiter `\x01` (control characters are rejected in patterns). **Order:** rules run in list order and a match that overlaps an earlier rule's match is skipped, so the higher rule wins (Fractions above Numbers) and a match is never split between two rules (a split `1/2` would break `frac` shaping). `MAX_MATCHES` (500) per rule per block.
- **Custom patterns** — `validate_pattern()`: non-empty, valid UTF-8, ≤ `MAX_PATTERN_LENGTH` (200) characters, no control characters, `js_incompatibility()` (a scanner that accepts only syntax both PCRE and a JS `u` RegExp accept: literals, groups `(?:` `(?<name>` and lookarounds, quantifiers with optional lazy `?`, classes, `\d\D\w\W\s\S\b\B\n\r\t\f\0`, backrefs, `\k<name>`, `\xHH`, `\cX`, `\p{Category}` with a general category, escaped punctuation; it names the first construct outside it: atomic groups, possessive quantifiers, inline flags, `\x{…}`, `\A`, `\v`, script names, POSIX classes, a lone `{`/`}`/`]`, `[]`, a quantified lookaround, `\-` outside a class), PCRE compiles it (the compile warning becomes the message), and it stays under `BACKTRACK_LIMIT` (100,000, `pcre.backtrack_limit` set around each call and restored — it also limits the JIT) on adversarial subjects. The admin form also runs `new RegExp(pattern, 'u')` before saving, so a pattern compiles in both engines. **Validation is shared, matching is not:** PHP's `u` modifier turns on UCP, so `\d`, `\w` and `\b` follow Unicode in PCRE and stay ASCII in a JS `u` RegExp (measured, PHP 8.4 / PCRE 10.44 vs Node 24: `\d` on `٣` and `\w` on `é` match only in PCRE; `f\b` on `café` matches only in JS). `\s` follows Unicode in both but differs on U+FEFF (JS only) and U+0085 (PCRE only). They agree on ASCII, and `\p{…}` agrees everywhere, which is why the built-ins use it. Only PCRE runs today; an editor preview must deal with this. **Runtime:** `match_all()` returns false on any PCRE error or limit, and that rule is skipped for that render (fail open). **Capability (the issue's open question, decided on the issue's proposed split):** built-ins need the routes' `edit_posts`; adding or changing a custom pattern needs `manage_options` (`sanitize_rules()`'s `can_write_custom`), and an author may keep (and reorder) a custom pattern already stored.
- **REST** — POST/PATCH accept `grepRules` (PATCH: absent = unchanged, `[]` = remove; `has_param()`). A bad list is a 400 `{field: 'grepRules', ruleIndex, ruleField: 'pattern'|'regex'|'styleId'}` and nothing is saved. A rule cannot apply its own style or an unknown one. DELETE removes the rules that applied the deleted style and returns `grepChanged`. The admin-card route's `related` includes the styles whose rules apply the saved style (their card names it).
- **CSS** — `font-feature-settings` is one property, so a span whose style sets `c2sc` would drop the paragraph's `onum`. `grep_feature_css($style, $styles)` writes, for each rule style that sets features when the paragraph style does too, `.typost-ps-A .typost-grep.typost-grep.typost-grep[data-style-id="B"][data-style-id]×3` (0,8,0) with both lists (paragraph first). It is a separate generator, not part of `generate_style_css()`, so the PHP/JS twins stay byte-identical; printed after the styles by `print_style_rules()` and appended by `get_all_css()` (an existing cached CSS text never has rules, so `CSS_CACHE_KEY` was not renamed). Variation settings are not combined (documented). `print_style_rules()`, `font_ids_from_content()` and `font_ids_from_forced_styles()` go through `with_grep_targets()`, so the rule styles' rules print and their fonts load wherever the paragraph style is used.
- **Admin** — the Edit form's "GREP styles" fieldset (`data-grep`) is in the template only when `grep_supported()`; `typostPSAdmin.grep` = `{supported, canWriteCustom, maxRules, maxLength, patterns}`. `admin.js` builds one `<li><div role="group" aria-label="GREP rule N">` per rule with DOM methods (`buildGrepRow()`; a role on the `li` would remove its list item semantics): Pattern select (Custom offered to administrators, kept in a row that has one), Regular expression (custom only; read-only for authors), Apply style (every style but this one; a deleted one as "A deleted style"), Move up / Move down / Remove with numbered `aria-label`s. `renumberGrepRows()` sets each control's `data-field="grep-{i}-{pattern|regex|styleId}"` so `showFormError()` / `grepErrorField()` mark the right control. Focus: Add → the new row's pattern; Move → the used button, or the other one at an end (`moveGrepRule()`); Remove → next row, previous row, else Add (`removeGrepRule()`); each is announced. `readEditForm()` reports `grepRules` (null without the fieldset, so a save never sends them), `validateEditValues()` ends with `validateGrepRules()`, `buildEditPayload()` sends `grepRules` only when the normalized list changed. The card lists the rules ("GREP styles: Fractions (1/2, not dates) → Fraction"; no Inherited/Override chip — rules do not follow Based On) and `render_card_preview()` runs the sample through `wrap_grep(..., false)` (the sample has no `typost-styled`), so the preview shows the sample's fraction and figures as a post would. Its spans carry `data-typost-font-id` (`$grep['fonts']`, the rule style's resolved font after replacements, passed to `wrap_grep()`/`open_tag()`; the frontend passes none), so the admin font loader adds an Adobe kit that only a rule's style uses. Below WordPress 6.9 the card shows neither.
- **Export and import** — each style writes `grepRules: [{pattern, regex?, style: "sN"}]`; the rule styles are added to a selection with a note, like parents (the export closure now runs until nothing is added). `read_items()` rejects a rule whose `style` key is missing or the style itself, and runs `validate_pattern()` on every custom pattern: one failure rejects the whole file in the preview and the import ("“Body”, GREP rule 2: … Nothing was saved."). The preview lists each style's rules (`items[].grep`, shown as a note under the name in `admin-export.js`) and every custom pattern as a section note, and warns when the site is below 6.9 (the rules are imported but do nothing). After every style has its ID, `plan()` maps each rule's style key (an imported style, or the site style that stands in for a skipped one); an unknown built-in name (a newer release's) and a rule whose style is not imported are left out with a warning. Overwrite takes the file's rules. Export always writes the key, also as `[]`, so Overwrite from a style with no rules removes the target's rules; a file written before #196 (no `grepRules` key, `null` in `plan()`) keeps the overwritten style's own rules.
- **Tests** — `tests/Unit/ParagraphStylesTextRangesTest.php` (engine on the real parser, `wrap_grep`, the render filter, the card), `ParagraphStylesGrepTest.php` (patterns, the subset scanner, limits, order, sanitizing, REST, CSS, fonts), `ParagraphStylesGrepTransferTest.php`, and Jest `__tests__/admin-grep-rules.test.js`. The parser tests load WordPress's HTML API from `TYPOST_WP_DIR` (a WordPress 6.9+ checkout, `tests/Support/HtmlApi.php`, which also loads `utf8.php` when the processor calls `wp_scrub_utf8()`, as 7.1 does) and are skipped without it; CI sparse-clones `wp-includes/html-api` and `class-wp-token-map.php` from WordPress 6.9. Their `tearDown()` sets the engine's support memo back to false, so later tests run as on an older WordPress whatever order PHPUnit picks.
- **Not done:** an editor preview (the block editor shows the text without the rules; running patterns in the editor needs a Web Worker with a time limit, per the issue — the shared subset means the pattern compiles there, and `\d \w \b \s` need handling on non-ASCII text, see Custom patterns), rules on styles applied to a text selection (out of scope), rules inherited through Based On, fit-to-width text, and combining `font-variation-settings`.

## Nested styles (#195, v2.4.0+)

A style can carry an ordered list of **nested rules** on its record (`nestedRules`, beside `grepRules`; not in `properties`, so Update Style never touches them and no property plumbing changed). Each rule applies another style to the start of the text: rule 1 from the first character, each later rule from where the one before stopped. The issue's open question (a separate character style list?) is answered **no**: rules pick from the paragraph style list, as GREP rules do, because a sparse style already works as a character style.

- **Rule shapes** (`Typost_PS_Nested::sanitize_rules()`, `includes/class-typost-ps-nested.php`): `{styleId, unit: 'words', count, end: 'through'|'upto'}`, `{styleId, unit: 'characters', count}`, `{styleId, unit: 'marker', count, marker, end}`, `{styleId, unit: 'line'}`. Fields a unit does not use are dropped; `end` defaults to `through`; `count` is an integer 1–`MAX_COUNT` (100, a digit string is accepted); `MAX_RULES` 10. A marker is exactly one grapheme (`^\X$`, ≤ 32 bytes), no `\p{Cc}` and not U+FFFC (the engine's object mark). The admin form checks the grapheme count only with `Intl.Segmenter`, and leaves it to the server otherwise: counting code points would refuse a flag. **First line must be the last rule** (an error otherwise): where line 1 ends depends on the width, so nothing can start after it. A rule cannot apply its own style or an unknown one.
- **Counting** (`find_ranges()` / `rule_end()`): every rule starts at its first character that is not a space after the previous rule (`[\s\x{FFFC}]`: Unicode white space with `u`, a `<br>`'s `\n`, and the object mark of an image or skipped element), so a span never starts with a space. Words are runs between spaces (punctuation belongs to its word; `—` joining two words makes one word). **Through** a word count takes the spaces after the last word (the space is the word's end marker, as in InDesign); **Up to** stops at the end of the word. Characters are grapheme clusters (PCRE `\X`, no intl needed; spaces inside the run count), and Through/Up to give the same text, so the rule stores no `end`. A marker rule runs to the count-th marker: Through includes it, Up to stops before it, so the next rule starts at the marker. Text shorter than the count, or a missing marker, ends the rule at the end of the text and the later rules style nothing (acceptance criterion). A rule whose style was deleted still uses its text (no span), so the rules after it stay where they were. A PCRE failure (invalid UTF-8) returns no ranges: fail open. Offsets are bytes.
- **Rendering** — `apply_nested_styles()` on `render_block` at **priority 8**, before GREP (9) and the collector (10), same `GREP_BLOCKS`, same strpos/`references_grep_rules()` gate, against `get_nested_style_map()['rules']` (styles with a rule that wraps text — a style with only a First line rule is never parsed). `wrap_nested()` mirrors `wrap_grep()` (shortcode guard, `rule_root_callback()` — the root test both share: `typost-styled` + a `typost-ps-{ref}` class with rules, not `typost-fit`) and writes `<span class="typost-styled typost-nested" data-style-id="B">` (`Typost_PS_Nested::open_tag()`), rendering through B's `[data-style-id]` rule. GREP then runs on the result, so a GREP match inside a nested span is wrapped inside it (`<span nested>Step <span grep>1</span>:</span>`; verified on WordPress 7.1.4). One level: nested spans carry no `typost-ps-` class, so B's own rules never run inside them. The screen reader copy of a Typography Stylist block has neither class and never changes.
- **First line** is CSS, from `nested_css()`: `.typost-ps-A:not(.typost-fit)::first-line { … }` (plus the legacy ref) with the declarations of the line style that a first line takes: `property_declarations()` — the declarations of a style's main rule, extracted from `generate_style_css()` with byte-identical output (`test_the_style_css_itself_is_unchanged_by_the_declarations_refactor`) — minus `--typost-hang`, `text-wrap` and `text-wrap-mode`; layout, alignment and indents never come along because they are separate rules. Its `font-feature-settings` lists the paragraph's features first when both set some. The selector has no `.typost-styled`, so the admin card sample (class `typost-ps-N` only) shows it. **Inheritance:** the spans of the rules before it sit inside line 1, so a property their style sets wins there and the rest comes from the first line (the "L" of a Bold-then-uppercase-first-line style is bold *and* uppercase) — documented, not fixed. In the editor the rule applies to the editable element directly; `::first-line` does not move the caret (measured in Chromium: Home lands at the start and Shift+Home selects the line, unlike `::first-letter`).
- **CSS** — `nested_css()` also writes the feature-combining rules for the nested spans: `rule_feature_css()` (extracted from `grep_feature_css()`, which now calls it with `typost-grep`; output unchanged) with `typost-nested`, for the text rules' styles (`target_style_ids($rules, true)` leaves out the line style). Printed after the GREP rules by `get_all_css()` and `print_style_rules()`. **Below WordPress 6.9 it returns `''`**, First line included, so the rules have no effect anywhere (issue's "must keep"); the CSS transient is not renamed (no cached CSS ever had these rules).
- **Fonts** — `with_grep_targets()` is now `with_rule_targets()` and adds the targets of both rule lists (`get_nested_style_map()['all']`, First line included), so the fonts of nested styles load wherever the paragraph style is used and their CSS prints. `save_styles()` resets the map and clears core's per-post font detection cache, as before.
- **REST** — POST/PATCH accept `nestedRules` (PATCH: absent = unchanged, `[]` = remove). A bad list is a 400 `{field: 'nestedRules', ruleIndex, ruleField: 'styleId'|'unit'|'count'|'marker'|'end'}`; nothing is saved. Every author with the routes' `edit_posts` may write rules (no pattern runs, so no `manage_options` split). DELETE removes the rules that applied the deleted style and returns `nestedChanged`; the rules after a removed one then start earlier. The admin-card route's `related` includes styles whose nested rules apply the saved style.
- **Admin** — the Edit form's "Nested styles" fieldset (`data-nested`) sits after the GREP fieldset inside the same `grep_supported()` gate; `typostPSAdmin.nested` = `nested_admin_settings()` `{supported, maxRules, maxCount, units, ends}`. `admin.js` builds one `<li class="typost-ps-nested-rule"><div role="group" aria-label="Nested rule N">` per rule (`buildNestedRow()`): Apply style, Ends (Through/Up to), Count, Unit, Character, then Move up / Move down / Remove. **Own classes only** (`typost-ps-nested-up/-down/-remove/-add`): the GREP click handlers are bound by class on `document`, so sharing `typost-ps-grep-remove` would let them act on a nested row (a Jest test checks). `updateNestedRow()` hides the fields a unit does not use and `readNestedRules()`/`normalizeNestedRule()` drop them, so a switched unit never sends a stale marker. `data-field="nested-{i}-{field}"`; `validateNestedRules()` (run after `validateGrepRules()`) mirrors the server (`canBeOneCharacter()` checks the grapheme count only with `Intl.Segmenter`, else the server decides; `utf8ByteLength()` checks `MAX_MARKER_BYTES`); `nestedErrorField()` maps a 400. Focus and announcements as for GREP. The card lists the rules ("Nested styles: Through 1 “:” → Bold; Up to 3 words → Small caps; First line → Lead") and `render_card_preview()` runs `wrap_nested()` before `wrap_grep()`. Detach reports nested rules in its notice (`buildDetachBlockSettings({hasNestedRules})` → `'nestedRules'`, label "nested styles", from both `editor.js` and the block's `edit.js`).
- **Editor preview** — the issue requires the editor to show the result and the spans never to reach saved content. `nestedRuleRanges()` in ps-utils.js is the **counting twin** of `find_ranges()` (UTF-16 offsets; `Intl.Segmenter` for graphemes with a code-point-plus-marks fallback), held to `__tests__/fixtures/nested-rule-ranges.json`, which `ParagraphStylesNestedTest::test_the_shared_fixture_matches_the_javascript_twin` and `nested-preview.test.js` both read. `collectNestedText()` reads an element as the engine reads HTML (`<br>` = `\n`, skip/void elements = U+FFFC, `<wbr>`/comments nothing); `applyNestedPreview()` wraps each covered piece of a text node in a span marked `data-typost-nested-preview` and returns `{original, parts}` records; `removeNestedPreview()` puts the **same** text node objects back and unwraps any marked span left over. `initNestedPreview()` in editor.js (on `wp.domReady`, only when `typostData.paragraphStylesOptions.nestedPreview`, i.e. WP 6.9+) decorates only roots whose block is **not selected, not multi-selected, has no selected inner block, and holds no focus**, scanning `document` and every `iframe[name="editor-canvas"]` for `[data-block] .typost-styled[class*="typost-ps-"]` and `.typost-styled[data-block]` (core blocks are their own `data-block` element). Why this is safe: RichText reads its element's DOM only on input/composition/selection events of the focused element, and serialization reads attributes, not the DOM. Undecorate happens on store change (selection, also from List View; done synchronously in the subscriber before the throttled re-sync) and in **capture-phase** `pointerdown`/`mousedown`/`touchstart`/`focusin`/`dragstart` listeners on each canvas document, before the browser places a caret or RichText sees focus. A re-sync compares a signature (plain text + rules) and that every record part is still inside the root (RichText rewrites the DOM on undo), else it removes and re-applies. Verified in WordPress 7.1.4 (Chromium, SQLite): unselected core paragraphs, headings and a Typography Stylist block show the spans; a click mid-word lands the caret on the clicked character and typing works; keyboard entry, undo while another block is selected, multi-select and Save leave `getEditedPostContent()` and the stored post free of `typost-nested`/`data-typost`. The editor still does not preview GREP rules.
- **Preview traps (review and QA of #352)** — (1) **A press on a span:** the spans come off in the capture phase of `pointerdown`, and in Chromium a press whose target text sat in a span that was removed there selected the block but placed no caret: the selection stayed in the previous block and typing went nowhere (Firefox was fine; a plain-text press was fine because its parent stays). So every preview span has `style="pointer-events: none"`, the target is the parent, and carets land at the offsets a block without a preview gets (`private/demo/qa-nested-click.js`, measured against a control block). (2) **A value written over the preview:** when a block's value changes while it is decorated (undo, a programmatic update, another author), RichText's `applyValue()` reuses a child of the same node name, drops its attributes and rewrites its text, so a part being in the element proves nothing. `nestedRecordIsUntouched()` puts the original text node back only if each part is still under one parent, each span keeps its marker and the parts' text equals the original; otherwise what the editor wrote stays. (3) **After a style changes in the editor (#354):** `refreshDynamicStyleCss()` rebuilds only each style's main rule from JS, at once, and it only adds to the CSS printed at load, so a declaration a style dropped would stay until a reload (the style's own rule and a First line rule both); a `::first-line` rule or a combined feature rule also reads another style. `refreshServerCss()` therefore reads `GET /paragraph-styles/editor-css` (`{main: get_main_css(), nested: get_nested_css()}`; `get_all_css()` is the two joined) on every style change. It writes `main` over `#typost-paragraph-styles-inline-inline-css`, writes `nested` to `#typost-ps-dynamic-nested-css` after the dynamic main rules, and empties `#typost-paragraph-styles-nested-inline-css` (`enqueue_editor_style_css()` prints the nested rules on their own handle). A rebuilt canvas brings the old elements back, and the re-injection writes them again. Only the latest response counts; a failed read leaves the rules as they were. The admin card's preview wrapper carries the `data-typost-font-id` of a First line rule's style, because no span does. (4) The preview changes DOM that RichText owns. Core's experimental `__experimentalCreatePrepareEditableTree` decorates without that, but it is experimental; not done.
- **Marker search (review of #352):** `find_marker()` / `nestedFindMarker()` skip a match that a combining mark or a zero width joiner follows, so "e" does not end a rule inside a decomposed "é". Known limit, accepted for an emoji marker only: a match can still be part of a longer cluster when a skin tone modifier follows it, in half of a flag, or as the tail of a joined sequence. Comparing grapheme boundaries would close it, but `\X` and `Intl.Segmenter` can disagree, which risks the twins' parity.
- **Deleting a style a nested rule applies** removes the rule, so the rules after it start earlier. The Delete confirmation names the styles that lose a rule (`nestedRuleUsers()` in admin.js).
- **Export and import** — each style writes `nestedRules: [{style: "sN", unit, count?, marker?, end?}]`, always (also `[]`, so Overwrite can clear); the export closure adds the rule styles with a note. `read_items()` runs every file rule through `sanitize_rules()` with a placeholder style id, so the checks are Save's; one failure rejects the file ("“Step”, nested rule 2: Type one character only. Nothing was saved."), as does a missing key or the style itself. The marker round-trips as the character (JSON `—` decodes back; tested with `—`). After every style has its ID, `plan()` remaps each rule's style; a rule whose style is not imported is left out with a warning that the rules after it start earlier. A file with no `nestedRules` key keeps an overwritten style's rules. The preview lists the rules per style (`items[].nested`, shown by `admin-export.js` with `typostExportL10n.nestedRules`) and warns below 6.9.
- **Tests** — `tests/Unit/ParagraphStylesNestedTest.php` (counting, the shared fixture, sanitizing, `wrap_nested` and both render filters on the real parser, `nested_css`, the refactor's unchanged output, fonts, REST, the card), `ParagraphStylesNestedTransferTest.php`, Jest `__tests__/admin-nested-rules.test.js` and `__tests__/nested-preview.test.js`.
- **Not done / limits:** line rules beyond the first line, Repeat rules and "End Nested Style Here" (out of scope); fit-to-width text (left alone, as for GREP); rules on styles applied to a text selection; rules inherited through Based On. A span written in the middle of a word (Characters, or a marker inside a word) can make some screen readers read the word in two parts on core blocks, as for GREP ordinals.

## Export and import (#205)

`includes/class-typost-ps-transfer.php` (`Typost_PS_Transfer`) registers the `paragraphStyles` section on core's `typost_export_sections` (see root CLAUDE.md "Export & Import" and HOOKS.md "Export Sections"); capability `edit_posts`, `options: ['typost_paragraph_styles']`, priority 20. The module gives it two public wrappers: `sanitize_style_properties()` (the REST create route's `sanitize_properties()`) and `save_imported_styles($styles, $next_id)` (one `save_styles()`, counter moved forward only).

- **File shape:** `{key: "s1", name, basedOn: "s1"|null, properties}` in stored order. `key`/`basedOn` are file-local; `properties.fontId` is the file font key (`$fonts->key_for_font_id()`), dropped for a standalone style whose font is gone and written as `0` for a child (so it does not inherit the parent's font). A child is written with its **own** properties exactly as stored (empty unsets included), so inheritance survives; a style whose parent no longer exists is written with its compacted resolved look and no `basedOn`. `legacyId`, `id`, `created`, `modified` are never written. Exporting a selection (`$args['items']`) adds every ancestor, with a note; the export UI says the same live from `items()` (`{id, name, parent}`).
- **Import plan** (`plan()`, run by the preview with the defaults, by the dry run and by the write): `read_items()` rejects a non-list, bad or duplicate keys, empty names, a missing or self parent, non-object properties, and chains `based_on_error()` rejects (loops, more than `MAX_BASED_ON_LEVELS`) on a temporary copy with IDs 1..n. Styles are placed parents first (`parents_first()`). Choices (`default_choices()` when none is sent): **skip** (default when the name exists, compared trimmed and case-insensitive) — the existing style stands in, so children are based on it, with a warning when that makes a child look different from the file (`same_look()`: `drop_inherited_properties()` both ways); skip of a style with no namesake leaves its children standalone with their file look; **add** (default otherwise; the name must be free), **rename** (default for a name an earlier style in the file uses; `suggestedName` = "Name (2)"…, avoiding every name in the file and every other suggestion, so a later style whose own name is free stays **add**: "Body", "Body", "Body (2)" → add, "Body (3)", add), **overwrite** (keeps `id`, `name`, `legacyId`, `created`; takes the file's properties and parent; the preview lists the styles based on it as `affected`; two overwrites of one style are rejected). New IDs start at max(counter, highest ID + 1), so a deleted style's ID is never reused. Properties go through `sanitize_style_properties($raw, $has_parent)` and, for a child, `drop_inherited_properties()` against the parent's resolved properties — the create route's steps. A numeric `fontId` in a file is another site's ID and imports as no font. After placing, the chain of every added or overwritten style is checked with `based_on_error()`, which also counts the styles below an overwritten one (an overwrite can link existing styles into a loop or past 10 levels); only those, so a broken chain already stored on the site does not block an unrelated import. Warnings: OpenType features hidden for the mapped font in Feature Visibility, and axis tags in `fontVariationSettings` that `typost_font_axis_tags` (Variable Fonts) does not list for it.
- Tests: `tests/Unit/ParagraphStylesTransferTest.php` (round trip on the same site changes nothing; another site with other IDs; selection; collisions; loops; sanitizing; warnings) and the property round trip in `tests/Unit/ExportRegistryTest.php`.

## REST API

CRUD at `typost/v1/paragraph-styles` (GET/POST) and `/paragraph-styles/{id}` (PATCH/DELETE), plus `/paragraph-styles/{id}/admin-card` (GET, the admin tab's card refresh, #221), all requiring `edit_posts` — styles are author-facing content, unlike variable-font axes (`manage_options`). `sanitize_properties()` whitelists keys; `fontVariationSettings` is re-validated at CSS generation time (`"tag" number` pairs only). Every request in the admin tab's `admin.js` (save, Reset to Base, delete, admin-card) wraps its URL in `withUserLocale()` and sets `dataType: 'json'`, so the server's error messages use the admin's language (#296); a source-scan test in `admin-edit-form.test.js` fails on a call that skips either.

## Conventions

- Own text domain `typost-paragraph-styles` with its own `languages/` (.pot, fr_FR/es_ES .po/.mo, and JED .json files for `wp_set_script_translations`; JED filenames hash the plugin-relative script path, e.g. `paragraph-styles/assets/js/editor.js`).
- **`ps-utils.js` is translatable too**, because it builds the browser's size labels ("Fluid 20–48", "Fit ≤ 120px"). Script translations are per *handle*, not inherited from the editor script that depends on it, so `typost-paragraph-styles-utils` declares `wp-i18n` and gets its own `wp_set_script_translations()` call and its own JED file. Inside the file `wp.i18n` is looked up lazily behind a `typeof wp !== 'undefined'` guard and falls back to the English source, because Jest requires the module directly with no `wp` global.
- No console logging / `error_log()` (repo policy); REST failures surface as HTTP error responses, saves fail quietly in the panel.
- Editor panel CSS is injected once by `editor.js` into the top document (the panel renders in popovers/sidebar, not the editor canvas iframe).

## Selection-scoped apply and inline overrides (v2.3+)

`applyTo: 'selection'` wraps the selected text in a `data-style-id` span, and the style renders through its CSS class. Inline declarations on spans *inside* that wrapper (a first letter with its own font and swash) beat the class in the cascade, which is why a style once visibly skipped such text. Core's `applyInlineParagraphStyle` (edit.js) now calls `countParagraphStyleConflicts()` first and, when the selection contains spans carrying style-owned attributes, asks with `window.confirm` before applying; on confirm it runs `stripParagraphStyleOverrides()` (both in core `utils.js`) over the styled span and its descendants. The strip set mirrors the normalized apply payload (font, weight, style, size, spacing, line-height, features, variation settings); raw `data-feature-settings` and `data-fitscale`/`data-fitshift` are glyph-level and survive. A span that strictly contains the selection is handled by **splitting** it (`applyParagraphStyleBySplit()`, built on `splitSpanAndApply()` with a temporary marker attribute to pin the innermost container): the class-beats-inline argument only holds for properties the style declares, and the module's CSS generator is silent on unset ones, so a nested wrapper would inherit the run's size or swash. The selected segment gets the style id and is stripped like any affected span; the text on either side keeps the run's styling. Only the innermost container is split — a second, outer container makes the splitter refuse (a child crosses a boundary) and the apply falls back to the nested wrapper, a documented limit. Cancel returns `true` from the handler so the style is **not** applied block-level as a fallback.
