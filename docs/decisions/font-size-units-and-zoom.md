# Font size units and zoom

- **Topic:** how the block, inline spans and paragraph styles write a font size (px or rem), how responsive and fit-to-width sizes grow with browser zoom, and the setting that picks the unit for new content.
- **Issues:** #233, #234, #235, #248, #250, #255 (and #410, which moved the #248 variation into `assets/js/new-block-tag.js`)
- **Code:** `assets/js/font-size-units.js`, `assets/js/new-block-tag.js`, `blocks/typography-stylist/save.js`, `blocks/typography-stylist/deprecated.js`, `blocks/typography-stylist/utils.js`, `blocks/typography-stylist/hooks/use-fit-measurement.js`, `blocks/typography-stylist/style.css`, `assets/js/block-editor.js`, `assets/js/inline-editor/`, `paragraph-styles/paragraph-styles.php`, `paragraph-styles/assets/js/lib/ps-utils.js`

Moved from the root [CLAUDE.md](../../CLAUDE.md) by #361. Read the guide's hard rules first: content saved before #233 must keep its px markup byte for byte.

**Responsive Font Sizing:**
- Uses CSS `clamp()` function with three independent size values
- **Mobile (320px+):** Minimum size for small screens
- **Intermediate:** Preferred size for medium screens (calculated via viewport units)
- **Large (up to 1920px):** Maximum size for large screens
- Breakpoint constants: `RESPONSIVE_FONT_MIN_VIEWPORT = 320`, `RESPONSIVE_FONT_MAX_VIEWPORT = 1920`
- Size controls operate independently with soft validation (warnings only, no auto-adjustment)
- CSS `clamp(min, val, max)` does **not** auto-sort out-of-order values; it evaluates to `max(min, min(val, max))`, so when `min > max` the expression effectively collapses to `min` and may clamp to an unintended size. The UI warns when values are out of order to prevent this and does not auto-correct them.
- Default sizes for new blocks: 16px / 32px / 64px

**Font size units (v2.3.2+, #233):** authors always enter px; new content writes rem (px ÷ 16) so it follows the reader's default font size setting, and content saved before #233 keeps writing px byte-for-byte. One shared module, `assets/js/font-size-units.js` (CommonJS, required by `block-editor.js` through browserify and imported/re-exported by the block's `utils.js`), holds `resolveFontSizeUnit()` (only an explicit `'rem'` is rem — missing means older content, so px), `pxToRem()` (six decimals by textual shift, below 0.0001rem → 0 because PHP prints smaller floats as `1.0E-5`), `formatFontSizeLength()` and `buildResponsiveClamp(min, pref, max, unit)` — the px form is the legacy expression byte-for-byte (float artifacts included), the rem form rounds the vw term to four decimals like the paragraph style generators (16/32/64 → `clamp(1rem, 2rem + 3vw, 4rem)`). **Block:** attribute `fontSizeUnit` (`'px' | 'rem'`, enum, default `'rem'`) drives the responsive/fit clamp, the fixed size and the fit cap (`min(…cqi, Nrem)` via `buildFitFontSize`/`buildFitLineOpenTag`/`buildFitLinesHtml`/`wrapFitLines`, all with a trailing `unit` param defaulting to px); `edit.js` uses the same unit (`blockFontSizeUnit`) for its preview and fit editing value so the editor and frontend agree, and its slider readouts show "24px (1.5rem)" only on rem blocks. **Deprecations `[v2, v1]`:** v2 is a frozen copy of the pre-#233 save with its utils helpers copied in under a `v2` prefix (never edit), schema = block.json minus `fontSizeUnit`, `apiVersion: 3`; both v2 and v1 `migrate()` set `fontSizeUnit: 'px'` (core runs only the matched entry's migrate and keeps only the entry's schema attributes, so without it the attribute came back undefined and unstored). Inherit blocks and styleClass blocks write no block-level size, validate against the current save directly and get the `'rem'` default — except a fit block, whose per-line sizes are written under a styleClass too (a px cap, and since #235 a rem line reads `--typost-fit-width` even uncapped), so it matches v2 and migrates to px. A styleClass block's own unit therefore says nothing about its age: under a style the editor previews size edits in the style's unit (`sizePreviewUnit`), and when the block leaves the style — Detach (`styleClass: ''` through the apply bridge) or the orphan effect for a deleted style — `resolveDetachFontSizeUnit()` sets `fontSizeUnit` to the style's unit (a deleted style gives px, the pre-#233 output), so the sizes it then writes itself render as the style did (review of #233: Detach used to turn an older styled block's sizes into rem). Verified in the real editor on 10 pre-#233 demo blocks (fit + responsive) plus crafted pre-#218 and post-#218 fixed blocks: all valid, post not dirty, edit + save keeps px with `"fontSizeUnit":"px"` stored. **Inline spans** have no stored unit. A size the author sets is written in rem (the new-content unit: px on a site with the #248 setting, see below). The inline editor rebuilds a span's whole style on every apply, also for a feature-only change, so its full-rebuild path asks `resolveSpanFontSizeUnit()` (font-size-units.js): author changed the size this session → the new-content unit (rem, or px with the #248 setting); the span already declares a font-size → that declaration's unit (the px clamp rebuilds byte for byte); the span is under a paragraph style (Detach) → the style's unit, px for a deleted one; otherwise the new-content unit. Read `pending.keys` before `_resetPendingChanges()`. The mixed-selection patch path writes a size only when the author changed it, and the block's QFT merges keep the existing declaration (`applyOrMergeStyling`), so neither needs it. QFT `buildInlineFontSizeSpan()` also converts a fixed `'24px'`/`24` to rem (the new-content unit, #248) (keeping `data-fontsize` as given). **Fixed inline sizes (#255):** the inline editor's select has only Inherit/Responsive, but a fixed size (`64` from a paragraph style through the apply bridge, or a span's `data-fontsize="64"` read back into state) still reaches its span write paths; all three (full rebuild, mixed-selection patch, and the partial-selection Convert to block span — the whole-block convert sets block attributes through `buildConvertBlockAttributes()` instead) go through `buildInlineFontSizeValue()` (font-size-units.js: `parseFixedFontSize()` → `formatFontSizeLength()`, else the responsive clamp, `null` for no size — guard on the value, not on `fontSize !== 'inherit'`) and its twin `buildInlineFontSizeAttributes()` (`data-fontsize`, plus the slider values only when not fixed), so a fixed size is a length and writes no `data-fontsize-min/preferred/max` (the patch path removes them). The convert span takes `getZoomNoticeUnit()` — the rebuild's unit rule — so a partial convert inside a px span nests a px size, and it carries `data-fontsize` so the new block's QFT reads the size back (review of #255). Before, every non-inherit size was `buildResponsiveClamp()` of the sliders, so a 64 showed at the 16/24/32 defaults' 32px. `buildInlineFontSizeSpan()` shares the same parser. Both selects (inline Font Size, QFT "Font Size (for selected text)") add a disabled "Fixed (Npx)" option plus help text while a fixed size is active, like the inline "Fit to Width (blocks only)" option, so the menu no longer says Inherit; choosing Responsive from there still applies the clamp (verified on mnc4). Under an active paragraph style the inline editor writes no inline size (`hasActiveStyle`), so its help text says to click Detach Style first instead of "choose a responsive size"; the QFT writes the size inline over the class, so its help keeps the responsive wording. **Paragraph styles:** style property `fontSizeUnit`; see `paragraph-styles/CLAUDE.md`. The PHP and JS style generators are held to one shared fixture, `paragraph-styles/__tests__/fixtures/font-size-unit-css.json`, read by both `ps-utils.test.js` and `tests/Unit/ParagraphStylesFontSizeUnitTest.php`, and the whole main rule to `paragraph-styles/__tests__/fixtures/style-css.json` (`style-css.test.js` and `tests/Unit/ParagraphStylesStyleCssTest.php`, #358). **Not done (separate issue):** rem/em entry in the Inspector. Zoom growth for new content is #234/#235 and the site-wide switch to px is #248, both below. Note the test site's theme pins `html, body { font-size: 16px }`, so the browser default size has no effect there; the 32px check needs that rule overridden to `100%` (measured: new responsive max 64 → 128px, fixed 24 → 48px, old px blocks unchanged).

**Sizes that grow with browser zoom (v2.3.2+, #234, #235):** zoom narrows the viewport in CSS px, so at zoom z in a W px window the reader sees z × size(W / z); WCAG 1.4.4 for fluid type is read as "2× by 500% zoom" (no size that grows with the viewport doubles at 200%). Both fixes ride on #233's `fontSizeUnit: 'rem'` as the new-content flag — no new deprecation; px content keeps its markup byte for byte. The one new attribute is `fitWordSizes` (below). No deprecation covers rem output from development builds between #233 and these fixes (unlimited rem slope, plain-cqi or uncapped `var()` lines): all three ship in 2.3.2 and released versions wrote px, so only a dev site can hold such a block (decided 2026-10-09; it shows the invalid-content warning). **Responsive (#234):** for rem, `buildResponsiveClamp()` writes the slope from `getResponsiveZoomLimit()` (font-size-units.js). Closed form, with a = pref, m = min, M = max: the size doubles in every window up to 1920px whatever the slope when M ≤ max(4a, 2.5m) (`reach`); otherwise exactly when b·1920 ≤ reach − a, so the slope is lowered to (reach − a)·100/1920 vw, floored to four decimals (with a 1e-7 epsilon so 2.5 stays 2.5), and the size reaches `reach`, not M, at 1920. The intercept stays pref, so sizes at small windows are unchanged and the default 16/32/64 is not limited at all. 16/16/120 → `clamp(1rem, 1rem + 2.5vw, 7.5rem)` (64px at 1920, 2.00× at 500%; px was 1.71×). Twins: PHP `Typost_Paragraph_Styles::responsive_zoom_vw()` and `responsiveZoomVw()` in ps-utils.js, held to the shared fixture plus a Jest grid parity test. `getResponsiveZoomNotice()` drives a `ZoomNotice` component (`blocks/typography-stylist/components/zoom-notice.js`, and a twin in `assets/js/inline-editor/zoom-notice.js` for the separate build; each names its own sliders, so the wording differs on purpose, and `assets/js/__tests__/twin-parity.test.js` pins both) under the Inspector sliders (responsive only — fit's clamp is just the no-container-query fallback), the QFT inline sliders and the inline editor sliders: `'slower'` for rem (reaches X instead of M; Intermediate ≥ ceil(M/4) reaches M), `'fails'` for px. Speech: the visible text carries live slider values and core's `Notice` re-speaks its children whenever they change — one full sentence per slider step (measured in the live region, review of #250) — so the Notice gets `spokenMessage=""` and the component speaks a value-free sentence only when the notice appears or changes kind after mount (never on mount, which in the QFT/inline modal is the tick the dialog takes focus; screen-reader rule (1) in [screen-reader-rules.md](screen-reader-rules.md)). Unit: the Inspector uses `sizePreviewUnit`; the inline editor `getZoomNoticeUnit()` (same rule as its full rebuild: rem once the author changed the size, else `resolveSpanFontSizeUnit()` on the active format at the saved selection); QFT `inlineFontSizeUnit`, set from `parseInlineStylesAtCursor().fontSizeUnit` (the detected span's declaration — a QFT size apply rewrites the span in rem and the re-detection reports it). Before, both inline surfaces always said 'slower', describing a limit an untouched px span never got. `__tests__/zoom-resize.test.js` evaluates the emitted clamp strings like a browser over every window 320–1920 and reproduces the issue's Chromium table for px. **Fit (#235):** CSS cannot tell zoom from a narrow window, and a line that grows with zoom must overfill some real narrow container, so the floor is gated to where narrow means zoom: rem lines are `min(calc(R * var(--typost-fit-width, 100cqi)), calc(C * 100cqi)[, cap])` (`buildFitFontSize`), and `style.css` sets `--typost-fit-width: 32rem` plus `white-space: normal; overflow-wrap: normal` inside `@media (orientation: landscape) and (max-width: 781.98px) { @container (width < 32rem) }` on `.wp-block-typost:not(.block-editor-block-list__block) .typost-line[style*="--typost-fit-width"]` (px lines never get the wrap). **Word cap (review of #250):** the first version used `overflow-wrap: anywhere`, and a one-word line under the floor is by construction wider than its container, so it always broke mid-word ("April" → "Apr/il" from 300%, measured). C is the line's widest-word ratio from the new `fitWordSizes` attribute (content, like `fitLineSizes`: never in the apply bridge or styles): `measureFitLines()` (`hooks/use-fit-measurement.js`) measures each line's min-content width (`white-space: normal; width: min-content` on the same probe — the browser's own break opportunities, so a word split across inline spans counts as one) and `computeFitWordRatio()` turns it into a ratio, hang-aware like `computeHungFitRatio`, **floored** to four decimals so a word never overflows by a rounding step. C = W when W > R, else R (one word, or W not measured yet): such a line cannot grow without breaking a word, so its cap is its own size. Every rem line keeps the `var()` form even with C = R, so rem output stays distinct from px and a pre-#233 fit block with a styleClass (no block-level size) still matches v2 — writing plain `calc(R * 100cqi)` there made it validate directly as rem, and the measurement then wrote `fitWordSizes` on open and marked older posts dirty. `fitWordSizes` is measured and written only for rem blocks for the same reason. `overflow-wrap: normal` because many themes set `break-word` on headings, which would split a word a sub-pixel too wide. **Measuring probe (review of #250):** `measureFitLines()` used to append its probe `div` to the canvas `body`, so a fit block with no `fontId` was measured in the theme's *body* font while its line renders in the theme's *heading* font — on the test site 208.5px vs 217.1px for "April" at 100px, a 4.1% too-large ratio and a line 31px past its 760px column (horizontal scroll). The probe is now built from the block's own visual heading: same tag, `buildFitProbeClassName()` (drops `typost-fit` — its inline-size containment makes the natural width 0 — `typost-hang` and RichText/`block-editor-*`/`is-*` classes), a copy of its inline style, margin/padding/width/max-width/text-indent reset, appended to the block wrapper `[data-block]` (never inside the editable heading, where RichText would see it) and removed in `finally`; the canvas body stays the fallback when the heading is not rendered. Result: ratio 0.4796 → 0.4606, frontend ink = box (760 = 760). Older fit blocks with no font re-measure the next time they are opened (their stored ratios were wrong); blocks with their own font are unchanged (the four demo pages opened clean). **Frontend only:** the editor canvas iframe is its own viewport — 1100×600 window + Inspector gives a 613×471 canvas, landscape and under 782px, so every fit line wrapped in the editor while the frontend at that window showed one line (measured, review of #250); the editor wrapper always carries `block-editor-block-list__block` and saved markup never does, so the editor shows lines as at 100% zoom, also when the author's browser is zoomed. A zoomed desktop window stays landscape; a phone held upright is portrait; a narrow column in a wide window is above 782px. 32rem = 0.4 × 1280, so with a 16px root a line filling a 1280px window doubles at 500% when its word cap allows. After the word cap (Chromium, 1280×800 window, 760px column): "Moonlit garden party" 2.02× at 300%, 2.69× at 400%, 3.37× at 500%; one-word lines "April"/"Showers" 1.50/1.43/1.37× (container-driven only), no broken word and no #250-caused horizontal scroll at 300–500%. Measured before the word cap (zoom emulated as viewport = window ÷ z): 1280 full width 1.00× → 2.00×; 650px column 1.97× → 3.94×; 1920 full width 1.00× → 1.33× (needs 48rem; not done — it would wrap landscape phones); no horizontal scroll at 320×180; portrait 390 phone, landscape 844 phone and a 350px column in a 1280 window render the same font-size as px lines. Known gaps: a zoomed portrait window (portrait monitor, mobile page zoom) gets no floor; text-only zoom (Firefox) scales rem but not cqi, so it does not reach the floor either; an unzoomed landscape window under 782px with a container under 512px wraps lines of several words (the editor never does, see Frontend only); the floor and the 1280/500% figure assume a 16px root (32rem is the floor), and the responsive limit holds for windows up to 1920px only (16/16/120 is 1.80× at 2560px, 1.57× at 3840px). Every pre-#233 fit block with a styleClass (capped or not) now validates through v2 and keeps `calc(R * 100cqi)`.

**New-content unit setting (v2.3.2+, #248):** Options → "Write new font sizes in px" (option `typost_new_font_sizes_px`, `'1'`/`'0'`, default off) switches what *new* content writes; `Typost::get_new_font_size_unit()` localizes it as the **string** `typostData.newFontSizeUnit` (`'px'`/`'rem'`, so no stringified-flag trap) and `getNewFontSizeUnit()` (font-size-units.js, re-exported by utils.js; only the exact string `'px'` is px) reads it. block.json's `fontSizeUnit` default **stays `'rem'`**: it also decides how saved blocks parse, so a block saved under the rem setting stores no unit, and a per-site default would re-read it as px and fail validation. A new block therefore stores its unit when it is created: (1) the inserter — `installNewBlockVariation()` (`assets/js/new-block-tag.js`, called at the end of `block-editor.js`) registers one `isDefault`, `scope: ['inserter']` variation, `typost-new-block`, on every site: `attributes: { fontSizeUnit: 'px' }` from `buildNewBlockUnitVariation()` on a px site, plus the tag the author picked last (#410), otherwise no attribute. Core's `getInserterItems` drops the block's own item when a default variation exists and inserts with the variation's attributes (`getItemFromVariation` → `initialAttributes`), so the main/quick/slash inserter and drag-from-inserter all store px; no title/icon, so the item keeps the block's. Registered from `block-editor.js` because `typostData` is localized on that handle; variations are keyed by block name, so registering before the block type exists is fine. Before 2.4.0 `block-editor.js` registered `buildNewBlockUnitVariation()`'s own variation (`typost-new-font-size-unit`, px sites only, no `isActive`), so on px sites the block's "Most used" count never rose; the variation now has an `isActive` that matches every Typography Stylist block no other variation claims, and the count rises. How it counts, the one-time reset and the frozen "Transform to" order: [new-block-variation.md](new-block-variation.md). (2) The transforms in `index.js` and Convert to block (`buildConvertBlockAttributes({ fontSizeUnit })`, new blocks only — an existing block keeps its unit). A block created by other code (an extension's `createBlock`) gets rem unless it passes `fontSizeUnit` (HOOKS.md). Duplicate/copy/paste/patterns carry their stored unit, which is the point. Inline spans: `resolveSpanFontSizeUnit({ newUnit })` (a changed or new size → the new-content unit, an untouched declaration keeps its own unit, Detach → the style's unit), the QFT `buildInlineFontSizeSpan(…, unit)` and the QFT span previews use `getNewFontSizeUnit()`. Paragraph styles: `buildPropertiesFromState(state, newUnit)` stores the new-content unit; Update Style keeps a sized style's own unit (rem stays rem under the px setting, px stays px under rem). Changing the setting rewrites nothing. **Zoom (#234/#235) is rem-only:** the limited slope, the fit floor and the word cap all key on `fontSizeUnit: 'rem'`, because px output must stay byte-identical for content saved before #233 and a new px block is indistinguishable from an old one at save time. So with the px setting on, new responsive sizes keep the author's slope (the zoom notice then says 'fails' and suggests values that double) and fit lines never grow with zoom; DOCUMENTATION.md says so.
