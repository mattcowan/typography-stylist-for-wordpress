## Extensibility / Hook System (v2.0.0+)

The plugin provides a lightweight action/filter system (`window.typostHooks`) for JavaScript and standard WordPress hooks for PHP. See [HOOKS.md](../../HOOKS.md) for the complete developer reference. `__tests__/hooks-doc.test.js` (#372) fails when HOOKS.md and the code list different hooks; how to write an entry (a backticked name at the start of a heading, a first table cell or a bold paragraph, under the right section; `{placeholder}` for a name built at run time; `JS_HOOK_WRAPPERS` for a component that fires a hook named by a prop) is in [TESTING.md](../../TESTING.md), "When You Add or Change a Hook".

**Key concepts:**
- Extensions are generally separate WordPress plugins (the bundled Glyphs Panel, Variable Fonts and Paragraph Styles modules are the exceptions — see [bundled-modules.md](bundled-modules.md))
- JS hook containers use `data-hook` attribute for context-aware CSS: `[data-hook="typost_qft_modal_top"]`
- `typost-apply-block-properties` CustomEvent is the generic bridge for extensions to set editor properties
- Block attribute `styleClass` + inline attribute `data-style-id` provide generic infrastructure for class-based styling by extensions
- **Toolbar buttons (v2.3+) are a filter, not a container.** `typost_editor_toolbar_buttons` returns `{id, icon, label, isActive, editors, onClick}` descriptors that core renders as real `ToolbarButton`s in both editors — a foreign React root mounted into a hook `<div>` would sit outside the toolbar's roving tabindex and break keyboard navigation. The click `context` carries `state` (resolved for the clicked block — the shared `typost_current_editor_state` filter only answers for the block holding the caret, so a List View selection would report the default font) and `reopenHost: false` (no host modal was open, so `typost_glyphs_panel_closed` must not open one). Core snapshots the selection into `capturedSelection` before calling `onClick`, which is what makes `typost-insert-content` land at the selection and advance the caret between insertions. In the inline editor, `handleExtensionToolbarClick()` first loads the selection's own properties into state with `readSelectionProperties()` (the same reader the modal uses on open) and calls `onClick` after that commit: with the modal closed, state held what the last modal session left, so a paragraph style applied from the toolbar dropped the selection's `data-animation-id` and the style browser showed no active style or Detach for it (#219 review). `buildQftEditorState`/`resolveBlockSelectionRange` in `blocks/typography-stylist/utils.js` hold the tested logic; both editors use `filterToolbarButtons()` from `assets/js/toolbar-buttons.js` (`utils.js` re-exports it; until #357 `block-editor.js` kept its own copy).
- **Word-boundary notice reaches extension surfaces (v2.3+)**: `getSelectionAccessibility()` resolves the notice fresh from the store (not component state, which a toolbar launch never populates) and rides in the toolbar click context as `accessibility`. The Glyphs panel renders it at the top of its own modal, and offers the fix through the `typost-convert-to-block` CustomEvent — every mounted format instance handles that, which is harmless because `replaceBlocks` on an already-replaced client ID is a no-op.
- **Boolean flags in `typostData` must be cast in PHP (v2.3+)**: options are stored as `'1'`/`'0'` strings and `wp_localize_script()` stringifies everything, so an uncast `'0'` arrives as the **string `"0"` — truthy in JS**. `enableAriaLabels` (since removed, 2026-10: NVDA ignored the label on a generic span and split partial words), `disableAccessibilityWarning` and `showClearConfirmation` were all silently inverted when switched off. They are cast now, and `isFlagEnabled()` (`assets/js/inline-editor/sanitize.js`, used by `block-editor.js`) parses defensively because the `typost_editor_data_{user}` transient can still hold pre-fix values for an hour. Add both when introducing a new flag.
- **Single-setting extension options (v2.3+)**: `typost_admin_options_rows` (echo `<tr>` rows into the core Options tab) + `typost_admin_options_checkboxes` (register the option key, `typost_`-prefixed, so both the REST save and the POST fallback persist it). Checkboxes marked `data-typost-option="1"` are collected generically by `admin-page.js`. Expose the value via `typost_editor_data`, which runs *after* the localized-data transient read, so toggles apply immediately instead of after the hour-long cache.
- **Editor vs Save rendering:** `save.js` uses the CSS class when `styleClass` is set (for the frontend). Since the 2026-09 QA fixes `edit.js` does the same: when `styleClass` names a style that exists (`findParagraphStyleByClass`), the content element carries `typost-styled {styleClass}` and `buildStyle()` (since #356 a wrapper in `edit.js` around `buildEditorStyle()` in `editor-style.js`) emits inline declarations only for attributes that differ from the style (`stylePropertyOverrides`) — the attributes are the Inspector's working copy, so an in-progress edit previews inline while everything else renders from the class, and a fixed px size (a style saved from the inline editor) renders at all. On `typost-paragraph-styles-updated` every block using the style re-syncs its copy from the style (`hooks/use-paragraph-style-sync.js`). The editor iframe receives the class CSS via `enqueue_block_assets`; note WordPress prefixes theme editor styles with `.editor-styles-wrapper`, which is why the module's selectors are boosted to (0,6,0) (see `paragraph-styles/CLAUDE.md`).
- **Glyph insertion swap window (2026-09):** the Glyphs panel's alternates view inserts with `swap: true` only while the author keeps browsing the same character (`shouldSwapInsertion` in `glyphs-panel/assets/js/lib/insertion.js`); both insert handlers run the range through `adjustInsertionRangeForSwap` (utils.js) so a different character goes *after* the glyph that stayed selected for swapping, and an alternate picked right after a caret insertion replaces that glyph (QA finding GP-1).
- **Indirect font references (2026-09):** the frontend font scan applies `typost_content_font_ids` (HOOKS.md) so content styled only through a paragraph-style class still enqueues its font; `Typost::clear_font_detection_cache()` is public so the module can invalidate the per-post detection cache when a style changes.
- **The inline editor registers its extension listeners on mount (#386, v2.4.0):** `TypographyFeaturesControl` (`assets/js/block-editor.js`) only *creates* its seven callbacks in the constructor (`createExtensionListeners()`, `assets/js/inline-editor/extension-listeners.js`; the callbacks themselves are built in `extension-bridge.js`). `componentDidMount()` sets `_isMounted` and registers them (`attachExtensionListeners(this, window.typostHooks, document)`): the `typost_current_editor_state` filter, the `typost-apply-block-properties`, `typost-insert-content` and `typost-convert-to-block` listeners on `document`, and the `typost_glyphs_panel_closed`, `typost_extension_panel_closed` and `typost_editor_toolbar_buttons_changed` actions, in the order the constructor used before. `componentWillUnmount()` removes them from the registry and document it stored (`detachExtensionListeners()`), even if `window.typostHooks` was replaced in between. Attach does nothing while they are registered, detach does nothing when none are. **Why:** with `SCRIPT_DEBUG` on, WordPress loads React's development build, and StrictMode constructs the component twice and runs mount, unmount, mount on the instance it keeps. Registration in the constructor stayed on the instance that was thrown away, and the mounted one had none: on core blocks a style from the style browser, a glyph, Convert to block from a panel, the dialog reopen and the toolbar refresh did nothing, and the state filter answered with an unmounted instance's first state. On sites with `SCRIPT_DEBUG` off (React's production build, no double mount) it worked, which is why it was found only in wp-env (CI). Before the fix, one more orphan instance stayed registered at every selection change; the inline instance is also mounted in a Typography Stylist block (only its toolbar button is hidden), so orphans built up there too. **Rule:** a constructor has no side effects; every registration has its removal, in a mount and unmount pair (`componentDidMount()`/`componentWillUnmount()`, or a `useEffect` with cleanup). A scan of every `addEventListener`, `addAction`, `addFilter`, `.subscribe(`, observer, `setInterval` and `window.x =` in the shipped JS found no other registration outside such a pair (the rest are in a `useEffect` with cleanup, at module scope, in an event handler, or `installModalFocusGuard()`, installed once). **Known gap (order at a selection change):** the editor mounts a new instance at each selection change; the old one detaches in `componentWillUnmount()` and the new one attaches in `componentDidMount()`, both in one React commit. A caller that applies `typost_current_editor_state` for `'inline'` between the two (a `wp.data` subscriber that runs during the commit) gets back the value it passed in, as when no inline editor exists; the next store change asks again and gets the mounted instance's state. Before 2.4.0 the new, not yet mounted instance answered in that moment. Any commit-time registration has this gap, and only commit-time registration is safe under StrictMode. With `SCRIPT_DEBUG` off, the registered lists, their positions relative to the block's own providers and the instance that answers were measured the same as before in 7 scenarios. `assets/js/__tests__/inline-editor-listeners.test.js` renders the real component in StrictMode; `tests/e2e/inline-extension-listeners.spec.js` covers each route in wp-env. A related, unfixed property of both hook registry twins (`hook-registry.js` and `edit.js`, docs/twins.md row 41): `doAction`/`applyFilters` loop over the array they read when the call started, so a callback removed during the call still runs; this is why the `_isMounted` guards in `extension-bridge.js` stay.
- **Active block variation (#410, v2.4.0):** the plugin registers one default inserter variation of `typost/block`, `typost-new-block`, whose `isActive` matches every Typography Stylist block that no other variation claims. `getActiveBlockVariation('typost/block', …)` therefore returns it (before 2.4.0: `null`); an extension's own variation still wins for the blocks it claims. See [new-block-variation.md](new-block-variation.md).
- **Remove all styling leaves extension attributes (#411, v2.4.0):** `layeredConfigId` and `animationConfigId` are in `THEME_LOOK_UNDECIDED_ATTRIBUTES` (`assets/js/theme-look.js`), so "Remove all styling" and "Reset Entire Block" keep them. See [remove-all-styling.md](remove-all-styling.md).

**Filter hooks for extensibility:**
- `typost_available_features` - Filter available features
- `typost_presets` - Filter presets list (renamed from `typost_default_presets`; update any custom integrations using the old hook name)
- `typost_force_enqueue_font_ids` - Force fonts (by numeric ID) to load on every page — for fonts referenced only from theme/extension CSS (v2.1+; see HOOKS.md)
