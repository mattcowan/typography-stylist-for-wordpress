# Screen reader and focus rules

- **Topic:** focus and screen reader rules for the plugin's modals (the focus guard, notices that mount with a modal, scroll containers, drag and resize handles, the style browser) and for the settings page tabs.
- **Issues:** #349, QA Session B (2026-09, SR-7)
- **Code:** `blocks/typography-stylist/utils.js` (`installModalFocusGuard()`), `assets/js/font-picker.js`, `assets/js/block-editor.js`, `blocks/typography-stylist/components/quick-feature-toggles.js`, `paragraph-styles/assets/js/editor.js`, `includes/admin-page.php`, `assets/js/admin-page.js`, `tests/e2e-sr/`

Moved from the "Key concepts" list of the root [CLAUDE.md](../../CLAUDE.md) by #361 (the rest of that list is in [extension-api.md](extension-api.md)).

- **Modal focus guard (2026-09):** `installModalFocusGuard()` (utils.js, installed once from `edit.js`) keeps focus inside any `typost-*` modal when RichText re-applies a selection after an apply/insert. Firefox moves the active element into the canvas iframe on that write *without firing any focus event in either document* and ignores `focus()` on the element it still records as focused, so the guard combines focusout/focusin listeners, a `focusin` listener attached on demand to the canvas document, a 100 ms poll that runs only while a plugin modal is open, and a "focus the frame first" fallback. Keyboard users were otherwise stranded outside an open dialog with Escape dead (QA finding SR-7).
- **Screen-reader rules for the plugin modals (2026-09, QA Session B):** (1) core's `Notice` pushes its content into the a11y live region the moment it mounts, which is the same tick a modal takes focus, so NVDA read a notice *before* the dialog's name — every notice that mounts with a modal passes `spokenMessage=""` and, when it matters (the word-boundary warning), is announced by a deferred `wp.a11y.speak()` ~800 ms later, after the title. (2) Scroll containers are Tab stops in Firefox and Chrome and a screen reader reads the whole container at that stop, so `typost-modal-content` / `typost-scrollable-content` carry `tabIndex={-1}` (their controls still scroll them into view); the same fix is applied to the font picker's suggestions `<ul role="listbox">` by a MutationObserver in `assets/js/font-picker.js`, because core renders it without a tabindex. (3) The draggable header is a mouse-only drag surface (no role, no tabindex); keyboard repositioning is the named "Move panel, use arrow keys" button beside Close, and the tips bar has its own "Dismiss tip" button instead of Notice's "Close". (4) The resize handles are `aria-hidden` mouse affordances (they had `role="slider"` with no value and no keyboard handler). (5) The Paragraph Styles browser focuses the active (else first) row on open; the toolbar click context's `state.selectionParagraphStyleId` (the `data-style-id` at the captured selection, from `parseInlineStylesAtCursor().styleId`) is what it marks active in selection scope, never the block's `paragraphStyleId`. (6) Both editors confirm before a paragraph style replaces the selection's own styling (`countInlineParagraphStyleConflicts()` on RichText formats for the inline editor, `countParagraphStyleConflicts()` on HTML for the block) and fire `typost-paragraph-style-apply-cancelled` on cancel so the module's panel drops its badge. (7) The inline modal's Paragraph Style panel has no select: "Browse styles…" opens the module's `ParagraphStylesBrowser` through `openBrowser({ editorSource: 'inline' })`, which applies through the `source: 'inline'` route and reports back via `onApplied`; the browser filters with `filterParagraphStyles()` and pages `BROWSER_PAGE_SIZE` (24) rows at a time.
- **No `aria-controls` on the settings tabs (2026-11, #349):** with it, NVDA in Firefox spoke each tab twice per arrow key ("Options, tab, selected, 6 of 10. Options, tab, selected, 6 of 10"). Measured in the NVDA harness: removing only that attribute gives one announcement; removing the panels' `aria-labelledby`, emptying the panels, blocking the panel focus call or moving focus before selection do not; a minimal tablist speaks once, and twice after `aria-controls` and hidden panels are added. The tab code is older than v2.3.0 and an NVDA run in 2026-09 heard each tab once, so an NVDA or browser update may have exposed it (not checked). Chrome not tested. `admin-page-markup.test.js` and `tests/e2e-sr/admin-tabs.sr.spec.js` hold this.
