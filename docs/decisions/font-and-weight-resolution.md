# Inherited font and rendered weight

- **Topic:** which font id and weight the editors report for text the theme styles (`fontId`, `fontWeight`), which values code that saves must read instead (`explicitFontId`, `explicitFontWeight`, `selectionFontWeight`), and when the inline editor writes `data-fontweight`.
- **Issues:** #254, #278, #280, QA 2026-09 E-2 and E-3
- **Code:** `assets/js/font-options.js` (`resolveFontIdFromFamily()`), `assets/js/inline-apply-rules.js`, `assets/js/block-editor.js`, `assets/js/inline-editor/`, `blocks/typography-stylist/utils.js`, `glyphs-panel/assets/js/lib/insertion.js`

Moved from the "Key concepts" list of the root [CLAUDE.md](../../CLAUDE.md) by #361 (the rest of that list is in [extension-api.md](extension-api.md)).

- **Inherited font resolution (v2.3+)**: text styled only by the theme carries no `data-font-id`, so the shared editor state used to report `fontId: 0` and the Glyphs panel fell back to the first font in the list. Both editors now resolve the *rendered* family back to a numeric id with `resolveFontIdFromFamily()` ([assets/js/font-options.js](../../assets/js/font-options.js), the inverse of `resolveActiveFontFamily`) and report it: inline via `getInheritedFontId()`, the block via `qftStateRef.current.inheritedFontId` (assigned after `fontIdMap` exists — the ref is built earlier in the render, so referencing the map at that point is a TDZ error). Precedence is inline span → block attribute → inherited. **Persisting consumers read `explicitFontId` / `explicitFontWeight` instead (v2.3.3+, #278):** the same values without the inherited/rendered fallback (inline `getExplicitFontId()` — a font picked in this popover session, else `resolveSpanExplicitFontId()`: the span's `data-font-id`, or under a `data-style-id` the style's current font unless the span declares its own `font-family`, the font twin of `resolveSpanStoredFontWeight()` — and `getSetFontWeight()`, which is `getEffectiveFontWeight()` minus the computed weight; QFT: span/block font, and style-span → stored → block weight, never `<strong>`). Paragraph Styles diffing/saving/detaching the rendered `fontId` wrote the theme's font onto spans on Detach and into styles on Save.
- **Rendered weight, not the `'400'` default (v2.3+)**: a core heading is bold because of theme CSS, while `fontWeight` defaults to `'400'` and save always emits it. Treating unset as 400 lightened converted headings *and* made Glyphs-panel insertions lighter than the surrounding headline, because consumers wrote the reported weight onto the span they created. `getEffectiveFontWeight()` is the single source: a weight the author picked in the popover (tracked by `_pendingChanges.keys`; first since the PR #280 review, because the pick reaches the span only after the debounced apply, matching `resolveWeightToWrite()`; a pending clear — an apply event with an empty `fontWeight`, which sets the popover weight to `'400'` — skips both the pick and the stored weight, `resolveSetFontWeight()`) → a stored `data-fontweight` on the selection (`getStoredFontWeight()` → `resolveSpanStoredFontWeight()`: on a span with a `data-style-id` the attribute counts only with an inline `font-weight`, because the apply path keeps it under a style without one and no CSS reads it; `getExplicitFontWeight()` stays raw for the apply path and the weight select) → the weight of the paragraph style on the selection (`resolveParagraphStyleFontWeight()` in `inline-apply-rules.js`, #254 — the computed weight is read from the block element, which a style span does not change) → the computed weight. It feeds both `convertToBlock()` and the `typost_current_editor_state` filter. **Inserted glyphs write only a stored weight (#254):** the state also reports `selectionFontWeight`, the `data-fontweight` stored on the selected text ('' when inherited from a style, `<strong>`, the block or the theme); the block derives both values in `resolveSelectionFontWeights()` (utils.js) from `parseInlineStylesAtCursor()`'s `storedFontWeight` / `styleFontWeight` (the first span out from the selection that decides a rendering weight; its `fontWeight` stays the raw first `data-fontweight` for the QFT controls) and `boldInsideStyleSpan` (a `<strong>`/`<b>` inside the style span renders 700). The Glyphs panel writes only `selectionFontWeight` (`resolveInsertionFontWeight()` in its `insertion.js`), so an inherited weight reaches the glyph through CSS and the insert handlers' format merge and is never baked inline over a style's class. `getActiveFontWeight()` hard-defaults to `'400'`, so `getExplicitFontWeight()` exists to tell "unset" from "deliberately 400". The apply path follows the same idea (QA 2026-09 E-2): `resolveWeightToWrite()` in `assets/js/inline-apply-rules.js` writes `data-fontweight` only when the selection already stores a weight or the author picked one in this popover session (`_authorPickedWeight`); the select opens on `getEffectiveFontWeight()` for display only, so a feature toggle on a theme-bold heading never writes 400. `buildConvertBlockAttributes()` (same module, E-3) gives a partial-selection conversion inherit defaults on the block — the span keeps the selection's size, spacing and line height — and carries the modal state only for a whole-block conversion. The block-menu transform can't reach the DOM through its attributes-only signature, so it uses `detectBlockComputedWeight()` in `utils.js`, locating the source through the selection and bailing when more than one block is selected.
