# WP Font Library integration

- **Topic:** how plugin fonts are registered in the WordPress Font Library and Library fonts are adopted for the editor: identity, CSS, adopted font faces, lifecycle, and the slashing rule for JSON post content.
- **Issues:** #310, QA 2026-09 E-8 and E-16 (WordPress 6.5+)
- **Code:** `includes/class-typost-font-library-bridge.php`, `includes/class-typost-font-sources.php`, `typography-stylist.php`, `tests/Unit/FontLibraryBridgeTest.php`

Moved from the root [CLAUDE.md](../../CLAUDE.md) by #361. The REST routes are listed in [rest-api.md](rest-api.md).

## WP Font Library Integration (v2.1+, WP 6.5+)

- **Identity:** the numeric `font_id` stays canonical forever. Registration adds `wp_slug`/`wp_post_id`/`wp_registered_date` fields to the font entry and stamps `_typost_font_id` post meta on the created `wp_font_family` post (ownership marker — rollback never deletes user-created families). Font binaries are NOT copied; `wp_font_face` posts reference the plugin's existing upload URLs.
- **CSS:** entries with a live registration emit `--font-N: var(--wp--preset--font-family--{slug}, "Family", fallbacks)` — the literal `var()` fallback covers plain admin pages (no preset vars) and stale registrations, so content can never break. The frontend `@font-face` path skips a font only when WordPress will **actually print** its faces (`entry_faces_printed_by_wordpress()`: family present in `WP_Font_Face_Resolver::get_fonts_from_theme_json()`, i.e. theme fonts + Library fonts *activated* in global styles). A live registration alone is installed-not-activated — `wp_print_font_faces()` emits nothing for it, so the plugin keeps printing its own `@font-face` (the frontend would otherwise silently fall back to local/system fonts while the editor looks correct). Editor-iframe/admin-preview paths intentionally keep the plugin CSS.
- **Adopted fonts get the same treatment (2026-09, QA finding E-8):** an adopted entry has no `css_content`/`font_faces` of its own, so the plugin builds its `@font-face` rules from the family's `wp_font_face` posts (`Typost_Font_Library_Bridge::build_font_face_css_for_family()` → `build_font_face_rule()`, pure and allow-list sanitized: family, style, weight incl. `"100 900"` ranges, display, stretch, unicode-range, `src` string or array via `esc_url_raw()` with the format hint derived from the file extension; faces without a usable `src` are skipped). On the frontend they print only when the font is in use (its `font_id` is in the detected/forced IDs, the same signal as the kits) **and** WordPress will not print it (`adopted_entry_faces_printed_by_wordpress()`, matching on the first family of the entry's `font_family` stack); the slugs the plugin prints for are folded into `get_font_css_cache_key()` so activating the family later cannot serve stale CSS. The editor iframe (`typost-block-fonts`), the popover-preview handle (`typost-editor-fonts`) and the admin preview (`get_admin_font_css()`, also returned by `admin/refresh`) include every adopted font unconditionally, like the kits, so their static transient keys stay valid (a duplicate of a face WordPress also prints is harmless). Adopted entries that share a `font_id` or slug with an uploaded kit are skipped everywhere — the kit-reuse branch of `adopt_library_font()` already prints through the kit path. Deleting an adopted family through the Library UI is reported by `handle_deleted_post()` (entry untouched) so `on_wp_font_family_deleted()` clears the CSS caches; `save_post_wp_font_face` → `on_wp_font_face_saved()` runs `clear_cache()`, so a face added to an already-adopted family reaches the printed CSS on the next request, and `save_post_wp_font_family` → `on_wp_font_family_saved()` invalidates the per-user editor-data transients so a family installed in the Library is in the picker on the next editor load instead of after the hourly transient expires (QA E-16; the widened `on_wp_font_family_deleted()` does the same for deleted families that were never registered or adopted).
- **Lifecycle:** new uploads auto-register when `typost_auto_register_wp_fonts` is on (default) and WP ≥ 6.5; existing fonts are opt-in (per-font/bulk buttons + dismissible notice on the Custom Fonts tab). A `deleted_post` watcher rolls back registration fields if the family is deleted via the Library UI. Registration REST endpoints require `manage_options`; the editor's adopt endpoint (`POST /typost/v1/wp-fonts/adopt`) requires `edit_posts`.
- **Post content must be slashed (#310):** `wp_insert_post()` and `wp_update_post()` unslash their input, so every JSON `post_content` goes in as `wp_slash( wp_json_encode( … ) )`, as core's REST controllers do. Before 2.3.4 `register_font()` skipped it: a family name with a space (quoted by `build_font_family_post_content()`) stored `"fontFamily":""EB Garamond""`, which `json_decode()` rejects (core's `GET /wp/v2/font-families` returned `fontFamily: ""`), and a `\uXXXX` escape decoded to the wrong name; `\/` in face URLs survived. The `FontLibraryBridgeTest` doubles for both functions unslash like core so the omission fails a test. `repair_registered_font_json()` rewrites posts registered before the fix, from `maybe_repair_font_library_json()` on `admin_init` for a `manage_options` user (registration's own capability, so kses treats the JSON the same; for a user without `unfiltered_html` it turns a bare `&` in a face URL into `&amp;`, as at registration), behind the non-autoloaded `typost_font_library_json_repaired` option (the plugin has no version-upgrade routine; same pattern as `typost_htaccess_verified`). It returns `{repaired, failed}`, and the flag is stored only after a run with no failed `wp_update_post()`, so a failed post is retried on the next admin request (cross-session review). Scope: families owned by an entry (`wp_post_id` + matching `_typost_font_id`, the `unregister_font()` rule) and their faces, matched by post title (`pick_face_content()`: two faces can share a title — same family, style and weight, other files — so a title with several candidates takes the one whose content the post holds or whose stripped JSON it equals, and a post that matches none is skipped rather than given another face's files; PR #318 review); a post is rewritten only when its JSON does not decode, or when it decodes to something else *and* equals the rebuilt JSON with backslashes stripped — so a face that lost only `\/` escapes, or anything a user edited, is left alone. Verified on the test site (WP 7.1.3): 11 of 12 owned families rewritten, each differing from its backup only by restored backslashes; 65 valid posts untouched; a second run rewrote 0. Not repaired: global styles keep their own copy of a family's settings when it is activated in the Library, so a family activated while its JSON was broken may hold an empty `fontFamily` there (user data outside the plugin's posts; not reproduced — the test site's global styles hold no font families).
- **Adoption:** picking an unadopted Library font in the editor allocates a `font_id` and stores a manual-fonts-shaped entry in `typost_adopted_wp_fonts` — the block save format never changes. Adobe Fonts (remote Typekit CSS, EULA) and manual definitions stay plugin-managed by design.
