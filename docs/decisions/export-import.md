## Export & Import (v2.3.5+, #205)

Settings → Typography Stylist → **Export & Import** writes one JSON file and imports it on another site (staging → production, a house style set on each client site). Step 1 of the issue: the file format, fonts and paragraph styles. Step 2 (decisions in the #205 comment of 2026-10-29): presets, options, Feature Visibility and variable font axes; the font order is not exported (it orders one site's whole list).

- **Step 2 sections** use the generic **row** preview form (`{rows: [{key, name, detail?, note?, current?, incoming?, choices: [{value, label}], choice}], notes?}`, HOOKS.md "Rows"): the server sends every label, `admin-export.js` renders any section with `rows` in one table (`renderRows()`, `rowFieldId()`, `rowSectionIds()`), and the answers go back as `choices.sections[id][key] = value`. A row with `choice: ''` has no default and blocks Import (client `collectErrors()` and the section's dry run both check). Results return `groups: [{heading, items}]`. `Typost_Export_Settings` ([includes/class-typost-export-settings.php](../../includes/class-typost-export-settings.php)) registers `featureVisibility` (priority 10), `presets` (30) and `options` (40); the Variable Fonts module's `Typost_VF_Transfer` registers `variableFonts` (15). Only the per-font sections (`featureVisibility` 10, `variableFonts` 15) import before the paragraph styles (20), so the styles' hidden-feature / undefined-axis warnings read the imported settings; `presets` (30) and `options` (40) import after them.
  - **Options:** keyed by option name. `Typost_Admin_Options` ([includes/class-typost-admin-options.php](../../includes/class-typost-admin-options.php)) holds the definitions (label, type, default) and the one `sanitize()` that the Options REST handler, the Accessibility REST handler, the no-JS POST fallback and import all use (#205: "the two paths cannot drift"). `definitions($typost)` drops `typost_auto_register_wp_fonts` without the Font Library and adds every `typost_admin_options_checkboxes` option with its label/default from the new `typost_export_option_details` filter (Glyphs and Paragraph Styles register theirs). Only options that differ get a row, each with no default (`keep`/`apply`); an import missing an answer is refused before anything is written. Names the site does not define are listed and never written.
  - **Presets:** only the stored `typost_presets` (built-in defaults are empty). Name clash → skip by default; "Add as “Name (2)”" (server-suggested, no text field) or overwrite (keeps id and name). Unknown features are dropped; a preset left with none is not imported and is listed. New ids `preset-{slug}[-N]`.
  - **Per-font settings:** written under file font keys and returned from `fontKeys`, so a font only these settings use is not imported when the section is left out. One row per font, `apply`/`keep`, starting on `keep` when the font this site maps to has its own settings (`Typost_Export_Settings::font_settings_row()` / `font_settings_choice()` / `font_settings_groups()`, shared with the VF module). Variable fonts store by string ID, so the transfer maps numeric ↔ string through `get_fonts_map($typost)` (now public, takes a Typost or a double) and reads the map after the font commit so added/adopted fonts resolve; axes go through the module's `sanitize_axis()` (now public). `Typost_Export_Fonts::set_file_fonts()` / `file_font_name()` let a section name a file font.

- **`Typost_Export`** ([includes/class-typost-export.php](../../includes/class-typost-export.php), lazily built by `Typost::export()`): the file (`{format: "typost-export", version: 1, plugin, exported, fonts: {f1: descriptor}, sections: {id: data}}`), `parse_file()` (rejects text over 2 MB, invalid JSON, another `format`, a missing or newer `version` — each message ends "Nothing was saved."), the section registry (`typost_export_sections`, HOOKS.md "Export Sections"), `build_export()`, `preview()`, `import()`, three REST routes and the tab (`register_admin_tab()` priority 90, `render_admin_tab()` → [includes/admin-export-tab.php](../../includes/admin-export-tab.php), `enqueue_admin_assets()`). **Import is two passes:** every section's `import` runs with `$dry_run = true` first (a `WP_Error` stops everything, nothing written), then fonts are committed, then each section writes. A font that only left-out sections use (`include`, read through each section's `fontKeys`, `font_users()`) is dropped before `validate_choices()`: no choice needed, nothing added or adopted. A font that no section uses (carried by "All fonts") still imports as chosen; preview rows carry `sections` so the UI disables those selects. The file is sent again with the import rather than kept on the server between preview and import.
- **Fonts never travel as IDs.** `Typost_Export_Fonts` ([includes/class-typost-export-fonts.php](../../includes/class-typost-export-fonts.php)) writes a descriptor per used font (`key_for_font_id()`, following `typost_font_replacements` for a deleted font): uploaded kit `{family (font_faces[0]), name, slug?, fallbacks}`, Adobe `{family, kit (project ID without "adobe-"), kitName, cssUrl, availableWeights?}`, manual `{family (first of the stack), fontFamily, fallbacks}`, Library `{family, slug}`. `match_descriptor()` runs Adobe project + family → Library slug **and** family (a `-2` slug suffix is another family) → family → display name, case-insensitive; the first step with any match decides; more than one candidate is **ambiguous** and the author must pick (`validate_choices()` rejects an empty target) — the plugin never guesses. No match: Adobe (with a valid `https://use.typekit.net/{kit}.css` for the same kit) and manual definitions are **addable** (`Typost::add_adobe_font_entry()` joins an existing project; `add_manual_font_entry()`; both share the add endpoints' entry builders), anything else is **not found** (no font, listed in the result). A Library font not adopted yet is a `wpl:{slug}` candidate and is adopted on import. The author can map any font to any font on the site (`siteFonts`).
- **Paragraph styles section** (`Typost_PS_Transfer`, in the module): see `paragraph-styles/CLAUDE.md`. New IDs past the counter, Based On kept, skip/rename/overwrite per style.
- **Nothing left behind:** `tests/Unit/ExportRegistryTest.php` fails when an option in code is not deleted by `uninstall.php`, when a name `uninstall.php` deletes is neither in a section's `options` nor in `Typost_Export::NOT_EXPORTED` (with a reason), and when a key `sanitize_properties()` accepts is missing from the round-trip fixture. Checklist step 7 in `docs/typography-property-checklist.md`.
- **UI:** [assets/js/admin-export.js](../../assets/js/admin-export.js), hand-written ES5, enqueued unminified with `jquery` + `typost-admin` (uses `typostWithUserLocale`, `typostBeginBusy`/`EndBusy`, `typostDecodeEntities` from admin-page.js). Its strings are a **flat** localized object (`typostExportL10n`, from `Typost_Export::script_strings()`), which WordPress entity-decodes (#307), and every string reaches the page through `textContent`; a source test forbids `innerHTML`/`.html(`. Helpers are exported for Jest (`admin-export.test.js`); `admin-export-dom.test.js` drives the forms in jsdom with the real strings and checks the fixture against the template. Focus: the preview and result headings take focus; an unchosen font or a bad new name is marked `aria-invalid` and focused. "Import another file" reloads the page with `tab=export` (`exportTabUrl()`: tab clicks do not change the URL, so a plain reload opened the first tab) so the other tabs list the imported styles. Cancel is disabled while an import runs (the server writes anyway), and a failed preview clears the previous file's preview so it cannot be imported by mistake. Verified in Chromium against the real PHP classes with stubbed WordPress (two seeded sites), and on the test site (WP 7.1, real nonce): same-file re-import (all found, all skip), add a font definition and an Adobe project, adopt a Library font, rename, overwrite, both warnings, and the tab in French.
