# Fit-to-width natural width

- **Topic:** why a fit-to-width block gets a zero-height `::before` float, so that a parent that shrinks to fit does not give it 0px, and what that costs in a theme's own flex, grid or table layout.
- **Issues:** #243
- **Code:** `blocks/typography-stylist/style.css` (the `.wp-block-typost:has(> .typost-fit)::before` rules)

Moved from the root [CLAUDE.md](../../CLAUDE.md) by #361. How fit-to-width sizes are measured and written is in [font-size-units-and-zoom.md](font-size-units-and-zoom.md).

**Fit-to-width natural width (#243):** `container-type: inline-size` on `.typost-fit` makes the block's natural (max-content) width 0, so a parent that shrinks to fit (a column-flex item with auto margins — a sticky-footer theme centering the editor root — a float, a table cell) gave it 0px and every `cqi` line size 0. `style.css` adds a `::before` on `.wp-block-typost:has(> .typost-fit)` (not in a grid, and in a Row only on an item with no `wp-container-content-*` class) whose content is two zero-width spaces around one space widened to `100vw` by `word-spacing`: max-content grows to 100vw, min-content stays 0, so shrink-to-fit parents fill the available width and nothing overflows. Rejected alternatives, measured in Chromium 145 + Firefox 146: `contain-intrinsic-inline-size: 100vw` also sets min-content, so Row items, Fill items, Media & Text and max-width-less roots overflowed; an in-flow line or empty `minmax(0,100vw)` grid stopped the wrapper's and the heading's top margins from collapsing (+16px with a UA heading margin) — hence `float: left` with zero height, which keeps margin collapsing intact and still counts toward the parent's intrinsic width. A float is not free, though: it takes part in float placement. Without a margin its used width was the wrapper's full width, so after an earlier float (an aligned image) it dropped below that float, CSS 2.1 §9.5.1 rule 5 then held every later float below it (a later left float +204px in the harness, +278px in the review's own test), and in Chromium the styled heading itself moved under the image (1000px wide instead of 700px beside it). `margin-inline-end: -1000%` removes that: a percentage margin resolves to 0 in intrinsic contributions (max-content stays 100vw in both engines), while in layout a float's shrink-to-fit width is capped by its containing block minus its margins (W + 10W), so its outer width is min(11W, 100vw) − 10W, which is ≤ 0 whenever the wrapper is at least 10vw wide, and the float fits beside any earlier float. `-100%` was tried first and is not enough: outer = min(2W, 100vw) − W returns to W whenever 100vw ≥ 2W, i.e. a normal 650–800px content column on a desktop viewport (round-2 review; later float at 350 instead of 77). Not `-10000%`: Chromium's LayoutUnit saturates near ±33.5M px, and a 3000px wrapper would reach −30M. A length margin (`-100vw`) cannot work: it counts in the intrinsic contribution and nets max-content to 0. Measured with no page-level horizontal scroll in LTR and RTL. Do not use `::after`: the editor draws the block outline with it. **Accepted cost (decided 2026-10-08, keep the selector broad):** in a theme's own flex, grid or table container (no core layout class), the 100vw max-content competes with siblings — a fit block in an `auto` grid track left a `1fr` column at 73px, a theme flex sidebar went 128 → 105px, an auto table's text cell 992 → 694px. In each case the fit block was 0px before. Narrowing the selector to core layout classes would remove this but drop the fix for floats, table cells and classic-theme content areas. **Rows:** a Row item with no width setting is 0px wide at its content size, so it gets `flex: 1 1 0` (behaves as Grow). Core adds the `wp-container-content-*` class only when the child layout emits CSS (PHP `wp_render_layout_support_flag()` checks `$child_css`; editor `useBlockPropsChildLayoutStyles` returns no class for empty CSS), so with no per-viewport layout, no class = default or explicit Fit and class = Grow/Fixed, which keep core's rules. WP 7.1 also builds the class from `@mobile`/`@tablet` child-layout overrides and adds it when any of them emits CSS, so a default-width item with a mobile Grow override carries the class at every width and stays 0px on desktop (the pre-#243 result). `is-vertical` comes only from the base `layout.orientation`, so a Stack whose orientation is overridden to a row on one viewport keeps the `::before` with `flex-basis: auto` there, and its fit item asks for a 100vw basis. Neither is a regression for the fit block itself. The default Row item also gets the `::before` so a Row inside a shrink-to-fit root still grows (basis 0 keeps the line out of the item's own size). A Grow item cannot get it (basis auto would become 100vw), so a Grow fit block in a Row that is the post's only content still shows 0px in a sticky-footer editor — accepted corner. Stack (`.is-layout-flex.is-vertical`) gets the `::before` for its cross-axis width. Verified on the test site (WP 7.1.2) in Chromium + Firefox: frontend widths unchanged for Columns/Group/Row Grow/Row Fixed; Row default 0 → 923px with the neighbor unchanged; Stack 0 → full.
